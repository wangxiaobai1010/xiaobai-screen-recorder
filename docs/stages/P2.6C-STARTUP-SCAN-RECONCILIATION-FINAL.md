# P2.6C Startup Scan / Safe Reconciliation / User Recovery Candidates

## 1. 阶段目标

P2.6C 建立从应用启动到用户可见恢复候选的完整安全链：发现历史 Session，只读交叉验证 Manifest 与文件系统事实，保守分类异常 Session，建立持久文件身份与跨进程生命周期证据，在操作时重新验证全部授权事实，并仅允许一种受限 Manifest 元数据协调。该链已接入正式应用启动，只有用户明确操作才会尝试恢复，成功后还必须重新扫描确认。

## 2. 阶段非目标

本阶段不证明真实进程崩溃、强制结束或断电后的端到端技术恢复能力，不实现视频内容修复、自动删除、磁盘策略、正式视觉精修或任何 P2.6D 能力。P2.6C 通过不能写成“完整崩溃恢复 PRODUCT-PASS”。

## 3. 完整实现链

正式链路为：

`canonical SessionId / shared OutputRoot / structured ParseResult / handle-based PathSafety`

→ `read-only SessionInspection`

→ `persistent FILE_ID identity + session lifetime owner evidence`

→ `operation-time ReconciliationEvidenceGuard + expected-revision CAS`

→ `schema 2 ReadyToPublish -> schema 3 ReconciledCompleted`

→ `asynchronous startup inspection`

→ `user-visible recovery candidate`

→ `explicit user action`

→ `rescan confirms ReconciledCompletedConsistent`。

## 4. 模块职责图

- `RecordingSessionIdentity`：唯一 canonical SessionId 规则；Writer 使用 36 字符大写、无花括号 GUID，Reader 按 GUID identity 兼容花括号与大小写差异后规范化。
- `RecordingOutputRoot`：唯一 OutputRoot/SessionsRoot 解析规则；`SessionsRoot = MediaOutputRoot/sessions`。
- `SessionManifest`：持久事实、结构化解析、revision 与原子 CAS；不替代运行时 Snapshot。
- `SessionPathSafety`：基于句柄的只读路径事实；字符串前缀不是安全证明。
- `SessionInspection`：只读扫描和保守分类；不授予 mutation。
- `PersistentFileIdentity`：持久化和比较 volume identity + `FILE_ID_128`。
- `SessionLifetimeOwner`：以 kernel handle/share-mode 判断 live owner；文件存在和 PID 都不是所有权事实。
- `ReconciliationEvidenceGuard`：操作时重新取得并持有证据，阻断 TOCTOU。
- `NarrowReconciler`：唯一窄元数据 transition。
- `StartupInspectionCoordinator`：启动期 single-flight、异步扫描、取消和关闭编排。
- Recovery coordinator/UI：展示安全候选，接收明确用户操作，调用窄协调并强制 rescan。

## 5. 安全不变量

1. 无法证明安全即 Retain。
2. ScanResult 是点时观察，不是 mutation capability。
3. 所有 scanner classification 均保持 `deleteAllowed=false`、`reconciliationAuthorized=false`。
4. 历史恢复不移动、复制、删除、截断、修复或清理媒体。
5. 唯一允许的历史 mutation 是严格受 Guard 与 CAS 约束的 Manifest 元数据更新。
6. persistent identity 只能证明同一底层文件对象，不能证明历史上由哪个 publish API 完成移动。
7. owner 文件存在与 PID 不构成 live owner 证明。
8. NarrowReconciler 只能执行唯一 transition，且不可扩展为通用状态修复器。
9. 恢复必须由用户明确触发；启动扫描不得自动调用 NarrowReconciler。
10. 只有 rescan 得到 `ReconciledCompletedConsistent` 才可向用户报告成功。

## 6. Read-only Scanner

Scanner 只枚举 `SessionsRoot` 的 immediate children，不递归搜索媒体目录，也不修改 Manifest 或媒体。Session 目录、Manifest、三路径文件事实、owner、revision 与 identity 均以结构化结果表达；单个 Session 的 malformed、inaccessible 或未知事实不会终止整个扫描。任何异常、未来 schema/state 或不完整证据均进入保守分类。没有 Session 目录的孤立媒体仍是已知发现盲区。

## 7. File Identity

P2.6C 在 durable rename 前持久化 working 文件的 volume identity 与稳定 `FILE_ID_128`，并在发布后/历史检查时用句柄重新取得当前文件身份。强 identity match 只说明当前位置上的文件与持久证据指向同一底层对象；它不证明历史 Native `MoveFileExW` 一定成功，也不把手工 same-volume move 伪装成 Native publish。

## 8. Lifetime Owner

`session.owner.lock` 是持久 rendezvous 文件，真正的 active owner 事实来自当前进程持有的 kernel handle 和排他 share-mode。维护路径使用 existing-only acquisition，不创建虚假的 owner 证据。owner EvidenceMissing、Unsafe、Inaccessible、IoFailure 或 Active 均阻止自动协调；PID 只可诊断，不能参与正确性判断。

## 9. Reconciliation Guard

Guard 在 mutation 前按固定顺序重新取得 maintenance lease、锁内重读 Manifest、核对 expected revision、重验安全路径、持有 final handle、比较 persistent identity、要求 hard-link count 为 1，并确认 Working 缺失；紧邻 CAS 前再次确认 Working 缺失。旧 ScanResult 不参与授权。资源由 RAII 逆序释放，锁忙或任何 reparse、identity、revision、sharing、filesystem 变化均 fail-closed。

## 10. Schema 3 与历史真相

`ReconciledCompleted` 是独立持久状态，不等于 Native `Completed`，也不等于 `OutputSuccess`。schema 3 明确保留：

- `published=false`
- `publishedPath=""`
- `originalPublishResultKnown=false`

它只表达“当前同一底层媒体对象已在 PlannedFinalPath 得到确认”，绝不声称历史 Native publish 结果已知或成功。Schema 3 Reader/Classifier 先于 Writer 激活，未知或不一致的 schema 3 事实继续 Retain。

## 11. NarrowReconciler

唯一 transition 为严格 schema 2 `ReadyToPublish` → schema 3 `ReconciledCompleted`。它要求完整 operation-time Guard 证据、immutable whitelist、单一 `nowUtc`（`updatedAtUtc == reconciledAtUtc`）和 expected-revision CAS。重复调用以 target semantic equivalence 判定 `AlreadyReconciled`，并发 loser 不产生 N+2 write。它只修改 Manifest 元数据，不修改媒体；不存在第二种恢复 transition。

## 12. Startup orchestration

正式 MainForm 在 Preview lifecycle 初始化成功后调度一次异步历史扫描，不 await 扫描来阻塞 Preview 或 Recording。Coordinator 对同一实例 single-flight，MainForm 另有 schedule-once 门禁；异常被终态化为诊断，不破坏 Preview。关闭时先请求取消，再退订并等待 worker 真正结束后释放相关对象，late callback 通过 source、generation、snapshot 与 disposed/closing 双重检查被抑制。启动路径不会自动调用 NarrowReconciler。

## 13. User recovery candidates

恢复提示是非阻塞、非 MessageBox、不抢焦点的开发期最小 UI，不取代 Preview 首页。用户文案不暴露 Manifest、schema、revision、HRESULT、FILE_ID 或 reconciliation 等工程术语。只有 `PublishOutcomeUnprovenRetain` 且 owner inactive、revision 和安全证据完整的唯一候选显示“尝试恢复”；其余 Session 只保留或不提供按钮。只有按钮的明确用户操作才调用正式 NarrowReconciler，随后必须 rescan；仅 `ReconciledCompletedConsistent` 可显示成功。

## 14. ABI 总览

- Product API：`0x00040003`
- `XbRecordingSnapshot`：2856 bytes，既有字段 offset 与语义不变
- Historical Scan ABI：`0x00010001`
- Narrow Reconciliation ABI：`0x00010001`
- Narrow Layout / Options / Result：32 / 48 / 64 bytes
- Pack：8

历史扫描与 recovery 使用独立、版本化 ABI，没有塞入 RecordingSnapshot。Managed 侧对 size、offset、版本、UTF-16 和枚举/布尔事实执行 fail-closed layout 门禁。

## 16. 两个 test blocker 及关闭方式

### FrameTap test contract

旧 fixture 把生产允许的 `try_lock` lock-busy 安全丢帧错误固定为“第一次 tap 必须立刻抢到锁”。`53d807e` 仅在 NativeTests 将它收口为 64 attempts / 250ms 的有界合同，继续严格证明 generation 建立、过渡帧安全丢弃和固定纹理池事实。该修复没有修改生产 `RenderFrameTap`、NV12 pool/converter 或 Encoder 核心，是 `TEST CONTRACT / TEST FIXTURE DEFECT`，不是生产语义放宽。

### Scanner NativeTests lifetime

旧 `RequireInspectedSession` 可从临时 `SessionScanResult` 返回内部引用，形成 UAF。`53d807e` 增加 deleted rvalue overload，并把 21 个调用点改为具名 `SessionScanResult` 生命周期。生产 `SessionInspection` 没有为此修改。该问题属于 `TEST FIXTURE DEFECT`，不是 Scanner 生产语义缺陷。

## 17. 已知限制

- 当前 OutputRoot 仍是固定产品契约。
- sessions-only scanner 无法发现没有 Session 目录的孤立媒体。
- legacy/no-identity Session 只能 Retain。
- `IncompleteNoMedia` 不构成自动删除依据。
- 同步 Native scan 在进入调用后不可被 Managed CancellationToken 中断；关闭会等待有界扫描真实返回。
- Recovery UI 是功能语义闭环，不是正式视觉精修。
- 本阶段不验证真实 kill、断电或损坏媒体的可恢复性。

## 18. P2.6D 依赖

P2.6D Actual Crash Recovery Technical Validation 至少需要分别制造并验证：Recording 期间真实 kill、Stopping 附近 kill、ReadyToPublish 窗口 kill、rename 后 metadata 前 kill、应用重启、Scanner 真实发现、用户允许/触发恢复、媒体内容检查，以及 no-loss / retain 行为。上述场景不得由本报告或纯 fixture 证据代替。
