# P2.6C-3a-3 Reconciliation Guard Foundations

## 1. 问题定义

P2.6C-2b 的 `SessionInspection` 只产生某一时刻的只读观察；P2.6C-3a-1、
3a-2 分别补齐持久文件身份和跨进程 Session owner 证据，但这些事实仍不能直接授权
以后修改 Manifest。Scan 与 Mutation 之间，revision、owner、路径命名空间、文件身份、
hard-link 数量和 WorkingPath 是否存在都可能变化。

本切片建立未来 Narrow Reconciliation 动手前的最后一层 operation-time evidence gate：

- Manifest expected-revision CAS；
- 复用 `session.owner.lock` 的 maintenance lease；
- operation-time 路径、文件身份和状态重验；
- 对 TOCTOU、reparse、object replacement 与 hard link 的保守防御。

本切片没有生产 reconciliation 调用链，不扫描后自动写回，不修改历史 Session，
也不移动、删除或改写媒体文件。

## 2. 为什么 ScanResult 不能授权 Mutation

Scanner 输出最多是 candidate hint：canonical SessionId、观察到的 revision 与分类。
它保存的 `PathSafetyResult`、owner probe、file identity 和 Working absence 都是旧观察，
不得作为操作授权复用。

正式不变量是：

**Scanner Classification != Mutation Authorization**

即使 Scanner 同时观察到 owner inactive、persistent identity match、final 存在且
working 不存在，也继续保持：

```text
deleteAllowed = false
reconciliationAuthorized = false
```

只有显式调用独立 `ReconciliationEvidenceGuard`，并在同一临界区重取全部当前事实，
才可能得到 `EvidenceComplete`。Scanner 自身没有该调用，也没有任何写入能力。

## 3. Lock Ordering

未来维护动作的统一获取顺序为：

```text
Session maintenance lease
  -> Manifest write transaction
  -> held MediaOutputRoot / operation-time filesystem evidence
  -> held final media handle
  -> final/Working revalidation
  -> expected-revision CAS
```

具体实现先以 `AcquireExisting` 持有 canonical Session 目录和
`session.owner.lock`，随后以 `BeginExpectedRevisionTransaction` 持有
`manifest.write.lock` 并在锁内加载 current Manifest，再持有 MediaOutputRoot 和 final
handle。CAS 或放弃后按反向安全边界释放：Manifest transaction、final handle、root
handle、maintenance lease。这里采用既定释放边界，不宣称它是获取顺序的机械逆序。

正常 Recording 路径继续使用既有 owner `Acquire` 和正常 `UpdateManifest`/
`SaveAtomic`；它没有被迫进入 recovery CAS，也没有新增反向锁序。

## 4. Maintenance Lease

`SessionLifetimeOwner::AcquireExisting` 复用与 Recording Owner 相同的
`session.owner.lock` rendezvous，不创建第二把 competing lock：

- maintenance 只使用 `OPEN_EXISTING` 和 share mode 0；
- owner evidence 缺失返回 `EvidenceMissing`，不创建文件；
- active Recording/另一 maintenance holder 通过 sharing conflict 返回
  `AlreadyOwned`；
- unsafe、inaccessible、I/O 或未知结果全部 fail closed；
- canonical Session 目录 handle 也持续持有，并禁止 delete sharing；
- acquire 成功后，owner 与 Session 目录 handle 由 RAII 一直持有到 CAS 完成或放弃。

因此 legacy/no-owner-evidence Session 只能 Retain。一次 probe 后立即 close 不构成
maintenance lease，也不得用于 mutation。

## 5. Expected-revision CAS

`SessionManifestStore::BeginExpectedRevisionTransaction` 与
`SessionManifestWriteTransaction::CompareExchange` 提供独立的内部 Native CAS 合同：

1. 以 share mode 0 打开并持有 `manifest.write.lock`；
2. 在锁内重新读取并严格解析 current `manifest.json`；
3. 验证 schema、Session identity、路径和跨字段语义；
4. 要求 `current.revision == expectedRevision`；
5. 调用 CAS 前再次在同一把锁内完整重读 current Manifest；
6. revision 不同返回 `RevisionMismatch`，同 revision 但完整内容变化返回
   `ConcurrentChange`；两者均不写磁盘；
7. 只有 current 与 expected facts 完全一致，才生成且仅生成
   `expectedRevision + 1`；
8. 复用正常 Manifest 写入的同一序列化、校验和原子发布核心。

CAS 没有复制 serializer、validator 或另一套 JSON writer。正常 Recording lifecycle
仍使用原 API；专用 transaction 只为显式维护临界区服务。

## 6. Operation-time Manifest Reload

Guard 不信任 Scanner 保存的 Manifest。取得 maintenance lease 后，它在 held
`manifest.write.lock` 内重新 Parse/Validate，并重新确认：

- schema 2 与 canonical Session identity；
- current revision 精确等于 expected revision；
- current lifecycle eligibility；
- WorkingPath 与 PlannedFinalPath；
- persisted pre-publish Working identity 存在且可解析。

进入 `CompareExchange` 时，transaction 仍会在原 lock 内再次完整读取 Manifest，比较
revision 和完整序列化事实。Parser failure、unsupported schema、semantic invalid、
Session mismatch、I/O failure、revision mismatch 和 atomic replace failure 均保留旧
Manifest 为 authoritative，不产生半份 JSON，不降低 revision，也不覆盖更新事实。

## 7. Final Held-handle Identity Guard

Guard 从 current Manifest 取得 final candidate 后，重新验证 trusted root 与路径，再用：

```text
FILE_READ_ATTRIBUTES | FILE_READ_DATA
share mode = FILE_SHARE_READ
OPEN_EXISTING | FILE_FLAG_OPEN_REPARSE_POINT
```

打开 final。该 handle 不授予 `FILE_SHARE_WRITE` 或 `FILE_SHARE_DELETE`，在 Guard
lifetime 内阻止该 namespace entry 被 rename、delete 或 replace。

最终判断来自 held handle facts，而不是打开前字符串 probe：

- ordinary disk file，非 directory，非 reparse；
- handle-resolved final path 与 trusted root containment；
- nonzero file size；
- volume identity 与 `FILE_ID_128`；
- hard-link count；
- 与 Manifest 持久 pre-publish Working identity 精确相同。

缺 identity 返回 `IdentityMissing`；volume 或 file ID 不同返回
`IdentityMismatch`；final 缺失、不安全或不可访问均按结构化结果拒绝。

## 8. Working Absence Double-check

不存在的 leaf 无法像 final 一样持有 file object，因此本实现不宣称永久锁定
Working absence。Guard 采用两次 operation-time 检查：

1. maintenance lease、Manifest transaction 和 MediaOutputRoot handle 均已持有后，
   第一次检查 WorkingPath；
2. final handle 与身份事实仍持有、紧邻 CAS 之前，再次检查 WorkingPath。

仅 `CreateFileW(OPEN_EXISTING)` 返回精确 `ERROR_FILE_NOT_FOUND` 才算 Absent。
Working 存在返回 `WorkingStillPresent`；sharing、ACL、parent missing、I/O、reparse 或
其他不能证明的结果返回 `WorkingAbsenceUnproven`/安全错误。第二次结果变化立即放弃
CAS，不创建占位文件，也不修改媒体目录来“锁住不存在”。

## 9. Reparse / Namespace 防御

operation-time Guard 重新验证 Shared OutputRoot、canonical Session 目录、Manifest
路径和 final candidate，不复用旧 Scanner PathSafety snapshot。maintenance lease 持有
Session 目录，Guard 另持有 MediaOutputRoot 与 final handle；root/intermediate/leaf 任一
reparse、root escape、类型错配或无法证明的访问结果都 fail closed。

`session.owner.lock` 与 `manifest.write.lock` 自身也使用
`FILE_FLAG_OPEN_REPARSE_POINT` 并在 handle 上拒绝 directory/reparse leaf。Guard 不智能
跟随 junction/symlink，不把字符串 `starts_with` 当成 containment 证明。

## 10. Hard-link 策略

强 file identity match 仍不足以处理多个 namespace alias。若 held final handle 报告
`hardLinkCount > 1`，Guard 返回 `HardLinkAmbiguous`，不得得到
`EvidenceComplete`，也不得自动修改历史状态。

**Persistent File Identity != Reconciliation Authorization**

hard-link 场景默认 Retain。该策略不否定 identity 事实，只承认它不足以形成安全 mutation
gate。

## 11. TOCTOU 边界

本实现尽可能以 held kernel objects 稳定关键事实：maintenance lease 排除本程序的
Recording/第二 maintenance owner，Manifest transaction 排除并发 Manifest writer，
root/final handles 稳定已打开对象及 namespace，CAS 前重读 Manifest 并第二次检查
Working absence。

但 Windows 没有把 Manifest CAS、final namespace 和“不存在的 Working leaf”合成一个
全局 filesystem transaction。外部恶意或手工文件系统操作仍不能被绝对消除。本阶段的
边界是 double operation-time revalidation + fail closed；任何变化、不确定或访问失败
都放弃，不尝试猜测或补偿。

## 12. Structured Guard Result 模型

独立 `ReconciliationEvidenceGuardStatus` 不用 bool 压缩失败原因，包含：

- `EvidenceComplete`
- `ActiveOwner`
- `OwnerEvidenceMissing`
- `RevisionMismatch`
- `ManifestNotEligible`
- `ManifestUnsupported`
- `PathUnsafe`
- `PathInaccessible`
- `WorkingStillPresent`
- `WorkingAbsenceUnproven`
- `FinalMissing`
- `FinalUnsafe`
- `IdentityMissing`
- `IdentityMismatch`
- `HardLinkAmbiguous`
- `ConcurrentChange`
- `IoFailure`
- `Unknown`

结果同时携带 HRESULT、expected/observed revision 和 held final identity。commit 结果另
保存是否真正提交及底层 CAS 结果。

最重要的语义是：

**EvidenceComplete != Reconciled**

`EvidenceComplete` 只表示在当前仍持有的临界区中，证据足以允许后续窄范围 metadata
CAS 尝试；它不代表状态已经推进、用户视频已恢复、媒体已修改或 P2.6C-3b 已实现。

## 13. CAS 定向测试

`--p2.6c3a3-reconciliation-guard` 的 CAS fixture 矩阵必须覆盖：

1. expected revision 一致时 CAS 成功；
2. 成功只增加一个 revision；
3. stale expected revision 拒绝；
4. 拒绝后 Manifest bytes/hash/revision 不变；
5. 两个并发 writer 只有一个相同 expected-revision CAS 成功；
6. SessionId mismatch 拒绝；
7. unsupported schema 拒绝；
8. malformed Manifest 拒绝；
9. atomic replacement failure 保留旧 Manifest；
10. CAS 不能让 revision 倒退。

这些 CAS 只作用于 NativeTests 自建 fixture；没有生产 startup、Scanner 或历史 Session
调用。

## 14. Operation-time Evidence 测试

同一定向入口覆盖 maintenance 与 operation-time facts：

- inactive existing owner evidence 可取得 maintenance lease；active owner、evidence
  missing、unsafe/inaccessible/I/O 均拒绝且 missing 不创建 owner leaf；
- lease 持有时第二 owner/recovery 无法取得，RAII 结束后可再次取得；
- 合法 ReadyToPublish crash-window fixture 在 persisted identity、working absent、final
  同 identity、linkCount=1 时先得到 `EvidenceComplete`，随后仅在 NativeTests fixture
  内执行一次完整 Guard CAS，确认 revision 精确增加 1 且 Published facts 原子落盘；
- stale revision、final replacement/missing、Working present/inaccessible、root escape、
  intermediate/leaf reparse、directory leaf、identity missing/mismatch 与 volume mismatch
  均产生保守结构化结果；
- Scanner 结果继续保持 `deleteAllowed=false` 和
  `reconciliationAuthorized=false`。

最终执行结果必须由实际测试进程报告；不得用设计矩阵本身冒充 PASS。

## 15. 真实 TOCTOU 测试

Windows fixture 需要证明三类真实竞态：

1. Guard 由主测试线程持续持有 final handle 时，独立工作线程的 rename/replace 因没有
   `FILE_SHARE_DELETE` 而失败；Guard 释放后 fixture 可正常清理；
2. 第一次 Working absence 后、CAS 前人为创建 WorkingPath，第二次检查使 CAS 放弃，
   Manifest 不变；
3. Scanner 之后 owner 变 Active 或 Manifest revision 改变时，operation-time lease/CAS
   分别返回 ActiveOwner/RevisionMismatch。

真实 hard link fixture 还必须证明：identity 可以相同但 linkCount > 1，最终仍为
`HardLinkAmbiguous` 而非 `EvidenceComplete`。所有 seam 仅服务 NativeTests，不暴露公共
产品 ABI，也不默认进入正式运行路径。

## 17. 已知限制

- Guard 只建立 operation-time evidence，不定义或执行生产 reconciliation policy；
- Working absence 无可持有 leaf，仍依赖第二次检查与 fail closed；
- 没有跨多个 NTFS 对象和 Manifest 的全局事务，无法承诺抵御任意恶意外部篡改；
- legacy schema 1、no identity、owner evidence missing、hard-link、reparse、inaccessible、
  unknown 与 I/O failure 全部 Retain；
- 不执行媒体解析、修复、republish、delete、cleanup 或恢复；
- 没有 Recovery UI、Managed startup reconciliation、P2.6D，也未改 Scanner 授权；
- P2.6B 远程同步状态保持 `REMOTE-SYNC-PENDING`，本阶段不访问 GitHub。

## 18. P2.6C-3b 可用的最小接口

3b 最多可复用以下内部 Native 表面：

1. Scanner 只提供 canonical SessionId、expected revision 与候选提示；
2. 显式调用 `ReconciliationEvidenceGuard::Acquire(roots, sessionId,
   expectedRevision, guard)`；
3. 只有返回 `EvidenceComplete` 且 `guard.EvidenceHeld()` 为 true，才可读取
   `CurrentManifest()` 与 `FinalIdentity()`；
4. 3b 自己必须定义**比 Guard 更窄**的允许状态/字段转换和不可变字段白名单；Guard
   结果不能替代 reconciliation policy；
5. 基于 held current Manifest 构造单次 metadata candidate，再调用
   `guard.CompareExchange(candidate)`；
6. CompareExchange 紧邻提交前重验 final/linkCount/Working absence，并由 Manifest
   transaction 再次重读 current facts；任一变化即不提交；
7. 成功或失败后 RAII 释放所有 handles/locks，不循环猜测、不自动重试陈旧 candidate。

3b 不得把 `ReconciliationEvidenceGuard` 接到 Scanner 内部，不得让
`EvidenceComplete` 自动推进状态，也不得处理 working 恢复、媒体 move/delete/replace。
本阶段只交付证据与 CAS primitives；生产 reconciliation 调用链仍不存在。

阶段完成判定必须同时满足实际定向矩阵、回归、clean build 和 diff check。只有这些证据
全部成立，结论才可记为：`P2.6C-3A3-RECONCILIATION-GUARD-READY`。
