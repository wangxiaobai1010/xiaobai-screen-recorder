# P2.6C-3a-1 Persistent Media File Identity Evidence

## 1. 问题定义

P2.6A 能证明某个路径当前存在文件，却不能仅凭路径、文件名、大小、时间戳或
SessionId 证明该文件就是本 Session 的 working 文件经 same-volume durable rename 后的
同一底层文件对象。P2.6C-2b 因而正确地把 `ReadyToPublish + final exists + working
absent` 保留为 `PublishOutcomeUnprovenRetain`。

本切片只建立未来 reconciliation 所需的持久文件身份证据，不执行 reconciliation，
不授权 mutation，也不改变 P2.6A 的 publish、Published 或 Completed 语义。

## 2. Windows 强身份模型

新增内部 `PersistentFileIdentity` primitive。它对真实文件 handle 调用
`GetFileInformationByHandleEx(FileIdInfo)`，使用 `FILE_ID_INFO` 的：

- 64-bit `VolumeSerialNumber`；
- 128-bit `FILE_ID_128`。

强身份比较只比较上述两项。`fileSizeBytes` 与 `hardLinkCount` 同时从 handle 读取，但
只用于诊断，不是 ownership proof。`SessionPathSafety` 复用同一 primitive，不再保留
第二套 64-bit file-index 身份实现。

## 3. Canonical persistence 格式

- volume identity：16 个 uppercase hexadecimal 字符；
- file ID：按 `FILE_ID_128.Identifier[16]` 原始字节顺序编码为 32 个 uppercase
  hexadecimal 字符；
- Writer 只写固定宽度 canonical 文本；
- Reader 严格拒绝错误长度、小写或非 hex 字符，禁止截断和宽松猜测。

JSON 不使用可能受跨语言整数精度影响的 64-bit number 保存 volume identity。

## 4. Manifest schema 决策

原 schema 1 使用严格、精确的 22 字段合同，不存在可直接追加 optional 字段的既有
策略。因此 Writer 明确升级到 schema 2，而不是静默改变 schema 1。

schema 2 新增两个严格对象：

- `workingFileIdentity`：`attempted`、`captured`、`volumeIdentity`、`fileId`、
  `hresult`；
- `postPublishIdentityVerification`：`attempted`、`matched`、`hresult`。

Reader 同时严格支持 schema 1 和 schema 2。schema 1 缺少 identity 时解析为
Unavailable，而不是 Corrupt；schema 3 及未来版本仍返回 `UnsupportedSchema`。schema 2
字段缺失、类型不符、canonical identity 不合法或跨字段事实矛盾均返回
`SemanticInvalid`。

## 5. Capture 时机与生命周期

正式链路为：

```text
Finalize
  -> Validation
  -> recording resources released
  -> worker exited
  -> StopAndJoin completed
  -> validate nonempty WorkingPath
  -> capture Working FILE_ID_INFO
  -> persist ReadyToPublish + workingFileIdentity
  -> MoveFileExW(..., MOVEFILE_WRITE_THROUGH)
  -> capture PublishedPath FILE_ID_INFO
  -> compare with pre-publish identity
  -> persist Published / Completed + verification facts
```

健康路径中，working identity 随 `ReadyToPublish` revision 在 rename 前原子保存。没有
新增每帧或每秒写入。

## 6. Crash window 证明

复用既有 post-publish fault seam：先成功持久化 Ready revision 和 working identity，
随后执行真实 `MoveFileExW`，再模拟 Published metadata 尚未写入。测试证明：

- WorkingPath 已不存在；
- PlannedFinalPath 存在；
- Manifest 仍为 ReadyToPublish revision；
- Manifest 保留 rename 前的 volume/file ID；
- final handle 的当前 identity 与持久 identity 相同；
- Snapshot 的 durable publish/Completed 文件事实仍成立。

这只证明未来可以形成强 evidence，不在本轮推进 Manifest 状态。

## 7. Identity capture failure 策略

身份是 reconciliation evidence，不是用户录像成功发布的前置条件。working identity
capture 失败时，Manifest 尽力记录 `attempted=true`、`captured=false` 和真实 HRESULT；
Finalize、Validation、P2.6A publish 与 Completed 继续。Manifest 本身写入失败也继续沿用
P2.6B media-first 策略，不阻断或删除用户媒体。

缺失 identity 的 Session 未来只能 Retain。

## 8. Rename 后验证

durable rename 成功后重新打开 PublishedPath 并读取 current identity：

- 两项强身份一致：`attempted=true, matched=true, hresult=S_OK`；
- 无法打开或注入失败：`attempted=true, matched=false`，保留真实 HRESULT；
- 两个 identity 均可读但不一致：HRESULT 仍表示读取成功，`matched=false` 表示 mismatch。

验证失败或 mismatch 不否认已成功的 `MoveFileExW`，不清空 PublishedPath、不删除 final、
不把成功录像改成失败。

## 9. Final conflict

预先存在的 final B 保持 P2.6A no-replace 规则。测试证明 working A 与 final B 是不同
underlying objects，publish 失败后 A 保留、B 不覆盖，且 post-publish verification 未被
伪造为 attempted/matched。

## 10. Hard-link 边界

真实 hard link 测试证明两个路径可共享同一 volume/file ID，link count 至少为 2。该
结果是身份事实，不是删除、覆盖、rename 或其他 mutation 的授权。

**Persistent File Identity != Reconciliation Authorization**

**Persistent File Identity != SafeForMutation**

## 11. Legacy / no-identity 行为

受控 schema 1 fixture 可正常读取，identity 映射为 Unavailable。Read-only Scanner 保持
原分类和 `reconciliationAuthorized=false`；旧 Session 不会因缺少 schema 2 字段被判为
ManifestCorrupt，也不会自动推进 Published/Completed。

## 12. Scanner 暴露的只读 evidence

`SessionInspectionResult` 增加：

- `persistentWorkingIdentityAvailable`；
- `persistentIdentityComparisonAttempted`；
- `strongIdentityMatch`。

Scanner 只比较持久 working identity 与当前 PlannedFinalPath 的 handle identity。所有
classification 仍强制 `deleteAllowed=false` 与 `reconciliationAuthorized=false`；即使
strong identity match，也只作为未来 reconciliation 输入。

## 15. 未实现内容与后续依赖

本切片未实现 cross-process lifetime owner、revision CAS、operation-time revalidation、
TOCTOU/reparse/hard-link mutation defense、自动 reconciliation、delete/cleanup、恢复、
Recovery UI、Native ABI/Managed API 扩展或 P2.6D。

P2.6C-3a 后续仍需分别建立 lifetime owner 与 CAS/revalidation/mutation safety foundations；
只有这些证据和授权边界全部成立后，P2.6C-3b 才能考虑窄范围 reconciliation。
