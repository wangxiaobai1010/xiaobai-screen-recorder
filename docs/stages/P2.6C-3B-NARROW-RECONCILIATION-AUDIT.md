# P2.6C-3b Narrow Reconciliation Mutation Contract 独立反证审查

## 1. 总体结论

审查对象是
`docs/stages/P2.6C-3B-NARROW-RECONCILIATION-CONTRACT.md`，审查基线为
`feature/p2.6c-narrow-reconciliation@eba90401d158d6c06ce3521a26f78209e8f4c0f0`。
本轮没有审查或授权生产 reconciliation 实现。

合同的主方向成立：它没有把当前文件身份事实伪造成历史 Native publish 事实；source 被限制为
严格 schema 2 `ReadyToPublish`；target 使用独立 schema 3
`ReconciledCompleted`；旧 `publish.*`、`publishedPath` 和 post-publish facts 保持不变；
mutation 仅允许 Manifest metadata CAS；媒体必须零修改。

但是合同尚未达到代码实施门槛。独立反证发现四个必须先回写合同的 blocker：

1. `updatedAtUtc` 与 `reconciledAtUtc` 没有冻结唯一时间关系；
2. Result 模型没有区分合法状态但语义矛盾的 source facts；
3. `AlreadyReconciled`/并发 loser 的 operation-time 重读来源和 target 等价规则不完整；
4. schema 3 对旧消费者的启用顺序及必测负例没有成为硬门禁，现有 36 项矩阵仍缺明确用例。

因此本轮结论为 `P2.6C-3B-CONTRACT-AUDIT-BLOCKED`。这里的 BLOCKED 是成功的反证审查
结果，不表示需要在本轮修改合同或实现代码。

## 2. Blockers

### B1：两个 reconciliation 时间字段的关系未冻结

合同分别把 `updatedAtUtc` 和 `reconciledAtUtc` 描述为本次 operation time，但没有规定二者
必须相等，还是允许两个独立时钟采样。这样会产生两种都符合当前文字的实现：一次取时同时
写入，或连续取时产生微小差异。未来 strict schema 3 validator 与测试无法据此选择唯一规则。

合同必须改为：成功候选生成时只捕获一次 canonical UTC timestamp，同一个值同时写入
`updatedAtUtc` 和 `reconciliation.reconciledAtUtc`；validator 要求二者逐字符/规范化后相等，
且不早于 `createdAtUtc`。CAS 失败时该内存时间不得落盘，重试必须重新开始完整 Guard 流程，
不能复用旧时间候选。

### B2：Result 模型缺少语义冲突分类

`NotEligibleState` 只能表达 source state 不在白名单。一个 schema 2 Manifest 可以处于
`ReadyToPublish`，但仍包含互相矛盾的 error/publish/post-publish facts，或缺失 source
eligibility 的必需事实。把这些都压成 NotEligible 会掩盖“状态不适用”和“持久事实内部
矛盾”的差别。

合同必须增加 `InvalidSourceFacts` 或 `SemanticConflict`（选择一个稳定名称），并定义：

- state 不是唯一 source：`NotEligibleState`；
- schema/字段结构本身非法：现有 `SemanticInvalid`/`UnsupportedSchema` 路径；
- 结构合法但 source eligibility 内部事实冲突：`SemanticConflict`；
- operation-time 文件证据不足：`GuardRejected`/`EvidenceInsufficient`。

结果只用于诊断，所有上述非成功结果仍一律 no write/fail closed。

### B3：幂等识别与 concurrent loser 的事实来源不完整

合同规定严格有效的 schema 3 target 返回 `AlreadyReconciled`，但没有明确该判断必须来自
operation-time 严格重读，也没有定义并发 loser 所谓“相同 target”的语义相等规则。若实现
复用 Scanner 的旧 Manifest，或把自己尚未提交的 `reconciledAtUtc` 与 winner 时间比较，可能
误报、错误返回 `RevisionChanged`，或为“修正时间”再次推进 revision。

合同必须明确：

- `AlreadyReconciled` 不使用 Scanner snapshot、classification 或时间先后推断；
- 必须重新读取磁盘并通过完整 strict schema 3 validator；
- target 等价由 schema/state、`sourceRevision`、kind/evidenceKind、
  `originalPublishResultKnown=false`、`confirmedFinalPath` 及全部保留字段决定；
- winner 的 `reconciledAtUtc` 是唯一已提交时间，loser 不要求它等于自己的未提交候选时间；
- 严格有效且来源 revision/Session/path 相同才是 `AlreadyReconciled`，否则
  `RevisionChanged`/`SemanticConflict`，永不再次写入 `N+2`。

### B4：schema 3 消费者启用门槛和测试矩阵不完整

当前代码中 schema 2 `Completed/Published` 消费路径明确依赖 `publish.published=true`：

- `SessionManifest` validator 规定 Published/Completed 与 `publish.published` 等价；
- `SessionInspection::Classify` 的 Completed/Published 分支也检查
  `publish.published` 和 `publishedPath`；
- runtime `RecordingController`/LongRun 使用 Native Snapshot 的
  `Completed + Published + OutputSuccess + PublishedPath`，不是 Manifest reconciliation。

旧二进制会把 schema 3 当 UnsupportedSchema 并 Retain，这是安全行为；新 parser 若增加
schema 3，但消费者在同一版本没有显式处理 `ReconciledCompleted`，则只能 Retain，不能把它
送入普通 Completed/OutputSuccess 路径。合同虽然陈述了语义区别与 P2.6C-4 依赖，但尚未把
“写出 schema 3 前完成所有读取方审计、未知读取方 fail-closed、不得暴露给旧 UI”的顺序和
负向测试列为硬门禁。

合同必须增加 activation gate：3b 可以写入 schema 3 前，strict parser、validator、
read-only inspection/idempotency reader 必须在同一发布单元内安全识别；任何未升级的消费
路径只能 Unsupported/Unknown Retain。Managed/UI 直到 P2.6C-4 提供专门语义前不得接收
`ReconciledCompleted` 作为 Native Completed 或 OutputSuccess。

同时，现有测试矩阵的笼统“交叉不一致”不足以替代任务要求的逐个反例；详见第 16 节。

## 3. Schema 3 语义审查

`ReconciledCompleted` 可以表达所需区别，前提是它保持一个独立持久枚举值，绝不别名到
`Completed`。其唯一含义应为：source Manifest 已持久记录 Finalize/Validation/资源释放成功，
operation-time Guard 又证明同一个 persistent media object 当前位于 PlannedFinalPath。

它不表示：

- 产品曾调用或成功返回 `MoveFileExW`；
- 原 publish HRESULT 为 `S_OK`；
- Native runtime Completed/OutputSuccess；
- 当前重新执行了 SourceReader Validation；
- 文件内容在历史 Validation 后从未被外部修改。

状态名称本身存在“Completed-like”误读风险，但合同可以通过独立 enum、严格交叉 validator
和消费者 activation gate 安全表达，无需改成伪造的普通 Completed。

`reconciled=true` 与 `state=ReconciledCompleted` 是重复事实。schema 3 validator 必须把它们
定义为严格双向不变量，而不是分别验证：第一版 schema 3 只允许二者同时成立，缺失、false、
其他 state 或其他 provenance 组合全部 `SemanticInvalid`/Retain。

## 4. Source eligibility 审查

仅检查 `state=ReadyToPublish` 当然过宽；合同第 3 节给出的完整谓词已经补足关键条件，包括
媒体提交、worker 退出、资源释放、Finalize、Validation、持久 Working identity、未记录
publish、空 PublishedPath、未尝试 post-publish verification、无 error 以及 Guard 的当前
文件事实。

实施时还必须保持以下 fail-closed 解释：

- schema 2 是严格 exact-shape；出现 reconciliation 字段不是“已存在 provenance”，而是非法
  schema 2；
- 任何已知 publish failure（attempted/HRESULT）、非空 PublishedPath 或矛盾 post-publish
  facts 均拒绝；
- Working identity 的 canonical volume/file ID 只来自持久 source，不能从当前 final 反向
  补写 source；
- PlannedFinalPath 必须同时通过 schema semantic validation 和 3a-3 operation-time held-handle
  路径/身份校验；
- Source eligibility 必须读取 `guard.CurrentManifest()`，不读取 Scanner 缓存。

在这些条件下，唯一 source 足够窄，不需要增加第二个 source state。`Published -> Completed`
仍应留给独立合同。

## 5. Target semantic state 审查

唯一合法变化是 schema 2 `ReadyToPublish@N` 到 schema 3
`ReconciledCompleted@(N+1)`。目标表示 historical recovery terminal semantic state，
不属于原 Native Completed/OutputSuccess。

目标需要 strict validator 明确以下整体不变量：

- state 与 `reconciliation.reconciled=true` 双向一致；
- `sourceRevision == revision - 1`，且等于 CAS 前 revision；
- `confirmedFinalPath == plannedFinalPath`；
- `originalPublishResultKnown` 在 v1 恒为 false；
- publish/post-publish/publishedPath 保持 source 的 unknown/unattempted/empty；
- 只允许合同列出的 kind/evidenceKind；
- 时间满足 B1 的单次捕获规则。

除 B1 外，现有 target 字段足以表达区别，不需要增加普通 Completed bool。

## 6. Historical truth 边界

合同正确区分了两类事实：

- 历史持久事实：source revision 最后记录时 publish 未持久化；
- 当前证据：同一个 volume/file ID 的对象现在位于计划 final 路径，Working 当前严格 Absent。

用户手工 same-volume move 与产品在崩溃窗口内完成 namespace move，会产生相同的当前证据。
合同不尝试识别操作者，因此没有伪造历史。

`kind=FinalAtPlannedPathSamePersistentFileV1` 与
`evidenceKind=MaintenanceLeaseCasHeldFinalIdentityV1` 的命名指向当前文件身份，未暗示 Native
publish。两者必须作为封闭 enum 处理，未知值不能降级为普通字符串显示后继续信任。

## 7. Publish 字段审查

保持以下 source 值是唯一不伪造历史的选择：

```text
publish.attempted=false
publish.published=false
publish.hresult=null
publishedPath=""
postPublishIdentityVerification=未尝试/未匹配/null
```

schema 3 validator 必须为 `ReconciledCompleted` 增加独立分支，不能复用 schema 2 中
“Completed iff published”的不变量。也不能为了让旧 UI 打开文件而填充 `publishedPath`。
reconciled current path 只能从 provenance `confirmedFinalPath` 读取。

`originalPublishResultKnown=false` 只有在消费者先按 schema/state/provenance 分支时才足以防止
误读；它不能单独保护一个先看 `Completed-like state` 的旧消费者。这也是 B4 必须成为启用
门槛的原因。

## 8. Immutable whitelist 审查

白名单没有遗漏业务上必须修改的字段。合法 candidate 只需改变：schema、revision、
updatedAtUtc、state 和新增 reconciliation object。

以下必须 semantic-equal，合同已覆盖：SessionId、writer strategy、createdAtUtc、三路径、媒体
提交事实、worker/resource facts、Finalize、Validation、publish、持久 Working identity、
post-publish verification 和全部 error facts。

验证必须比较反序列化后的 typed facts，不能比较 JSON bytes、字段顺序、缩进或 escape 写法。
不过原子失败测试仍应额外比较旧磁盘 bytes 未被半写，这与 semantic whitelist 是两个不同
断言。

专用 schema migration validator 是必要的；现有通用 `ValidateUpdate` 禁止 schema 变化且只
验证部分单调事实，不能作为 3b 白名单授权。

## 9. Error 事实审查

第一版 source eligibility 已明确要求：

```text
errorCategory=None
errorCode=null
errorMessage=""
```

所以第一版没有任何非空 error 组合仍可进入 `ReconciledCompleted`，包括
ManifestPersistence diagnostic。这个选择比“保留但继续推进”更保守，也避免把 Finalize error
与成功 Finalize facts 一起带入 target。

结构合法但 error facts 与 Ready facts 冲突时必须返回 B2 所述 `SemanticConflict`，不得仅因
state 正确而忽略，也不得清空错误后继续。合同中“未来若扩大 source 则保留历史 error”只是
后续约束，不授权第一版接受任何错误。

## 10. Idempotency

第一次成功只能使 revision `N -> N+1`。第二次调用不得进入 Guard mutation path，也不得更新
时间。严格有效 schema 3 结果只能 no-op。

但必须先按 B3 补充 operation-time strict reload 和 target semantic equivalence。不得用
`reconciledAtUtc` 大小判断是否已经处理；不得把一个 malformed schema 3 当
AlreadyReconciled；不得为“补全”或“规范化”合法 winner 结果写入 N+2。

## 11. Concurrent CAS

3a-3 的 maintenance lease、`manifest.write.lock`、锁内 current 重读、expected revision 和
atomic replace 足以成为 single-winner 基础。两个基于 N 的 caller 只能一个提交。

loser 在 revision mismatch 后只能：

1. 释放/结束原 mutation attempt；
2. operation-time 只读重载；
3. 若严格 valid schema 3 与相同 source/Session target 等价，返回 AlreadyReconciled；
4. 否则返回 RevisionChanged/SemanticConflict。

它不能基于自己的不同 timestamp 再取 Guard 并重写 winner。

## 12. Guard 职责边界

合同正确要求四层同时存在：

1. Guard：owner、path、held handle、identity、link count、Working absence、TOCTOU；
2. Source Eligibility：业务 source facts；
3. Immutable Whitelist：唯一 candidate；
4. CAS：revision 和原子持久化。

Guard 当前只接受 schema 2 Ready source并证明文件事实；它不判断 Finalize/error/publish 等完整
3b 业务 eligibility，也不选择 target。Scanner classification 永久不授权 mutation。

Narrow Reconciler 只能显式调用 Guard，再以 `guard.CurrentManifest()` 评估 source；任何把
Scanner result 直接交给 CAS 的实现都违反合同。

## 13. Media zero-mutation

合同对此足够明确：3b 只能 CAS Manifest metadata，不能调用 rename、Move、copy、delete、
truncate、write、timestamp touch、repair、republish 或 cleanup。

final handle 只能请求读/属性证据权限，并拒绝 write/delete sharing。成功、失败和 Already
路径都不得触碰媒体。before/after bytes/hash、size、persistent identity 和 timestamps 均应
保持；Working 继续 Absent，不能创建 placeholder。

用户手工 move、rename 或 replacement 的操作者身份不参与授权。只有 Guard 当前文件事实满足
严格语义才允许 metadata reconciliation；hard-link/reparse/identity mismatch 一律 Retain。

## 14. Old consumer 兼容风险

当前 runtime Snapshot 消费者不是 Manifest reconciliation consumer：Native Completed 和
OutputSuccess 仍只来自正常 recording publish。它们不能因新增 schema 3 改变。

当前 read-only `SessionInspection` 对普通 Completed/Published 明确要求
`publish.published=true`；新增 `ReconciledCompleted` 后必须使用独立 case，或在 P2.6C-4 前
保持 Unknown/Retain。绝不能 fall through 到普通 Completed，也不能以空 `publishedPath` 形成
普通 OutputSuccess。

schema 3 的可用视频位置是 `reconciliation.confirmedFinalPath`。未来 Managed/UI 若要展示，
属于 P2.6C-4，必须展示“reconciled current final”而不是“已证实原 Native publish”。3b 在此
之前不得把 target 暴露给现有 RecordingController/MainForm 成功路径。

这些要求需按 B4 写入合同 activation gate；否则“同一提交中先写 schema 3、稍后再更新
consumer”的中间版本存在误读或不可发现窗口。

## 15. Schema 1/2/3 兼容

- schema 1：legacy/no persistent identity，继续 Retain，不能 migration；
- schema 2：正常 recording writer 的唯一 schema；正常 P2.6A/B 状态机和字段语义不变；
- schema 3：只允许严格 `ReconciledCompleted + reconciliation` 组合，正常 writer 不产生；
- future schema：UnsupportedSchema/Retain。

schema 3 不能仅因存在 reconciliation object 就被信任。缺字段、额外非法组合、未知 enum、
state/provenance 不一致、publish true、非空 PublishedPath、错误 sourceRevision/path/timestamp
都必须 SemanticInvalid/Retain。

旧 schema 2 parser 对 schema 3 的 UnsupportedSchema/Retain 是安全兼容策略。升级后的 parser
也必须保持 schema 1/2 exact validator，不能为支持 schema 3 放宽旧结构。

## 16. 测试矩阵补充

现有 36 项覆盖了主 happy path、Guard、CAS、媒体零修改、schema 迁移和若干 provenance 负例，
但实施前必须把以下项目变成独立、可定位的测试，而不是依赖第 35 项笼统描述：

1. `ReconciledCompleted + reconciliation.reconciled=false/缺失` 拒绝；
2. 非 ReconciledCompleted state 携带 reconciliation object 拒绝；
3. `ReconciledCompleted + publish.published=true` 拒绝；
4. `ReconciledCompleted + publishedPath非空` 拒绝；
5. `originalPublishResultKnown=true` 且无可证明历史 publish facts 拒绝；
6. `sourceRevision != target.revision-1/CAS前revision` 拒绝；
7. `confirmedFinalPath != plannedFinalPath/held candidate` 拒绝；
8. Finalize/Validation/Publish/errorCategory 互相冲突返回 SemanticConflict 且 no write；
9. 单次 timestamp capture：两个字段相等，CAS loser 不用自己的 timestamp 重写 winner；
10. 每个 immutable 字段逐项篡改均 no write；
11. 第二次调用从 operation-time strict schema 3 重读得到 AlreadyReconciled，revision 不变；
12. concurrent loser 对 winner 的不同时间仍判 target 等价，不推进 N+2；
13. schema 2 Native Completed/OutputSuccess 与 LongRun 语义完全不变；
14. 旧/未升级 consumer 对 schema 3 只能 Unsupported/Unknown Retain；升级后的 inspection 不把
    ReconciledCompleted 归入 Native Completed/OutputSuccess；
15. schema 3 CAS/Flush/verify/Replace 任一点失败，磁盘仍是完整 schema 2 revision N；
16. success/failure/no-op 全路径媒体 bytes/hash/identity/size/timestamps 不变。

其中第 3、4、8、9、14 项在当前施工图中没有独立明确断言；第 5、6、7 虽被第 33 项概括，
仍应保留独立用例以定位具体 validator 缺口。

## 17. 实施前必须修改合同的项目

在开始任何 P2.6C-3b 代码前，必须修订 CONTRACT（不是本轮修订）：

1. 冻结单次 UTC capture，并要求 `updatedAtUtc == reconciledAtUtc`；
2. Result 模型增加 `SemanticConflict/InvalidSourceFacts`，定义与 NotEligible/GuardRejected 的
   边界；
3. 定义 AlreadyReconciled 的 operation-time strict reread、semantic target equivalence 和
   concurrent loser 规则；
4. 增加 schema 3 consumer activation gate：未升级读取方只能 Retain，P2.6C-4 前不进入旧
   Managed/UI/OutputSuccess 路径；
5. 将第 16 节负例逐项纳入实施测试矩阵，尤其是 published/path、error、timestamp 和 old
   consumer 四组。

修订后应重新进行一次合同 closure；在此之前不能以当前 `CONTRACT-READY` 开始生产实现。

## 18. 不构成 blocker 的审查结论

- 不需要在 provenance 再复制一份 confirmed file identity；持久 Working identity 加 Guard
  当前等同性和 sourceRevision 已足够，复制会制造第二份身份真相；
- `publishedPath` 保持为空是正确选择；current final path 由 provenance 表达；
- 第一版完全拒绝任何 error facts 是保守且安全的；
- 不处理 `Published -> Completed` 是合理范围控制；
- 用户手工 same-volume move 仍可成立，但只证明 current same-object path fact；
- 3a-3 CAS/Guard 是足够的机制基础，缺口在 3b 合同语义和启用门槛，不在媒体操作；
- schema 2 正常 writer、Native ABI、Snapshot、RecordingController、LongRun 均不应修改。

## 19. 范围与 Git 结论

本轮只新增本审查报告。没有修改 CONTRACT、PLAN、源码、测试、ABI、Scanner 或 Guard；没有
实现 Narrow Reconciler、Managed startup、Recovery UI 或 P2.6D；没有执行网络或 Git 历史
操作。

最终合同审查状态：`P2.6C-3B-CONTRACT-AUDIT-BLOCKED`。
