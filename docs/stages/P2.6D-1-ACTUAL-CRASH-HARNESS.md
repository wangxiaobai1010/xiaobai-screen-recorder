# P2.6D-1 Actual Crash Validation Harness Foundations

Date: 2026-08-08

Baseline: `f30d1ed95b465387c5ae61874927386662d4a8c0`

Branch: `feature/p2.6d-crash-validation-harness`

## 1. Stage goal

P2.6D-1 establishes a deterministic, isolated, cross-process harness for an
actual Windows process termination. This slice runs one `RecordingActive`
smoke crash and proves that a fresh process can discover and retain the
persistent accident scene. It does not attempt media repair or the full crash
window matrix.

## 2. Actual kill versus failure injection

Failure injection, exceptions, and graceful process exit execute C++ stack
unwinding and may invoke Stop, Finalize, owner release, and cleanup. They do
not model a process crash. The D1 parent instead calls `TerminateProcess` on
the exact child process handle returned by `CreateProcessW`. The child is
blocked at a parent-controlled checkpoint and never executes Stop, Close,
Finalize cleanup, `exit`, or its normal return path.

## 3. Parent, child, and restart-inspector architecture

- The parent owns the isolated fixture, named synchronization events, the
  exact child/inspector process handles, evidence verification, kill, and
  final cleanup.
- `--p2.6d-crash-child` creates a real recording Session and waits at a
  `RecordingActive` barrier.
- `--p2.6d-restart-inspector` is a second, newly created process. It reloads
  the current Native binary and invokes the production read-only
  `ScanHistoricalRecordingSessions` path from disk facts.
- Evidence is exchanged through fixed, versioned, test-internal binary DTOs.
  Checkpoint synchronization never depends on stdout flushing.

## 4. Safe-kill contract

The harness starts each helper suspended, does not inherit handles, records
its PID and process handle, validates the helper PID and full executable path,
then resumes it. Before termination it revalidates that the owned handle is
alive and still identifies the current NativeTests executable. It never finds
or terminates processes by name. RAII fallback termination is limited to the
same verified process handle created by this parent.

The forced exit code is `0xD1260001`. The parent waits for the process handle
to become signaled and requires that exact code; the child normal-return code
and harness cleanup code are rejected.

## 5. Isolated fixture root

Each run uses the unique, Git-ignored directory:

`<repo>/artifacts/xbpreview-p2.6d-crash-<canonical-session-id>`

The fixture must be an immediate, non-reparse child of the repository
`artifacts` root and its leaf must exactly bind the run nonce. Media lives in
the fixture-local `recordings` directory; it never uses the product
`p2.5a-recordings` directory or a user's recording directory. Successful runs
remove only their verified owned fixture after all evidence is captured.
Failed fixtures are retained for diagnosis.

The initial `%TEMP%` prototype was rejected by the production handle-based
Path Safety layer in this Windows environment because the
`C:\Users\Administrator` ancestor returned `E_ACCESSDENIED`. The harness did
not weaken that safety rule; it moved to the already ignored repository
artifact root, which is also the trusted pattern used by the frozen owner
integration tests.

## 6. Real recording path

The child uses the real `RenderFrameTap`, `VideoEncoderConsumer`,
`SessionManifestStore`, Session lifetime-owner lease, Media Foundation H.264
SinkWriter, and P2.6A Safe Publish configuration. A protected D3D11 device and
deterministic 640x360 synthetic frames avoid WGC service dependencies while
retaining the real encoder and persistence path.

## 7. Test-only checkpoint seam

No public ABI, Host code, or product recording behavior was changed. The
RecordingActive checkpoint needs no new production hook: the dedicated child
polls durable Manifest/file facts after successful frame submission and then
signals the parent. Existing `XBPREVIEW_NATIVE_TESTS` lifecycle hooks remain
available for later D2 stop/publish windows, but D1 does not expose them through
the product ABI or an environment variable.

## 8. IPC and barrier design

Every run derives unique manual-reset event names from its canonical GUID:
`ChildReady`, `CheckpointReached`, `ChildContinue`, `InspectorReady`, and
`InspectorContinue`. Events are opened explicitly by the helper; no inherited
handle is trusted. Startup, checkpoint, forced-exit, restart-inspection, and
normal inspector exit all have bounded waits. An early helper exit fails the
gate.

## 9. Future crash checkpoints

The helper mode and event architecture can be extended to:

1. `RecordingActive`;
2. `StoppingBeforeFinalize`;
3. `ReadyToPublishBeforeRename`;
4. `AfterRenameBeforePublishedMetadata`.

Only the first checkpoint is executed in D1. The remaining three require a
separate P2.6D-2 matrix and must reuse internal-only lifecycle barriers.

## 10. RecordingActive smoke definition

The child signals `CheckpointReached` only after all of these facts hold:

- Manifest state is `Recording`;
- `writeSampleAttempted=true` and `frameSubmitted=true` are durable;
- the real `.partial.mp4` exists and is nonempty;
- the lifetime-owner lease is observable as Active from the parent process.

FrameTap generation priming uses a bounded 64-attempt/250-ms contract, not the
obsolete single-call timing assumption.

## 11. Pre-kill scene

Before termination the parent loads the Manifest from disk, proves the above
recording facts, reads a nonzero working size, rejects fabricated publish/file
identity facts, and verifies the actual child EXE and loaded
`XbPreview.Native.dll`. It captures Manifest bytes and the working file's
SHA-256, persistent FILE_ID, size, and timestamps before any restart scan.

## 12. First scene after kill

After `TerminateProcess` and the signaled process exit, the parent performs no
recovery, reconciliation, Manifest update, owner-file deletion, media move, or
cleanup. It freezes the first scene: Manifest bytes/revision/state, working
file observation, final-file absence, and persistent owner rendezvous file.

## 13. Owner release

The fresh inspector must report
`SessionLifetimeOwnerProbeState::InactiveLeaseReleased`. This demonstrates
that Windows released the child's exclusive kernel handle while the persistent
`session.owner.lock` rendezvous file remained. Child death alone is not used as
an owner-state inference.

## 14. Fresh-process restart inspection

The restart inspector is a new PID with its own process state. It reloads the
same current executable and Native DLL, invokes the production Scanner, and
writes a structured observation for the run Session. The parent does not call
the Scanner in-process and label it a restart.

## 15. Classification result

The expected and observed D1 classification is
`IncompleteWithWorkingMedia`: Manifest remains `Recording`, working media
exists, planned final media is absent, and the old owner lease is inactive.
The Scanner reports `deleteAllowed=false` and
`reconciliationAuthorized=false`.

## 16. Retain result

Manifest bytes/hash are identical before and after fresh-process scanning.
The working file's bytes/hash, FILE_ID, size, and timestamps are also
identical. The smoke path never invokes `NarrowReconciler`, never creates the
final MP4, and never attempts to repair, remux, truncate, or delete the
unfinalized working media.

## 17. Provenance

The parent records the current NativeTests EXE and loaded Native DLL paths and
SHA-256 values. The child and restart inspector must have the same full EXE
path and load the same full DLL path. Module provenance is read from the live
helper PIDs before they exit; expected build-directory strings are not used as
a substitute.

The final clean-build smoke used Session
`6C1BE76C-6B17-4A9A-A49B-64031C133545`, child PID 18312, forced exit
`0xD1260001`, Manifest revision 4, and a 79-byte crash-window working file.
Parent, child, and restart inspector all ran
`artifacts/bin/Release/x64/XbPreview.Native.Tests.exe`; all loaded
`artifacts/bin/Release/x64/XbPreview.Native.dll`. The final hashes were:

## 18. Timeouts and process cleanup

Child startup, Recording checkpoint, forced-exit wait, restart-inspector
startup, and inspector normal-exit waits are bounded. On exceptional exits,
the owner object can terminate only a still-live, revalidated process handle
that it created. A passing run requires both helper handles signaled and zero
related NativeTests processes before owned-fixture removal.

## 19. Targeted test matrix

`--p2.6d1-crash-harness` contains 24 gates covering helper identity, unique
IPC, real Recording checkpoint, external Active owner, real working media,
Manifest facts, exact-handle forced termination, non-graceful exit, automatic
owner release, retained working/Manifest, no fabricated final, fresh-process
restart, disk fact readability, `IncompleteWithWorkingMedia`, two mutation
authorization fields false, byte/hash/identity stability, no Narrow effect,
fixture isolation, binary provenance, and zero helper residue.

The final targeted run passed `P2.6D1_ACTUAL_CRASH_MATRIX=24` with exit code 0.
The successful owned fixture was removed only after all 24 gates. Earlier
diagnostic iterations remain preserved as required, including the
Path-Safety-denied TEMP fixtures and the artifact-root run that completed the
real kill/scan but still had the obsolete TEMP-isolation assertion.

## 21. What D1 does not prove

RecordingActive Crash Smoke is not Media Recovery PASS. The working MP4 may be
unfinalized, incomplete, and unplayable. D1 proves only:

`Real Kill + Persistent Evidence + Fresh-process Discovery + Retain Safety`.

It does not prove media repair, playback, remux, recovery publication, or any
of the three later crash checkpoints.

## 22. P2.6D-2 boundary

P2.6D-2 may execute the Stopping, Ready-before-rename, and
after-rename-before-metadata windows using the same safe Parent/Child/Inspector
architecture and internal-only barriers. It must define per-window expected
facts and keep repair/publication decisions separate. D1 does not begin that
work.

P2.6D-1 is ready; P2.6D-2 has not started.
