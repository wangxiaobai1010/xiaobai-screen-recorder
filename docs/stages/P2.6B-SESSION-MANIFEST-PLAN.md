# P2.6B Session Manifest 设计与影响面扫描

## 1. 目标

状态：**P2.6B-PLAN-READY（仅设计，未实现）**。

基线为 `main` / `8a00f29b9234e8ae36395fe22db0088381f8fea7`，对应标签
`p2.6a-safe-publish-pass-2026-08-07`。P2.6A 已经建立安全的文件生命周期：

```text
WorkingPath
  -> Finalize
  -> Validation
  -> worker resource release
  -> join
  -> ReadyToPublish
  -> MoveFileExW publish
  -> PublishedPath
  -> Completed
```

P2.6B 的唯一目标是为每个录制 Session 建立最小、版本化、原子更新的跨进程事实记录，
使未来进程启动后能够知道“上一次进程最后成功持久化了什么”。它不恢复、不修复、
不扫描，也不改变 P2.6A 的三路径、发布或 Completed 定义。

## 2. RecordingSnapshot 与 Session Manifest 边界

| 对象 | 事实范围 | 生命周期 | 所有者 | 主要消费者 |
| --- | --- | --- | --- | --- |
| `XbRecordingSnapshot` | 当前进程内实时事实，包括状态、PTS、资源、Finalize、Validation、Publish 和三路径 | Preview/进程存活期间 | Native `VideoEncoderConsumer`，同一 Snapshot mutex | Managed Controller、UI、LongRun |
| Session Manifest | 最后一次成功落盘的跨进程决策事实 | 跨进程、跨正常退出或崩溃 | Native 当前 Session 的单一 manifest writer | 未来 P2.6C scanner/reconciliation |

二者不能互相替代：

- Manifest 不参与 UI 计时、按钮状态、当前 Encoder 状态或 LongRun 的运行中判断。
- Snapshot 不证明进程崩溃后磁盘上最后留下的状态。
- Manifest 是“最后已知持久事实”，不是文件系统真值；路径、文件存在性、大小及内容
  仍必须由未来 reconciliation 重新核对。
- Manifest 写入不得在 Managed 层重建 Native 状态，也不得成为第二套
  `RecordingController`。
- 当前 Snapshot ABI `0x00040001` / 2856 bytes 不因 P2.6B 设计而修改。

## 3. 存储位置比较与推荐

### 3.1 候选比较

| 方案 | 权限与同卷 | 崩溃后发现 | 用户理解性 | 未来扫描与风险 |
| --- | --- | --- | --- | --- |
| A. 与媒体并列：`<SessionId>.manifest.json` | 与 working/final 完全同目录、同 ACL、同卷；不增加目录权限 | 在受管输出目录按后缀可发现 | 关联直观，但技术文件会混入视频列表，用户移动 final 后容易留下 sidecar | 扫描简单；输出目录越开放，误删、误编辑和技术文件可见性越高 |
| B. 同一受管输出根下的 Session 目录：`sessions/<SessionId>/manifest.json` | 与媒体共享输出根和卷；需要创建受管子目录，继承当前用户 ACL | 只扫描一个受限命名空间，Session 身份天然分区 | 用户视频列表保持干净；技术目录需要未来产品解释 | 扫描边界最清楚；manifest 与媒体靠绝对三路径关联，不能靠目录邻接猜测 |
| C. 全局应用数据目录，例如 `%LOCALAPPDATA%/.../Sessions` | ACL 易收紧，但可能与视频输出不同卷、不同权限域 | 单一全局入口最容易发现 | 用户输出目录最干净，但复制/迁移视频不会带走事实 | 输出位置变更、便携备份和多卷故障更难对账；不适合作为第一版 |

### 3.2 推荐方案

推荐 **B**：在当前受管录制输出根下使用应用保留目录，例如：

```text
<ManagedOutputRoot>/sessions/<SessionId>/manifest.json
```

理由：

1. 与 working/final 位于同一输出根、通常同卷并继承同一用户权限，不引入全局数据库。
2. P2.6C 未来只能扫描 `sessions` 这一受管命名空间，不需要遍历任意用户目录。
3. 每个 Session 独立目录可以容纳原子更新临时文件，而不污染用户视频列表。
4. 三类绝对路径仍是关联媒体的唯一依据；目录结构只是发现入口，不构成成功事实。

这对 P2.6 施工图中“相邻 sidecar”的早期建议作了收敛：媒体仍同目录安全 publish，
但持久元数据集中到同一输出根的受管 `sessions` 命名空间。未来扫描因此不需要把
用户视频目录中的每个 JSON 都当作候选 manifest。

“同卷”不能让视频 publish 和 manifest update 变成一个跨文件事务。P2.6A 的 move
成功而 manifest 尚未更新，仍然是必须由 P2.6C 对账的正式崩溃窗口。

## 4. 最小字段设计

建议 schema v1 使用 UTF-8 JSON。时间均为 UTC RFC 3339；HRESULT/错误码保存为
32-bit 数值，不保存本地化字符串。最小结构如下：

```json
{
  "schemaVersion": 1,
  "revision": 1,
  "writerStrategy": "mf-sinkwriter-standard-mp4-v1",
  "sessionId": "{00000000-0000-4000-8000-000000000000}",
  "createdAtUtc": "2026-08-07T00:00:00.0000000Z",
  "updatedAtUtc": "2026-08-07T00:00:00.0000000Z",
  "workingPath": "E:\\\\...\\\\session.partial.mp4",
  "plannedFinalPath": "E:\\\\...\\\\session.mp4",
  "publishedPath": "",
  "state": "Created",
  "workingFileOwnedBySession": false,
  "writeSampleAttempted": false,
  "frameSubmitted": false,
  "workerExited": false,
  "recordingResourcesReleased": false,
  "residualOutstanding": 0,
  "finalize": {
    "attempted": false,
    "count": 0,
    "hresult": null
  },
  "validation": {
    "attempted": false,
    "passed": false,
    "hresult": null
  },
  "publish": {
    "attempted": false,
    "hresult": null,
    "published": false
  },
  "errorCategory": "None",
  "errorCode": null,
  "errorMessage": ""
}
```

### 4.1 字段约束

- `schemaVersion`：格式版本；不支持的版本必须 fail-closed 为 `Unknown`，不得猜测。
- `revision`：从 1 单调递增；用于拒绝旧状态覆盖新状态，不是帧计数。
- `writerStrategy`：标识普通 MF SinkWriter MP4 策略，为未来 P2.6D 判断可恢复能力保留
  最小事实。
- `sessionId`：规范 GUID；必须与 Session 目录名及三路径文件名身份一致。
- `createdAtUtc`：首次创建后不可改变；`updatedAtUtc` 只在成功发布新 revision 时更新。
- `workingPath`、`plannedFinalPath`：Start 冻结的完整绝对路径，后续 revision 不变。
- `publishedPath`：publish 成功前必须为空；成功后必须逐字符等于 planned final。
- `workingFileOwnedBySession`：只有 Native `CREATE_NEW` 成功取得 working 所有权后才为
  true，且不能回退。
- `writeSampleAttempted`、`frameSubmitted`：第一次成功 `WriteSample` 后一起形成且永不
  回退；生命周期 writer 只在该边界写一次，不按帧更新。
- `workerExited`、`recordingResourcesReleased`、`residualOutstanding`：join 后记录的资源
  事实；ReadyToPublish 要求 worker 已退出、录制资源已释放且残留为 0。
- Finalize、Validation、Publish 子对象只保留跨进程决策所需事实，不复制 PTS、帧数、
  内存、句柄、线程或全部 Snapshot。
- `errorCategory`、`errorCode` 和受限 `errorMessage` 保存分类、机器码及固定诊断，不写异常堆栈、窗口标题、
  用户输入或原始诊断文本。

### 4.2 状态定义

允许状态：

| 状态 | 持久含义 |
| --- | --- |
| `Created` | Session 身份和三路径已冻结，尚未宣称编码启动 |
| `Starting` | 正在取得 working 所有权、注册 consumer 或启动编码管线 |
| `Recording` | Native 录制管线已进入 Recording；不代表已成功 Finalize |
| `Stopping` | 正式 Stop/Close 已请求，正在停止、Finalize、Validation 或 join |
| `ReadyToPublish` | join 后 P2.6A 的全部 publish 前置条件已成立，move 尚未成功 |
| `Published` | move 已成功且 Published 事实已持久化，终态收尾尚未写成 Completed |
| `Completed` | Published 已成立且 Session 终态已持久化 |
| `Failed` | 当前进程知道的终态失败；媒体是否存在仍由三路径和磁盘对账决定 |
| `Unknown` | 仅供解析/reconciliation 分类；正常 live writer 不主动写入此状态 |

合法迁移必须单调。错误或延迟写入不能把 `Stopping` 写回 `Recording`，也不能把
`Published`/`Completed` 写回失败状态。`Published` 是不可逆磁盘事实。

### 4.3 失败分类

`errorCategory` 至少区分：

- `None`
- `Recording`
- `Finalize`
- `Validation`
- `Publish`
- `ManifestPersistence`
- `UnknownCrash`

`UnknownCrash` 无法在崩溃瞬间由已终止进程写入。P2.6C 只能在确认没有 live owner、
manifest 停留在非终态且磁盘事实不一致时派生该分类；本阶段不实现该判断。

## 5. 生命周期写入策略

Manifest 只在关键状态或不可逆事实边界写入，不按帧、不按秒、不保存实时 PTS。建议
写入点如下：

| 生命周期边界 | 持久化内容 | 失败原则 |
| --- | --- | --- |
| Start 冻结 Session/路径后 | 原子首次创建 `Created` | 创建失败只记录持久化诊断；不得因此中断安全录制链 |
| 进入 Native Start | `Starting` | 不接管已有 manifest；写入失败时媒体事实仍由 Snapshot/Controller 推进 |
| `CREATE_NEW` 成功 | `workingFileOwnedBySession=true` | 不能记录所有权时不得依据 manifest 删除文件 |
| 管线进入 Recording | `Recording` | 不由 Managed UI 推断；使用 Native 事实 |
| 第一次 `WriteSample` 成功 | `writeSampleAttempted=true`、`frameSubmitted=true` | 只写一次；不按帧更新，确保 Recording 来自真实媒体提交 |
| 正式 Stop/Close 请求 | `Stopping` | 与现有 single-flight Stop 共用入口，不新增 Stop 路径 |
| worker exit 且 join 完成 | 写入 Finalize、Validation、失败和资源决策事实 | 未满足条件时写 `Failed` 并保留 working |
| 全部 publish 前置条件成立 | `ReadyToPublish`，在 move 前尽力持久化 | 写入失败不阻止 P2.6A 安全 publish；旧 revision 保持权威并等待 P2.6C 对账 |
| `MoveFileExW` 成功 | 立即写 `Published`、publish 成功和 `publishedPath` | 写失败不能回滚、删除或否认 final；由 P2.6C 对账 |
| Native terminal Snapshot 完成 | `Completed` | 若此更新失败，先前 Published 事实和 final 仍有效 |
| 已知终态失败 | `Failed` + 分类/代码及已成立子事实 | 不把所有失败压成字符串；不删除已写素材 |

### 5.1 为什么不每秒写

- 每秒更新不提供新的恢复决策事实；墙钟与 PTS 不能让未 Finalize 的普通 MP4自动
  变成可播放文件。
- 高频 flush 会增加磁盘写放大、延迟抖动和录制主链干扰。
- 关键边界更新已覆盖身份、所有权、媒体提交、Finalize、Validation 和 Publish。

### 5.2 写入所有权与并发

- Manifest writer 属于 Native `VideoEncoderConsumer` 当前 Session；Managed 不写。
- 不新增后台录制线程或第二套状态机。Start caller、encoder worker 和 StopAndJoin
  只把既有事实提交给同一个串行 writer。
- Manifest I/O 不得在持有 `snapshotMutex` 时执行，也不得回调 FrameTap/Managed。
- 独立 manifest mutex 只保护 revision 和文件替换；状态迁移检查必须防止晚到的
  `Recording` 覆盖已经持久化的 `Stopping`。
- `stopMutex`、manifest mutex 和 Snapshot mutex 的锁序必须在实现审查中固定；
  manifest writer 不等待 encoder thread，因此不能形成 join 环路。

### 5.3 Manifest persistence failure 语义

- Manifest 是持久事实记录，不是媒体安全或 publish 的前置控制器。首次创建、生命周期
  更新或终态更新失败时，当前 Session 禁止跳过 revision 继续覆盖，保留最后成功落盘的
  manifest（或无 manifest），并在 Native 编码诊断中记录首次/最后 HRESULT。
- 持久化失败不得把成功的 Start、WriteSample、Finalize、Validation、MoveFileExW 或
  Completed 改写成录制失败，也不得触发 working/final 删除。媒体继续走同一个正式
  RecordingController、StopAndJoin 和 P2.6A publish 链。
- `MoveFileExW` 已成功后，final、Published 和 P2.6A Completed 事实不可回滚。P2.6C
  将依据磁盘与旧 manifest 识别“final 存在、working 缺失、manifest 落后”窗口。

因此 Manifest 失败降低的是跨启动可发现性，不是否定当前录像安全。若未来要把该警告
暴露给 Managed/UI，应先独立审计是否需要 ABI 扩展；P2.6B 不改变 Snapshot ABI。

## 6. 原子创建与更新策略

### 6.1 首次创建

1. 在 Session 目录内用唯一临时名和 `CREATE_NEW` 创建临时文件。
2. 写完整 UTF-8 JSON，检查 WriteFile 结果并 `FlushFileBuffers`。
3. 关闭句柄后，用同一生产 parser 回读并验证 schema、SessionId、revision、三路径和
   状态不变量。
4. 使用同目录无覆盖 rename 创建 `manifest.json`。目标已存在视为 Session 身份冲突，
   Start fail-closed，不能接管或覆盖旧 manifest。

### 6.2 后续更新

1. 在 manifest mutex 下从当前已确认 revision 生成 `revision + 1`。
2. 用新的唯一临时名 `CREATE_NEW`，完整写入、flush、close、回读验证。
3. 仅当磁盘目标仍是期望旧 revision 时，使用 Windows 同目录原子 replace 更新
   `manifest.json`；失败时旧 manifest 保持权威，不宣称新 revision 成功。
4. replace 后重新打开正式 manifest，回读并确认新 revision；必要的 flush 只针对
   manifest，不改变视频 publish 规则。

推荐“temp + flush + validate + same-directory replace”。直接截断重写正式 manifest
会留下半截 JSON；先删后 rename 会产生无 manifest 窗口；跨目录临时文件不能保证
同文件系统原子替换。

P2.6A 禁止覆盖 final 的规则保持不变。Manifest 后续 revision 的 replace 是元数据
版本更新，不得复用到视频发布。Windows 的 rename/replace 与 write-through 也不等价于
已证明断电绝对耐久；必须通过隔离子进程和故障注入验证。残留临时文件不是正式
manifest，P2.6C 不得把它当可信状态，也不得在本阶段自动清理。

## 7. P2.6C 未来 reconciliation 规则

本节只定义未来分类输入，不实现扫描或动作。总原则是：**磁盘事实优先，Unknown
默认保留，不自动覆盖、删除或发布。**

| Manifest 与磁盘组合 | 未来分类与原则 |
| --- | --- |
| `publish.published=true` / State=Published 或 Completed，但 final 不存在 | `published-output-missing` / Unknown；不能凭 manifest 假装成功。保留任何 working，报告不一致，不自动重建或删除 |
| final 存在，manifest 仍为 Recording/Stopping/ReadyToPublish | `published-needs-reconciliation`；若 working 缺失且路径身份严格匹配，重新验证 final 后才允许更新 manifest。不能因旧 state 否认 final |
| partial 存在但 manifest 不存在 | `orphan-unknown`；文件名模式不能证明 Session 所有权。保留，不自动 publish、修复或删除 |
| manifest ReadyToPublish，working 存在、final 不存在 | `recoverable-candidate`；未来可重新验证并提供受控动作，本阶段不自动发布 |
| working 与 final 同时存在 | `path-conflict` / Unknown；两者都保留，不覆盖，不根据大小选一个 |
| manifest 损坏、schema 不支持、路径越界或 revision 非法 | `manifest-invalid` / Unknown；不跟随其中路径执行文件操作 |
| manifest Completed、final 存在且 working 不存在 | `published-consistent`；仍不需要修改视频，必要时可做只读验证 |

P2.6C 依赖 P2.6B 提供：稳定 schema/version、严格 parser、受管 Sessions 根、单调
revision、三路径、working 所有权、媒体提交事实以及 Finalize/Validation/Publish 的
独立结果。没有这些事实，P2.6C 只能分类为 Unknown。

## 8. 安全、权限与隐私

- Manifest 继承受管输出根的当前用户 ACL；不授予 Everyone 写权限，不提升权限写入。
- Manifest 包含绝对路径、Session GUID 和时间戳，可能暴露用户名、目录结构和录制
  时间，应按用户数据处理，不上传、不写遥测、不输出到公共日志。
- 不记录窗口标题、键盘内容、网页 URL、媒体像素、Token、完整异常栈或任意用户文本。
- 错误只保存枚举分类和数值代码；面向用户的本地化文字由运行时/UI生成。
- parser 对路径不做 Trim/猜测修复。未来 P2.6C 在执行任何动作前必须规范化路径并
  验证其位于受管根、SessionId 身份匹配，且不跟随 manifest 指向任意外部文件。
- 用户手工删除 manifest 后，残留媒体一律变成 unknown 并保留；不能按文件名自动
  删除。保留期限和用户删除入口属于未来 Recovery UI/策略，本阶段不定义自动清理。

## 9. LongRun 边界

LongRun 继续读取正式 Managed RecordingSnapshot，因为它验证的是当前运行的真实
RecordingController、PTS、Finalize、Publish、资源与 Preview Close。它不得在运行中
轮询 manifest，也不得用 manifest 推算状态或时间。

P2.6B 实现后，LongRun 可以在终态完成和 Preview 关闭后增加一次**补充证据**：确认
对应 manifest 可解析、SessionId/三路径一致并到达 Published/Completed。该检查只能是
持久化证据 Gate，不能替代 Snapshot、SourceReader 或 MP4 文件验证；本设计阶段不改
LongRun。

## 10. 测试策略与实现影响面

### 10.1 未来 P2.6B 测试矩阵

- schema v1 序列化/解析 round-trip，中文绝对路径逐字符一致。
- 缺字段、错类型、未知 schema/state、截断 JSON、非法 GUID/revision/path 均
  fail-closed 为 Unknown。
- 首次 manifest 目标已存在时不覆盖；旧文件字节保持不变。
- 后续 revision 单调；并发或迟到旧状态不能覆盖新状态。
- temp 写入、flush、回读或 replace 各阶段失败时，正式 manifest 保持上一份有效版本。
- 崩溃后只允许出现“旧有效”“新有效”或明确 invalid/临时残留，不允许半截正式 JSON
  被当作有效。
- Start、第一次媒体写、Stop、Finalize、Validation、Ready、Publish、Completed 和
  各类失败的 manifest 状态与正式 Snapshot 事实一致。
- manifest 失败不阻止正式媒体链；不得删除 working/final，也不得伪造更高 revision。
- 双 Session 目录、revision、路径及错误事实互不串用。
- 权限拒绝、中文路径、长/非法路径和真实进程中断使用隔离目录与专门子进程验证。

### 10.2 预计必须修改的生产范围（后续实现，不在本轮）

- 新增 Native `SessionManifest` model/parser/atomic store 及对应 Native 项目文件接线。
- `VideoEncoderConfig.h/.cpp`：派生受管 Sessions 根和当前 Session manifest 路径；不
  改 Working/PlannedFinal 生成规则。
- `VideoEncoderConsumer.cpp`：在现有 Start、worker、StopAndJoin、publish 和 terminal
  边界提交持久事实；不改 SinkWriter、帧、PTS 或 P2.6A publish 算法。
- Native 定向测试：序列化、原子替换、revision、故障矩阵和真实短 Session 接线。

预计不需要修改：

- `XbPreviewApi.h`、Exports 和 Managed P/Invoke/Snapshot ABI；Manifest 是 Native 内部
  持久事实，不加入当前 runtime Snapshot。
- `RecordingController`、MainForm 和正式 UI；它们继续消费 Snapshot。
- LongRun 正常运行逻辑；若未来加入终态 manifest 证据，应作为单独聚焦切片审查。

实现时若发现必须更改 ABI、Completed、MoveFileExW publish、cleanup 保留策略或
Managed Controller 语义，应停止 P2.6B 实现并重新审计，不能以 Manifest 为名扩大范围。

## 11. P2.6B 范围边界

P2.6B 只包含：

- 最小 schema 与严格 parser；
- 每 Session 的 Native 单一 writer；
- 关键生命周期原子持久化；
- manifest 自身故障对持久 revision fail-closed、对媒体链 fail-open 的定向测试。

P2.6B 不包含：

- 启动扫描或自动恢复；
- reconciliation 实现；
- 普通 MP4 修复或可播放承诺；
- fragmented MP4、分段录制或格式选择；
- Recovery UI、自动清理或保留期限；
- 云备份、磁盘阈值、音频或其他录制功能；
- P2.6C/D/E 的任何施工。

本设计已锁定：Manifest 位于受管输出根的 `sessions/<SessionId>` 命名空间；首次
创建无覆盖，后续使用同目录 temp + flush + validate + atomic replace；revision
单调校验；persistence failure 停止该 Session 的后续 manifest 覆盖并记录诊断，但不
阻止安全录制或 publish，也不得否认或删除 working/final。具体 Windows API 参数、错误映射和产品输出根名称在实现审查中固定，
但不得改变“Snapshot 是 runtime 事实、Manifest 是 persistent 最后已知事实、文件
系统必须重新对账”的核心边界。
