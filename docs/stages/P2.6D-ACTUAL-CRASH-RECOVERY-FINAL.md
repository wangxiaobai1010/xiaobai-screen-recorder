# P2.6D Actual Crash / Kill / Restart Recovery Final Audit

Date: 2026-08-08

Frozen candidate branch: `feature/p2.6d-postrename-crash-recovery`

Candidate HEAD: `3bcd8ac60c91938c9a07c10b8b99a15baf3cbc10`

Frozen P2.6C baseline: `f30d1ed95b465387c5ae61874927386662d4a8c0`

## 1. 阶段目标

P2.6D 用真实 Windows 进程终止验证录制 Session 在四个关键事故窗口中的持久事实、
kernel owner 自动释放、fresh-process 发现、保守 Retain，以及唯一被 P2.6C Narrow
Reconciliation 允许的 post-rename metadata 恢复链。

本报告是独立 Final Gate。它审查从冻结 P2.6C 到 D1、D2A、D2B 的完整线性差异，并以
当前同一 Release x64 构建执行最小冻结复验。

## 2. 阶段非目标

P2.6D 不证明也不实现：

- 任意 broken MP4 repair；
- RecordingActive 或 Stopping 事故后的 partial 必然可播放；
- Finalize 或 Validation 失败媒体可修复；
- 任意异常生命周期可自动恢复、自动发布或自动删除；
- fragmented MP4、分段录制或 remux；
- 磁盘空间、权限和保存目标的完整产品策略；
- P2.6E、P2.7、音频、60 FPS、后台或最小化录制。

## 3. 为什么真实 process kill 不同于异常注入

`throw`、故障注入、正常 `exit` 或 graceful Stop/Close 都可能执行栈展开、Finalize、
owner release 和 cleanup，不能代表进程突然消失。P2.6D Parent 使用
`CreateProcessW(CREATE_SUSPENDED)` 创建专用 Child，在恢复执行前绑定 PID、parent PID、
nonce、helper mode 和完整 image path；事故时只对这一个仍存活且再次核验的原始 process
handle 调用 `TerminateProcess`。

固定强制退出码是 `0xD1260001`。Parent 要求 handle 进入 signaled，且实际退出码既不是 0、
Child 正常返回码 47，也不是 harness 异常清理码 `0xD12600FF`。事故路径不按进程名或 PID
搜索目标，不调用 graceful Stop/Close，不让 Child 执行事故后的正常清理。

## 4. Crash Harness 架构

- Parent：创建隔离 fixture、唯一 named events、Child/Inspector/Managed Actor，验证模块，
  捕获现场并只终止自身创建的精确 Child handle。
- Recording Child：使用真实 RenderFrameTap、VideoEncoderConsumer、SessionManifestStore、
  lifetime owner、Media Foundation H.264 SinkWriter 与 P2.6A Safe Publish 链。
- Restart Inspector：全新 NativeTests 进程，从磁盘运行正式只读
  `ScanHistoricalRecordingSessions`。
- Recovery Actor：仅 D2B 在显式用户动作后创建的全新 ManagedTests 进程，调用正式
  `NativeNarrowRecoveryService` / Narrow ABI。
- Post-Recovery Inspector：恢复写入之后再次由全新进程确认最终分类。

每个 helper 都有有界启动、barrier 和退出等待。成功 fixture 只在所有 Gate 完成后删除；
失败 fixture 保留，且不会自动重跑。

## 5. 四个核心事故窗口总览

| 窗口 | kill 时持久状态 | 媒体事实 | fresh-process 结论 | 允许动作 |
|---|---|---|---|---|
| RecordingActive | schema 2 `Recording` | Working 未 Finalize，Final absent | `IncompleteWithWorkingMedia` | Retain |
| StoppingBeforeFinalize | schema 2 `Stopping`，Finalize 尚未开始 | Working 未 Finalize，Final absent | `IncompleteWithWorkingMedia` | Retain |
| ReadyToPublishBeforeRename | schema 2 `ReadyToPublish` | Working 已 Finalize/Validation，Final absent | `ReadyToPublishWorkingPreserved` | Retain，不自动 publish |
| AfterRenameBeforePublishedMetadata | schema 2 `ReadyToPublish` revision N | Working absent，Final 为同一 FILE_ID | `PublishOutcomeUnprovenRetain` | 仅显式用户动作后的 Narrow metadata reconciliation |

四种初始扫描结果均为 `deleteAllowed=false`、`reconciliationAuthorized=false`。Scanner 的
classification 是只读事实，不是 mutation capability。

外部 probe 在 kill 前得到 `ActiveOwned`。

## 7. StoppingBeforeFinalize 结果

Stopping barrier 是明确事件顺序，不依赖 sleep：先提交 `Manifest=Stopping`，再在 worker
进入 Finalizing、增加 finalize count 和调用 SinkWriter Finalize 之前阻塞。kill 前 Working
存在、Final absent、Finalize attempted=false/count=0、Validation 和 Publish 均未尝试，
owner 为 ActiveOwned。

本次 Session 为 `9FC9B232-4021-44A9-8ED7-CA7A03590EAA`，Child PID 16408，Inspector PID
9952，revision 5，Working 79 bytes。真实 kill 后新 Inspector 得到
`InactiveLeaseReleased` 和 `IncompleteWithWorkingMedia`；未调用 NarrowReconciler，现场不变。
结论是 `Stopping Crash Retain PASS`，不声明媒体可播放或可修复。

## 8. ReadyToPublishBeforeRename 结果

该 barrier 位于真实 Finalize 成功、SourceReader Validation 成功、worker exit、Join、录制
资源释放、`residualOutstanding=0`、Working persistent FILE_ID 持久化和
`PersistManifestReady` 之后，但位于 `MoveFileExW` 之前。

本次 Session 为 `27F514B0-5EE0-49AC-A870-A0C10300DC41`，Child PID 4648，Inspector PID
20692，revision 6，Working 6054 bytes。kill 前 Working exists、Final absent、Owner Active；
kill 后 fresh Inspector 得到 `ReadyToPublishWorkingPreserved` 和
`InactiveLeaseReleased`，两个 mutation authorization 字段均为 false。

事故后的 Working 通过只读 SourceReader 验证：5 个单调样本，FirstPts=0，LastPts=666666，
HRESULT=S_OK。这只证明本次已 Finalize/Validation 的 Working 技术上可读，不授予自动 publish
或自动 reconciliation 权限。

## 10. Fresh-process restart 证据

RecordingActive、Stopping、Ready 和 PostRename 都由新的 Restart Inspector 进程读取磁盘，
不是 Parent 内调用 Scanner 后改名为 restart。D2B 还使用独立 Candidate Actor、Recovery
Actor、Post-Recovery Inspector、Post-Recovery Presentation Actor 和 AlreadyReconciled Actor。

每个 evidence DTO 都绑定 helper PID、parent PID、SessionId、phase/version；Parent 在 helper
仍存活时核对完整 image path 和已加载 Native DLL。旧进程的内存状态不参与事故解释。

## 11. Owner 自动释放

所有真实事故都在 kill 前由外部 probe 观察到 `ActiveOwned`，在 kill 后由 fresh process
观察到 `InactiveLeaseReleased`。Child 没有机会执行 owner release；结果来自 Windows kernel
关闭死亡进程的独占 handle。

持久 `session.owner.lock` rendezvous 文件在事故后仍可存在；文件存在不等于 owner active，
PID 也不作为 ownership 正确性依据。D2B recovery 完成后 maintenance lease 同样已释放。

## 12. 事故现场 Retain 语义

Retain 表示：在事实不足或历史结果不明时，不删除、不覆盖、不移动、不修复、不伪造成功。
Recording 和 Stopping 的 Working 可能尚未 Finalize；Ready 的 Working 虽在本 case 可读，也不
自动发布；PostRename 在显式动作前仍是未证明 publish 结果的候选。

`IncompleteWithWorkingMedia`、`ReadyToPublishWorkingPreserved` 和
`PublishOutcomeUnprovenRetain` 均不是 Completed、OutputSuccess 或 Recovered。

## 13. D2B explicit recovery 链

D2B 顺序固定为：fresh initial scan → 正式 Managed presentation 得到 CanTryRecovery → Parent
记录显式 `USER_RECOVERY_ACTION` → 新 Managed Recovery Actor → 正式 Narrow bridge。候选发现
阶段前后 Manifest 和 Final 完全不变，因此没有后台自动恢复。

Recovery Actor 在调用前重新检查正式候选，然后调用
`NativeMethods.XbPreview_ReconcileNarrowSessionV1`，输入 diagnostic directory、canonical
SessionId 和原 expected revision N。Parent 不直接调用 private Manifest writer，也没有第二套
Reconciler。

## 14. Guard / CAS / schema 3 结果

正式 bridge 返回 Guard `EvidenceComplete`、CAS `Succeeded`。实际链包含 maintenance lease、
operation-time Manifest reload、expected revision、handle-based Path Safety、held Final handle、
persistent identity、hard-link guard、Working absence 双检、窄 source eligibility、immutable
whitelist、single nowUtc 和 expected-revision CAS。

唯一写入是 schema 2/N=6 → schema 3/N+1=7、state=`ReconciledCompleted`。结果保存
`FinalAtPlannedPathSamePersistentFileV1` 和
`MaintenanceLeaseCasHeldFinalIdentityV1`，`updatedAtUtc==reconciledAtUtc`。这不是 Native
Completed，也不是 OutputSuccess。

## 15. Historical truth 边界

Harness 作为测试上帝视角知道 Child 的 MoveFileExW 曾成功；生产 recovery 逻辑不能使用这份
知识。NarrowReconciler 只根据 operation-time 文件句柄、持久 FILE_ID 和 Manifest 事实确认
当前 PlannedFinalPath 上是同一媒体对象。

恢复后仍为 `originalPublishResultKnown=false`、`publishAttempted=false`、publish HRESULT absent、
`published=false`、`publishedPath=""`，post-publish identity verification unattempted。系统没有
伪造历史 Native API 返回值。

## 16. Media zero mutation

Scanner/Inspector 在所有窗口前后保持 Manifest revision/bytes/hash 与 Working/Final 的
SHA-256、size、FILE_ID、creation time、last-write time 不变。D2B Narrow reconciliation 只写
Manifest metadata；恢复前后 Final 的上述全部观察事实相同。

事故链没有对媒体执行 Move（真实 publish move 除外）、Copy、Delete、repair、truncate、remux
或 touch。D2B 的初次 fresh scan 明确发生在 NarrowReconciler 之前。

## 17. Media 可播放与不可播放语义边界

- RecordingActive：Working 未 Finalize，只证明 Retain，不要求 SourceReader PASS。
- StoppingBeforeFinalize：Working 可能未 Finalize，只证明 Retain，不要求可播放。
- ReadyBeforeRename：本次已 Finalize/Validation 的 Working 通过 5-sample 验证，但不自动发布。
- PostRename：Final 是同一已 Finalize/Validation 媒体，SourceReader PASS；Narrow 只补窄 metadata。

因此 P2.6D 不能概括成“crash recovery 会修好视频”。它证明的是分窗口、按证据强度不同的
保留与窄恢复语义。

## 18. 幂等

D2B 在恢复后使用另一个新 Managed Actor，以同一 SessionId 和原 expected revision N 再次
调用正式 bridge，结果为 `AlreadyReconciled`。磁盘保持 schema 3 revision N+1=7，没有 N+2；
Manifest bytes/identity/timestamps 和 Final 全部未变。

只有 post-recovery fresh Inspector 得到 `ReconciledCompletedConsistent` 后，用户 presentation
才进入 Recovered。

## 24. 已知限制

P2.6D 只覆盖四个精确定义的事故窗口。D2B 窄恢复只适用于：Final 已存在于受信任 planned
path、Working absent、schema 2 Ready source 合法、owner inactive、revision 精确、FILE_ID 强
匹配、无 reparse/hard-link 歧义且 operation-time Guard 完整的 Session。

身份缺失/不匹配、owner active、Working 仍存在、unsupported schema、reparse、hard link、
inaccessible path 或媒体失败继续 fail-closed/Retain。Harness 的合成桌面帧不等价于新的完整
用户画面验收。

## 25. P2.6E 依赖

safety 以及相关失败处理。P2.6D 的 Retain、Path Safety 和窄 reconciliation 证据不能替代这些
产品策略；本轮没有开始 P2.6E 或 P2.7。
