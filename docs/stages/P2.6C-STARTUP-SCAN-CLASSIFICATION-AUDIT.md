# P2.6C 启动扫描与异常 Session 分类方案独立反证审查

审查日期：2026-08-07

审查对象：`docs/stages/P2.6C-STARTUP-SCAN-CLASSIFICATION-PLAN.md`

审查基线：`main@c0805f4e678117ce6a5041deefb37a6794844066`

审查角色：独立安全审查 / adversarial review

## 1. 审查范围

本审查只核对 P2.6C-1 施工图能否安全进入后续只读 Scanner/Classifier 施工，重点攻击：

- SessionId、ManagedOutputRoot、Manifest 与媒体路径的真实生产契约；
- Manifest 陈旧、缺失、损坏、future schema 与文件系统事实冲突；
- Windows 路径别名、reparse point、hard link、TOCTOU 与访问失败；
- 进程可能在任意持久化边界崩溃时的分类歧义；
- 当前分类枚举是否会产生误判、错误的 reconciliation 候选或未来误删依据；
- 跨进程 live owner、文件身份与 revision 是否足以支持未来 P2.6C-3。

本轮没有修改既有 PLAN、生产代码、测试、ABI、Manifest schema、Publish、Completed 或 UI，也没有实现 Scanner、Classifier、reconciliation 或 recovery。

## 2. 总体结论

结论为 **P2.6C-PLAN-AUDIT-BLOCKED**。

现有 PLAN 的“只读、默认 Retain、Manifest 路径不直接授权操作、Scanner 与当前录制分离”方向正确，但存在两个会影响 Scanner/Classifier 事实正确性的开工 blocker：

1. 正式生产 SessionId 与 Manifest validator/test 的规范格式确定不一致；Manifest 创建会在 Session 目录建立之前失败，而录制与 publish 继续 fail-open。正式录制因此可能成功，但根本没有可供 Scanner 发现的 Session 目录或 Manifest。
2. `PublishedNeedsReconciliation` 把 `State=ReadyToPublish + final 存在 + working 缺失` 视为可自动推进 Published 的候选；当前 Manifest 没有 final 文件身份/所有权证据，这个组合无法排除外部同名文件或文件替换，分类语义过于乐观。

仅允许先进入用于关闭事实契约的 P2.6C-2a；不得直接开始 P2.6C-2b Scanner/Classifier。跨进程 live owner、行动前重验与 revision CAS 是 P2.6C-3 前硬门禁，不是纯只读 Scanner 的必要前置。

## 3. Blockers

| ID | 阻断事实 | 证据 | 必须关闭的结果 |
| --- | --- | --- | --- |
| B-01 | 正式 SessionId 契约不一致，导致正式录制无 Manifest | `PreviewEngine.cpp:289-305,1920-1939` 生成 GUID 后删除 `{}`；`SessionManifest.cpp:867-879` 与 `StringFromGUID2` 的带花括号规范文本逐字符比较；`CreateManifest` 在 `SaveAtomic/create_directories` 前先校验；`VideoEncoderConsumer.cpp:490-541` 创建失败后只关闭 Manifest 写入，录制继续；Native 测试使用带 `{}` ID | 统一一个规范格式，并由正式 C API 短 Session 证明 SessionId、目录名、Manifest、working/final 文件名一致；不得由 Scanner Trim/补括号猜测修复 |
| B-02 | `ReadyToPublish + final exists + working missing` 被错误列入可自动 publish reconciliation | 当前 Manifest 只有路径、状态、媒体/Finalize/Validation/Publish 事实及 `workingFileOwnedBySession`；没有 final 的卷序列号、File ID、创建身份、发布时大小/哈希或 final ownership marker | 在分类契约中把此组合降级为 `PublishOutcomeUnprovenRetain` 或 `FilesystemConflict`；除非先增加可验证身份链，否则不得自动写 Published/Completed |

## 4. Mandatory-before-reconciliation

以下项目不阻止只读 Scanner，但必须在任何 P2.6C-3 写回前关闭：

1. **跨进程 lifetime owner 证明。** 当前 `manifest.write.lock` 只在单次 `SaveAtomic` 中持有，不能证明 Session 已无 writer。
2. **行动时重新打开并验证对象。** ScanResult 是陈旧观察，不是操作授权；reconciliation 必须重新取得 root/session/manifest/final 的 handle 事实。
3. **revision compare-and-set。** 写回前重新读取，要求 expected revision 完全一致；revision 已变化时放弃，不得覆盖。
4. **文件身份/来源证明。** 若保留 Ready 窗口自动推断，至少需要同卷 file identity 链；否则永久取消该自动分支。
5. **访问失败三态。** `Missing`、`Inaccessible`、`IoError/Transient` 必须区分；任何不确定均 Retain。
6. **路径、reparse 与 hard-link 重验。** 不能复用扫描阶段的字符串判断，也不能在检查后按路径名直接操作。
7. **失败隔离与可取消的有界操作。** reconciliation 不得因单个卡死 I/O 阻塞 App 或影响其他 Session。

PID 文件不是 lifetime owner 证明：它会残留，PID 会复用，进程存在也不证明它仍拥有该 Session。需要由录制进程在整个 Session 生命周期持续持有、随进程退出由内核释放的独占对象，并附带不可混淆的 Session/进程实例身份；具体可采用受控 lock handle 或命名内核对象，但不能只看一个 PID 数字或锁文件是否存在。

## 5. Non-blocking limitations

1. **历史 OutputRoot。** 当前正式路径不是用户可变设置，而是从 Release 运行目录的 `diagnostic-logs` 经 Native 私有 `ArtifactsRoot` 向上推导，再固定到 `artifacts/p2.5a-recordings`。因此 D→E 用户设置切换目前不是现存产品场景。未来一旦允许更改输出根，旧 `sessions/` 会不可见；必须先增加受控的历史 root registry 或明确迁移策略。当前记为产品限制，不擅自扩大本阶段。
2. **无 Session 目录的孤立媒体。** 只扫描 `sessions/` 无法发现 Manifest 首次创建 fail-open 且目录从未建立时留在 output root 的 partial/final。除 B-01 的系统性缺口外，其他偶发 Manifest 创建失败仍会形成这个盲区。第一版可如实限制覆盖面，不得扩展为全盘搜索。
3. **不验证 MP4 可播放性。** Scanner 只陈述文件与持久事实，不以扩展名、大小或 SourceReader 结果猜测恢复能力；媒体可恢复性仍属 P2.6D。
4. **外部修改不可完全阻止。** 用户或其他进程可在发布后替换 final。没有持久 file identity 时，`CompletedConsistent` 只能表示“当前观察一致”，不能表示当前文件仍是原发布字节。
5. **网络/可移除根未支持。** 当前 root 是本机卷。未来若支持 UNC、网络盘或可移除盘，必须单独定义掉线、延迟、大小写与持久性策略，不能复用本地卷的缺失判断。

## 6. SessionId 审查

### 6.1 正式生产格式

`PreviewEngine::StartRecording` 使用 `CoCreateGuid`，随后调用 `GuidToString`。`GuidToString` 先调用 `StringFromGUID2`，然后明确删除 `{` 与 `}`。正式值形如：

```text
xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
```

### 6.2 Manifest 接受格式

`ValidSessionId` 用 `CLSIDFromString` 解析，再用 `StringFromGUID2` 得到规范文本，最后要求输入与规范文本 `_wcsicmp` 相等。规范文本带 `{}`，因此正式无花括号值即使能被解析，最终比较仍失败。

P2.6B 基础与生命周期测试使用的 ID 均带 `{}`，例如 `{00000000-0000-4000-8000-000000000001}`，没有覆盖正式 `PreviewEngine::GuidToString` 输出。

### 6.3 失败结果

`CreateManifest` 在创建 Session 目录前调用 `ValidateManifest`。校验失败时 `SaveAtomic` 不会运行，`sessions/<SessionId>/` 不会建立。`PrepareManifest` 仅把 `manifestWritable` 置为 false 并记录诊断，Encoder、Finalize、Validation 与 publish 仍可继续。

因此以下路径真实存在：

```text
formal StartRecording
  -> brace-less SessionId
  -> Manifest Create fails before session directory creation
  -> recording remains fail-open
  -> working may be written and final may publish successfully
  -> sessions-only Scanner has no discovery anchor
```

这不是“可能需要实证”的低风险猜测，而是由当前代码组合确定的契约矛盾，定级 **BLOCKER**。

修复后必须新增正式 C API 短 Session 集成证据；单独构造带花括号 `VideoEncoderConfiguration` 的测试不能关闭此门禁。目录枚举、Manifest `sessionId` 与 expected media leaf name 必须共同使用同一规范，不得在 Scanner 中兼容两种格式。

## 7. OutputRoot 审查

当前正式链路为：

```text
MainForm.OnShown
  -> AppContext.BaseDirectory/diagnostic-logs
  -> NativePreviewSession.Create(diagnosticLogDirectory)
  -> PreviewEngine.diagnosticLogDirectory_
  -> CreateRecordingConfiguration
  -> ArtifactsRoot(diagnosticDirectory) 向上四级
  -> artifacts/p2.5a-recordings
  -> VideoEncoderConfiguration.outputDirectory
  -> SessionManifestStore(managedOutputRoot)
```

结论：

- 当前没有由 Managed 显式持有、可供 Scanner 复用的 `ManagedOutputRoot` 配置对象；真实 resolver 是 `VideoEncoderConfig.cpp` 中的 Native 私有 helper。
- Scanner 不能从 Manifest、当前工作目录、最近 MP4 或 UI 文本反推 root，也不能复制一份可能漂移的“向上四级”算法。
- P2.6C-2a 必须提取共享、只读、受测的 root resolver，Recording 配置与 Scanner 使用同一结果；resolver 失败时 Scanner 返回 root-level failure，不能访问子项。
- 当前输出根固定，历史 root registry 不是当前 blocker；但如果后续增加“保存到”设置，配置变更前必须持久保存历史受信 root 或执行显式迁移。否则昨天 D 盘的 Session 在今天 E 盘启动时必然不可见。

Scanner 的 root 信任必须来源于产品配置/共享 resolver。Manifest 中任何路径都只是待验证数据，不得提升为扫描根。

## 8. 路径安全审查

当前 `SessionManifest::EqualPath` 仅执行 `std::filesystem::absolute(...).lexically_normal()` 后做大小写不敏感字符串比较。它不足以证明 Windows 对象位于受控根内，也不处理对象在检查后被替换。

P2.6C-2a 至少需要以下语义：

1. 从可信配置得到本机绝对 output root；第一版拒绝相对路径、UNC、device namespace 与无法确认卷身份的根。
2. 用目录 handle 获取 root 的最终路径、volume serial 与 file identity；不以字符串 `starts_with` 判子目录。
3. `sessions` 必须是 root 的直接子目录；Session 目录必须是 `sessions` 的直接子目录；Manifest 必须是该 Session 目录的固定直接文件。
4. 目录枚举不递归、不跟随 reparse point。root、sessions、Session 目录、Manifest 与媒体对象任一带 `FILE_ATTRIBUTE_REPARSE_POINT` 均 fail-closed。
5. Manifest 路径只允许与 `trusted root + canonical SessionId + fixed suffix` 派生的 expected path 逐对象相符。拒绝 `..`、相对路径、ADS、意外冒号、混合 device prefix、引号、NUL/截断与未知规范化。
6. `/` 与 `\`、大小写、`\\?\`、trailing dot/space 等 Windows 别名必须通过 Win32 handle 最终对象语义归一，而不是 Trim/Replace。
7. 对不存在的 expected leaf，不能取得 leaf identity；只能证明其可信父目录及固定 leaf name，并把不存在与打开失败区分。
8. junction、symbolic link、mount point 等 reparse 路径第一版全部拒绝跟随。网络或可移除卷另立策略。
9. hard link 不带 reparse 标志；需用 volume serial + File ID（必要时 link count/创建信息）识别同一对象和替换，不能靠路径文本发现。
10. 所有文件事实都必须携带 `Exists/Missing/Inaccessible/UnsafeReparse/IoError` 等状态及原始 Win32/HRESULT，不能把 `GetFileAttributes` 失败一律解释为缺失。

字符串前缀比较在 `C:\root` 与 `C:\root-escape`、8.3 别名、device prefix、junction 与大小写/尾随别名下均不构成安全边界，明确禁止。

## 9. Live owner 审查

`manifest.write.lock` 在每次 `SaveAtomic` 内部以无共享方式打开，替换结束后关闭并 best-effort 删除。它只串行化一次 Manifest 写入，不覆盖 Recording Session 生命周期。

仅排除“本进程 RecordingSnapshot 当前 active Session”不够：

- 第二个 Host 进程看不到第一个进程的 Snapshot；
- 第一个进程可能仍录制、正在 Stop/Finalize，或卡死但尚持有资源；
- `Recording/Stopping` Manifest 可能是崩溃残留，也可能属于仍活跃 writer；
- 进程存在、PID 文件存在或 PID 匹配都不能排除 stale PID/PID reuse。

安全结论：

- P2.6C-2 可以在 owner 未知时做只读观察，但必须输出 `LiveOwnerUnknown` 并归 `UnknownRetain`/禁止任何动作。
- P2.6C-3 前需要 OS 负责释放的 Session lifetime owner 证明；owner 对象应在 Session 创建至终态持有，崩溃时由内核释放，并能绑定 SessionId 与进程实例而非只绑定 PID。
- “锁文件不存在”不等于无 owner；“锁文件存在”也不等于 owner 活着。必须以能否取得独占内核对象及实例身份为事实。

因此 PLAN 结尾把 live owner 与 SessionId 一起列为“P2.6C-2 实现前必须关闭”过严。应修正为：SessionId 阻止 Scanner；live owner 不阻止 read-only Scanner，但阻止 P2.6C-3。

## 10. File identity 审查

当前 Manifest 不保存：

- volume serial；
- File ID / file index；
- 创建身份或发布时文件时间；
- publish 前 working 与 publish 后 final 的同对象证明；
- 发布时大小或内容 hash；
- final 的 Session ownership marker。

`workingFileOwnedBySession=true` 只表明该 Session 曾通过 CREATE_NEW 保留 working path；它不是 final 当前对象的身份，也不能排除 working/final 后续被替换、删除、hard-link 或外部创建。

所以：

```text
ReadyToPublish
+ PlannedFinalPath exists
+ WorkingPath missing
```

**不足以自动认定 Published。** P2.6A 的无覆盖 rename 与“外部文件后来占据同名 final、working 被用户/其他进程移走”会呈现相同路径组合。当前 Manifest 无法消歧。

安全选项只有二选一：

1. P2.6C-3 永久不自动处理 Ready 窗口，只标记候选并由用户可见入口保留；或
2. 在另行审查的持久事实版本中记录同卷 working identity，并在 final 上重新验证同一 volume/File ID 后才允许推进。

hash 可用于内容完整性，但单独 hash 不是所有权证明；路径和大小也不是。hard link 与对象替换要求 handle-based identity。

`State=Published + publish.published=true` 是已持久化的实际 Move 成功历史事实，比 Ready 窗口强。它可成为未来“仅写 Completed 元数据”的候选，但仍需 owner、路径安全、最新 revision 与 final 当前存在事实；该动作不能删除、移动或覆盖媒体。若产品要求证明当前 final 仍是原对象，则仍需持久 identity。

## 11. Crash window 审查

| 崩溃窗口/现场 | 能安全断言的事实 | 分类/动作边界 |
| --- | --- | --- |
| Ready Manifest 成功，Move 尚未发生；working 存在，final 不存在 | 具备发布前事实，素材仍是 working | `ReadyToPublishWorkingPreserved`；保留；重新 publish 是恢复动作，不是 reconciliation |
| Ready 成功，Move 成功，Published 未写；final 存在，working 缺失 | move 可能发生，但现有持久事实不能证明当前 final 来源 | `PublishOutcomeUnprovenRetain`/Conflict；禁止自动 Published |
| Move 成功，Published 成功，Completed 未写；final 存在，working 缺失 | Manifest 已持久声明 publish 成功 | 可列“Published metadata reconciliation candidate”；仍须 C-3 的 owner、重验与 revision CAS |
| final 与 working 同时存在 | 可能是旧 final 冲突、外部复制、用户操作、race，或不同对象 | `FilesystemConflict`；两者都保留，不选边，不删 working |
| final 存在但 Manifest 仅 Recording/Stopping | 缺少 Finalize/Validation/Publish 持久事实 | `UnknownRetain`/Conflict；不得跨状态猜 Completed |
| Completed/Published=true 但 final 缺失 | 历史成功事实与当前文件现场冲突 | `FilesystemConflict`；不删除其他旁证，不把不可访问误作缺失 |
| Publish 明确失败且 working 存在 | final 可能是造成冲突的外部文件 | `PublishFailedWorkingPreserved`；保留 working 与 final |

P2.6A 使用不覆盖的 `MoveFileExW(..., MOVEFILE_WRITE_THROUGH)`。若 final 在 publish 时已存在，move 失败且 working 应保留；但崩溃后单凭“final 存在/working 缺失”仍无法证明当时执行的是成功 move，用户或其他进程可能改变现场。

## 12. Manifest Missing 审查

必须区分两个发现域：

1. **Session 目录存在、`manifest.json` 缺失。** Scanner 可从已验证的目录 SessionId 派生 fixed expected working/final，并只读探测；分类为 `ManifestMissing`，全部 Retain。
2. **working/final 位于 output root，但 Session 目录从未建立。** 严格只枚举 `sessions/` 的 Scanner 完全看不到；不能声称分类为 `ManifestMissing`。

当前 `SaveAtomic` 只有在 Manifest 校验通过后才创建 Session 目录。Manifest 创建 fail-open 因此可能产生第二类盲区。B-01 使该盲区对所有正式 Session 成为系统性问题，必须先修。修复 B-01 后，权限、磁盘或 I/O 导致的首次创建失败仍可能留下孤立媒体；这是受控扫描边界的已知限制。

不得通过“扫描整个磁盘”补偿。若未来需要发现 output root 直属的严格命名 `.partial.mp4`，应作为独立、只读、受限且经过安全审查的 orphan inventory 设计，而不是悄悄扩大本 Scanner。

## 13. Parser/schema 审查

当前读取已具备有价值的安全基础：Manifest 非空且最大 1 MiB、严格 UTF-8/JSON、字段数量和类型严格、重复 key/尾随内容拒绝、schema/状态/不变量严格校验、原子写回前回读校验。

但 `LoadManifest` 最终只返回 HRESULT，不能稳定区分：

- `Missing`；
- `Inaccessible` / sharing / transient I/O；
- `MalformedJson`；
- `SchemaMissing`；
- `UnsupportedFutureSchema`；
- `SemanticInvalid`；
- `UnknownState`；
- `UnsafePath`；
- `Oversized`。

future schema 不能归 `ManifestCorrupt`。即使最终都 Retain，原因、升级兼容与用户提示不同。P2.6C-2a 应增加只读结构化 load result，复用现有 parser 的严格性但不放宽 writer API，也不修改 schema。

资源隔离还需明确数值策略：只枚举直接子目录；限制总 entry 数、并发 handle/解析数、单次 scan 结果数与总耗时；每项支持取消；超限时标记 inventory incomplete，绝不能返回“扫描完整”。1 MiB 只限制单文件，不能防止十万个小目录造成启动拒绝服务。同步本地 I/O 难以可靠超时，因此应在后台有界调度、拒绝网络 root、在条目间响应取消，并保证单 Session 失败不终止已完成结果。

## 14. 分类枚举逐项审查

下表中的“缺失证据”表示当前 Manifest/现场是否缺少足以支持该类强语义的事实。

| 分类 | 最小成立证据 | 必须排除的相似情况 | 默认素材策略 | 未来自动 reconciliation | 自动删除 | 缺失证据/审查结论 |
| --- | --- | --- | --- | --- | --- | --- |
| `CompletedConsistent` | strict current manifest；Completed；publish attempted/succeeded；PublishedPath=planned；safe final exists；working Missing；无 owner/访问不确定 | final Inaccessible、reparse、working 同时存在、路径/identity 冲突、future schema | final Retain | 不需要 | final 绝对禁止 | 缺 final identity；建议命名 `CompletedObservedConsistent`，只陈述当前观察一致 |
| `PublishedNeedsReconciliation` | 仅 `State=Published + publish.published=true`、safe final exists、working Missing 可成立 | Ready 窗口、Recording/Stopping、final identity 不明且要做媒体动作、owner unknown | final Retain | 仅未来元数据 Published→Completed，需硬门禁 | 绝对禁止 | 当前类把 Ready 与 Published 混在一起，必须拆分 |
| `ReadyToPublishWorkingPreserved` | strict Ready 前置事实；safe working exists；final Missing | final Inaccessible、working/final 同时存在、Finalize/Validation 未成功 | working Retain | 否；publish 是恢复动作 | 绝对禁止 | 语义成立，但不证明 working 可播放 |
| `IncompleteWithWorkingMedia` | 非终态/Failed；safe nonzero working 或已持久 media-attempt facts | 明确 Finalize/Validation/Publish failure 应优先进入更具体类；访问不确定；both-present | working Retain | 否 | 绝对禁止 | media facts 可能陈旧；只可作保留分类，不可作恢复承诺 |
| `IncompleteNoMedia` | 只能观察到 owner=false、WriteSample=false、frame=false、working Missing 且所有访问确定 | Manifest 更新失败/陈旧、working Inaccessible、0-byte/header file、live owner unknown | Manifest/现场全部 Retain | 否 | **绝对禁止** | 当前证据不能证明从未产生用户媒体；建议改名 `NoMediaObservedRetain`，不得成为清理授权 |
| `PublishFailedWorkingPreserved` | strict explicit publish attempted + failed HRESULT；safe working exists | final/working both、final Inaccessible、Ready 但 publish 未尝试、Manifest stale | working 与现有 final 都 Retain | 否 | 绝对禁止 | 语义成立；失败 final 可能是外部冲突文件 |
| `FinalizeOrValidationFailedWorkingPreserved` | explicit Finalize 或 Validation failure；safe working exists | publish failure、访问不确定、Manifest invalid、both-present | working Retain | 否 | 绝对禁止 | 两类可共享主类但必须保留独立 reason/HRESULT；不可暗示可恢复 |
| `ManifestCorrupt` | fixed manifest 是安全普通文件；支持范围内 JSON/语义损坏 | future schema、Missing、I/O/ACL、unsafe Manifest/reparse | 不信 Manifest 路径；仅保留安全派生对象 | 否 | 绝对禁止 | 必须从 future schema/unsafe/inaccessible 拆开；当前 HRESULT 不够 |
| `ManifestMissing` | canonical Session 目录安全存在；固定 manifest 确认 Missing | Session 目录不存在、manifest Inaccessible、output-root orphan、非规范目录 | 派生 working/final 全 Retain | 否 | 绝对禁止 | 不能覆盖“从未建立 Session 目录”的孤立媒体 |
| `FilesystemConflict` | 至少一个确定冲突：both-present、路径越界/不匹配、PublishedPath 不一致、Published final Missing 等 | 单纯 I/O unknown/future schema/live owner unknown 应进 Unknown | 所有可见对象 Retain，不访问越界目标 | 否 | 绝对禁止 | 过宽，必须用 reason + 明确优先级；安全冲突应压过生命周期类 |
| `UnknownRetain` | unsupported schema、unknown state、I/O/ACL/transient、owner unknown、资源上限、未覆盖组合 | 已有更具体且全部事实确定的类 | 全部 Retain | 否 | 绝对禁止 | 安全兜底成立；必须保留原始 status，而不是只有字符串 |

分类优先级应为：root/path/manifest 安全与访问不确定 > live-owner unknown > parse/schema 状态 > 文件系统冲突 > 明确操作失败 > 正常生命周期组合。否则同一 Session 可能同时满足具体 failure 与更严重的路径冲突，枚举顺序会改变结果。

必须新增或调整：

- 把 Ready + final/no working 从 `PublishedNeedsReconciliation` 移出，归 `PublishOutcomeUnprovenRetain` 或 `FilesystemConflict`。
- 将 `IncompleteNoMedia` 改为只读观察命名，并明确永不授权删除。
- 将 future schema 作为 `UnknownRetain + UnsupportedSchema`，不能归 `ManifestCorrupt`。
- `CompletedConsistent` 的“Consistent”限定为当前可观察事实，不代表内容/身份未被外部替换。

## 15. 安全不变量

1. **不可逆文件事实不能被旧 Manifest 否认。** final/working 当前存在时不得因 Manifest 陈旧而删除。
2. **Manifest 成功声明不能替代当前文件事实。** final 缺失/不可访问时不得宣称当前输出可用。
3. **任何 working media 默认 Retain。** 不因 final 存在、0 byte、扩展名或旧状态删除。
4. **Unknown/Corrupt/Future/Inaccessible 默认 Retain。** 不确定性永远不能转化为删除或 publish 权限。
5. **未通过路径安全验证的 Manifest 路径不可访问。** 只能作为诊断文本，不得 Open/Move/Delete。
6. **Scanner 只读。** 不写 Manifest、不创建/删除目录、不 publish、不修复、不取得 Encoder 控制权。
7. **ScanResult 不是行动授权。** reconciliation 必须重新打开、重新验证对象与 live owner。
8. **无法证明文件属于 Session 时不得自动 Published/Completed。** 路径名与存在性不是身份。
9. **访问失败不等于不存在。** ACL、sharing、I/O、网络/卷不可用均单独记录并 Retain。
10. **受信 root 只来自共享产品配置/resolver。** 不从 Manifest 或 current directory 提升信任。
11. **revision 只证明读取时版本。** 写回必须 re-read + expected revision CAS；不匹配即放弃。
12. **working+final 同存时两者均保留。** 不自动选择、覆盖、移动或删除任一侧。
13. **NoMedia 是观察，不是清理证明。** Manifest 持久化失败或陈旧足以否定自动删除资格。
14. **单 Session 错误隔离。** 单条损坏/权限/异常不能阻止 App 启动或污染其他分类。
15. **扫描必须有界且可取消。** 超限/取消时 inventory 标记 incomplete，不得宣称完整。
16. **Published 持久事实与当前文件身份分开。** 前者可支持受限元数据对账，不能授权媒体变更。

## 16. P2.6C-2 开工门禁

### BLOCKER（Scanner/Classifier 实现前必须关闭）

1. 统一 SessionId 规范，并由正式 C API 短 Session 验证完整持久事实链。
2. 修改分类合同：Ready + final/no working 不得是自动 `PublishedNeedsReconciliation`；拆分 Published 持久事实与 publish outcome 未证明。
3. P2.6C-2a 提供共享 trusted output-root resolver、结构化只读 Manifest read result、handle-based path/reparse/file fact DTO；2b 不得自行复制简化实现。
4. 定义确定的分类优先级、access 三态与 scan incomplete 语义。
5. 定义并测试有界枚举、1 MiB 文件限制、entry/result/concurrency 上限、取消和单 Session 隔离。

### MANDATORY-BEFORE-RECONCILIATION

1. 跨进程 Session lifetime owner 证明；PID 文件不足。
2. 行动时重新验证 root、path、reparse、file identity 与访问状态。
3. latest revision re-read + expected revision CAS。
4. 若要自动处理 Ready move 窗口，增加持久 file identity；否则删除该自动动作。
5. crash-at-each-boundary、并发 writer、对象替换/hardlink、权限与 sharing 竞态测试。
6. reconciliation 只能做经证明的元数据推进；不得删除、覆盖、二次 move 或恢复 working。

### NON-BLOCKING-LIMITATION

1. 当前固定 root 下无需历史 root registry；未来 root 可配置前必须补。
2. sessions-only Scanner 无法发现无 Session 目录的 output-root orphan；必须如实声明覆盖范围。
3. Scanner 不证明 MP4 可播放或可恢复。
4. 当前无持久内容 hash/identity，Completed 只能表示观察一致。

## 17. 推荐阶段拆分

原 2a/2b/3/4 方向仍合理，但建议明确以下停止线：

1. **P2.6C-2a0：契约修复门禁。** 只统一 SessionId，并用正式 C API 回归 P2.6B Manifest fail-open/正常路径；不写 Scanner。
2. **P2.6C-2a1：事实读取原语。** 共享 root resolver、结构化 parser result、handle-based safe path/file facts、资源上限；不枚举、不分类。
3. **P2.6C-2b：只读 Scanner + 纯 Classifier。** 使用已审查 DTO，实现修正后的矩阵、优先级、错误隔离、取消与 incomplete inventory；不写任何 Session。
4. **P2.6C-3：证据允许才做受限对账。** 先建立 lifetime owner、行动时重验与 CAS。默认只考虑已持久 `State=Published/publish=true` 的元数据 Completed 推进。
5. **Ready move 窗口单独决策。** 若不扩展 file identity，则降级为候选识别 + 用户可见提示，永久不自动 reconciliation；不要为了维持原计划硬做。
6. **P2.6C-4：Managed startup 编排。** 后台、可取消、有界；Preview 可启动，但新 Recording 在 scan 终止/安全取消/根错误已记录前受 gate；UI 不读取 Manifest 作为当前录制状态。

P2.6D 仍只负责 working 媒体的可恢复性验证，不得被 P2.6C 的分类名称提前承诺。

## 18. 必须修改 PLAN 的项目

下一轮应单独修改 PLAN，至少包括：

1. 把 SessionId 风险从“待实证”升级为已由源码证实的 blocker，并写明 fail-before-directory + recording fail-open 链。
2. 删除 `ReadyToPublish + final/no working` 的自动 reconciliation 授权；新增 outcome-unproven Retain/Conflict 分类。
3. 拆分 `PublishedNeedsReconciliation`：仅已持久 `State=Published + publish.published=true` 可成为元数据对账候选。
4. 将 live owner 从“P2.6C-2 前门禁”改为“P2.6C-3 前门禁”；owner unknown 的只读扫描合法但必须 Retain。
5. 明确 `IncompleteNoMedia` 永不授权自动删除，最好改名为 `NoMediaObservedRetain`。
6. 明确 `CompletedConsistent` 只是 observed consistency，不证明当前 final 的 session identity/content 未被替换。
7. 补充 Windows path 规则：UNC/device namespace、trailing dot/space、alternate separator、每级 reparse、hard link、nonexistent leaf 与 handle identity。
8. 补充 TOCTOU：P2.6C-3 必须重新打开并重验，不复用 ScanResult。
9. 补充 parser 结构化状态，尤其 future schema、semantic invalid、unsafe、inaccessible 与 missing 的区分。
10. 补充 scan 资源上限、取消、inventory incomplete 与十万目录/大量小 JSON 的拒绝服务边界。
11. 明确 Manifest Missing 只覆盖“Session 目录存在”的情形；无 Session 目录 orphan 是当前发现盲区。
12. 明确当前 OutputRoot 固定且由 Native 私有算法产生；2a 必须共享 resolver；历史 root registry 是未来可配置根的前置而非当前扩题。
13. 为全部分类规定安全优先级，避免枚举顺序改变分类。
14. 把 file identity/live owner 不足时的 P2.6C-3 降级路线写成正式停止线，而不是实现期再决定。

## 19. 审查结论

现有 PLAN 的安全基调正确，但当前生产 SessionId 使持久事实链系统性失效，且 Ready move 窗口缺乏文件身份却被列为自动对账候选。二者在修正前都不允许直接实现 Scanner/Classifier。

允许的下一步仅是单独修订 PLAN 并实施 P2.6C-2a 的契约/事实读取门禁；本报告不授权 P2.6C-2b、P2.6C-3、recovery、媒体删除或任何生产写动作。

最终结论：**P2.6C-PLAN-AUDIT-BLOCKED**。
