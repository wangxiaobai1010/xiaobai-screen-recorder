- 阶段：P2.6 安全保存与恢复（CURRENT）

## 2. 当前真实写盘链

### 2.1 调用、线程与所有权

```text
UI thread: MainForm Start button
  -> RecordingController.StartAsync
ThreadPool: RecordingController.StartCore
  -> NativePreviewSession.StartRecording
C ABI caller thread: XbPreview_StartRecording
  -> PreviewEngine.StartRecording [lifecycleMutex]
     -> CoCreateGuid
     -> CreateRecordingConfiguration
     -> PreviewRenderer.StartRecording [recordingMutex]
        -> VideoEncoderConsumer.Start
           -> PrepareSnapshot(Starting, predicted final path)
           -> Register FrameTap consumer
           -> start encoder MTA worker

render/capture path:
  OutputCanvas -> RenderFrameTap bounded queue

encoder MTA worker, on first accepted frame:
  create output directory
  -> calculate <outputDirectory>/<SessionId>.mp4
  -> CreateFileW(..., CREATE_NEW) and close reservation handle
  -> MFCreateSinkWriterFromURL on that same .mp4 path
  -> BeginWriting
  -> repeated WriteSample

UI thread: MainForm Stop button
  -> RecordingController.StopAsync
ThreadPool: RecordingController.StopCore
  -> NativePreviewSession.StopRecording
C ABI caller thread: XbPreview_StopRecording
  -> PreviewEngine.StopRecording [lifecycleMutex]
     -> PreviewRenderer.StopRecording [recordingMutex]
        -> VideoEncoderConsumer.StopAndJoin [stopMutex]
           -> request FrameTap consumer stop
           -> join encoder worker

encoder MTA worker during stop:
  stop accepting/writing frames
  -> NotifyEndOfSegment
  -> IMF SinkWriter Finalize exactly once
  -> wait for tracked NV12 returns
  -> bounded QuickRuntimeValidation through SourceReader
  -> Shutdown SinkWriter/pool/converter
  -> unregister FrameTap consumer and release D3D references
  -> publish fixed-storage WorkerOutcome and exit

control thread after worker join:
  failure: DeleteFailedSessionOutput
  -> PublishTerminal(Failed)

  success: no deletion and no rename/move step
  -> PublishTerminal(Completed)

UI timer/UI callbacks:
  GetRecordingSnapshot
  -> ManagedRecordingSnapshot
  -> state, elapsed PTS, path, error and Open actions
```

主要源码依据：

- `XbPreview.Host/RecordingController.cs`：Managed 唯一 Start/Stop 入口，
  `StartCore`、`StopCore`、`StopForCloseAsync` 和 Snapshot 映射。
- `XbPreview.Native/PreviewEngine.cpp`：创建 Session GUID 和配置，并把
  Start/Stop 转交 Renderer。
- `XbPreview.Native/VideoEncoderConfig.cpp`：正式录制目录由诊断目录向上解析到
  `artifacts/p2.5a-recordings`。
- `XbPreview.Native/VideoEncoderConsumer.cpp`：路径生成、`CREATE_NEW` 所有权、
  worker、Finalize、验证、失败删除、终态发布。
- `XbPreview.Native/MfH264SinkWriterSession.cpp`：
  `MFCreateSinkWriterFromURL`、`WriteSample`、`Finalize` 和 SourceReader 验证。
- `XbPreview.Host/PreviewLifecycleController.cs` 与 `MainForm.cs`：窗口关闭先走
  `StopForCloseAsync`，再停止/释放 Preview。

### 2.2 当前路径和事实来源

| 事实 | 当前产生位置 | 当前所有者 |
| --- | --- | --- |
| Session ID | `PreviewEngine::StartRecording` 的 `CoCreateGuid` | 本次 Native recording Session |
| 输出目录 | `CreateRecordingConfiguration` | Native 配置，仅运行时 |
| 输出全路径 | `VideoEncoderConsumer::PrepareSnapshot` 预计算；worker 首帧时再次计算 | `WorkerOutcome` 保存固定路径 |
| 文件所有权 | `ReserveSessionOutput` 的 `CREATE_NEW` 成功后 | `outputOwnedBySession=true` 的当前 Session |
| 编码资源 | encoder MTA worker | `VideoEncoderConsumer` |
| 原始失败 HRESULT | `VideoEncoderDiagnostics.failureHResult` -> `WorkerOutcome` -> Snapshot | worker 产生，Snapshot 发布 |
| cleanup HRESULT | `DeleteFailedSessionOutput` -> Snapshot 独立字段 | join 后的 `StopAndJoin` |
| Completed | Finalize、tracked return、QuickRuntimeValidation 全部成功后，join 后发布 | `StopAndJoin` 终态所有者 |
| UI 最终路径 | Native Snapshot `outputPath` 的 Managed 映射 | Native 是事实源，UI 只展示 |

当前路径是**直接写最终文件名**：`<SessionId>.mp4`。虽然只有通过 Finalize 和
QuickRuntimeValidation 才发布 `Completed/OutputSuccess`，但文件系统中没有
“工作文件 → 验证 → 发布”这一独立生命周期，也没有 publish 状态或 publish
HRESULT。当前所谓成功是状态发布，不是文件名发布。

`QuickRuntimeValidation` 只解码最多 8 个样本，检查文件非空、尺寸、存在解码帧
和所读样本 PTS 单调；它不读取到 EOS，因此不能单独证明整个长文件均可解码。
P2.4 的长测和人工抽样是额外证据，不改变此运行时验证边界。

### 2.3 正常关闭链

录制中正常关闭窗口时，`MainForm.CleanupAsync` 首先调用同一个
`RecordingController.StopForCloseAsync`。随后 `PreviewLifecycleController.CloseAsync`
再次检查录制是否仍 active，并仅在需要时复用同一路径，然后才停止 Native
Preview 和 Dispose Session。Native Preview worker 清理最终调用
`PreviewRenderer::Shutdown`，其内部仍复用 `VideoEncoderConsumer::StopAndJoin`。
single-flight 和 FinalizeCount=1 的 P2.5 不变量应继续保持。

## 3. 当前风险矩阵

下面的“可验证”只描述当前产品可以证明的事实。`UNKNOWN` 表示源码和现有证据
不足以保证，不能用“文件存在”代替证明。

| 场景 | 当前会留下什么 | Session/Finalize 事实 | 验证/可播放 | 当前 cleanup | 恢复可能 |
| --- | --- | --- | --- | --- | --- |
| A. 正常 Stop / Finalize | 直接最终名 `<SessionId>.mp4` | 运行时 Snapshot 持有 Completed、Finalize 和 HRESULT | QuickRuntimeValidation 成功；正常产品证据支持可播放 | 不删除 | 已是成功文件，不属于恢复 |
| B. Finalize 失败 | 失败时可能已有非空 `.mp4` | worker 保存 Finalize 失败；StopAndJoin 发布 Failed | 未完成 MP4 不保证可播放 | join 后尝试删除 Session 所有文件；删除失败才残留 | 删除前可能存在技术材料，但当前不保留；残留可恢复性 UNKNOWN |
| C. 输出验证失败 | 可能是已经 Finalize 的 `.mp4` | validation HRESULT 成为原始失败，Snapshot=Failed | 当前验证不通过；不允许当成功视频 | join 后尝试删除，即使可能已 Finalize | 被删除前可能可进一步诊断/修复，但当前丢失；可恢复性 UNKNOWN |
| D. 正常关闭但正在录制 | 与正常 Stop 共用 Controller/StopAndJoin | 应 Finalize 一次并得到 Completed 或真实 Failed | 成功时按正常路径验证 | 失败时删除；成功时保留 | 成功无需恢复；失败材料当前不保留 |
| E. 进程突然崩溃/被终止 | 首帧后可能残留直接最终名 `.mp4`；首帧前可能无文件 | 内存 Snapshot、WorkerOutcome 全丢失；无 manifest | 未调用 Finalize，不能保证 MP4 正确、可播放或可修复 | 没有机会运行 cleanup；下次启动也不扫描 | UNKNOWN；当前没有产品恢复能力 |
| F. 断电/OS 崩溃 | 文件、长度和已落盘数据本身都不确定 | 无持久 Session 状态，Finalize 通常未完成 | 文件系统与 MP4 内容完整性均 UNKNOWN | 无 cleanup | UNKNOWN；比普通进程崩溃风险更高 |
| G. 磁盘满 | 可能在建目录、保留文件、WriteSample 或 Finalize 阶段失败 | 检测到的 worker 错误可进入 Outcome；无预警/空间状态 | OutputSuccess 不会被伪造；部分文件不可视为成功 | 显式 Stop/Close 触发 StopAndJoin 后尝试删除；删除失败独立记录 | 当前通常删除；worker 自行失败到显式 Stop 前，Snapshot 仍可能保持 active，终态发布和删除会延后 |
| H. 权限/路径错误 | 可能无文件；保留失败时不会接管同名旧文件 | Snapshot=Failed；原始 HRESULT 保留 | 不可验证，不可播放 | `CREATE_NEW` 未取得所有权时不删除 | 无素材可恢复；路径是否支持取决于实际 Win32/OS 配置 |

额外边界：中文路径已通过 UTF-16 Managed/Native 编组验证，但 ABI 的
`outputPath[260]`、固定缓冲截断和未显式使用长路径前缀意味着长路径能力没有被
证明。当前没有 Start 前磁盘空间门禁、录制中空间监测、低空间安全 Stop 或为
Finalize/publish 预留空间的策略。

### 最大的三个安全风险

1. **未验证文件占用最终成功名称。** 崩溃后残留 `.mp4` 看起来像完成视频，
   但没有 Finalize、validation 或 publish 事实。
2. **失败清理会删除潜在恢复材料。** Finalize 或 validation 失败后，
   `StopAndJoin` 当前会删除本 Session 拥有的输出；原始材料和进一步诊断机会随之
   消失。
3. **没有跨进程 Session 事实。** Snapshot 只存在于内存；崩溃/断电后无法区分
   finalized-unpublished、未 Finalize、无效或未知文件，也没有安全启动扫描。

## 4. 普通 MP4 未 Finalize 的真实边界

当前普通 MP4 通过 `MFCreateSinkWriterFromURL` 写入，正常成功依赖
`NotifyEndOfSegment` 和 `IMFSinkWriter::Finalize`。如果进程在 Finalize 前突然终止，
本项目目前只能保证：

- 如果文件已经由当前 Session 成功创建，OS 可能在进程退出后留下该路径；
- 文件句柄会由 OS 回收；
- 不能保证容器索引、时长、尾部元数据或缓冲数据已经正确落盘；
- 不能保证 SourceReader、Windows 播放器或其他播放器可以打开；
- 即使某个具体文件偶然可播放，也不能推广为产品保证；
- 当前没有记录该文件精确写到了哪个生命周期阶段，也没有恢复器。

因此 P2.6 在完成专门技术验证前只能使用“保留未完成素材”“识别未完成
Session”“尝试恢复”“恢复失败时不覆盖或删除原始素材”等口径，不能写成
“崩溃后可恢复录像”。要达到“崩溃后尽量恢复可播放视频”，至少还需要对
fragmented MP4 或分段方案进行隔离故障实验，覆盖进程终止和断电近似故障点，
并证明常用播放器、SourceReader、时长和结尾行为。

## 5. P2.6 子切片与依赖顺序

### P2.6A：安全发布骨架

目标：在不改变编码格式、时间戳、Encoder 参数和 UI 主结构的前提下，引入三类
互不复用语义的路径事实和显式发布事实：

- `WorkingPath`：由 Native Session 创建并拥有，是真正写入的素材；失败保留时
  用它定位恢复材料。
- `PlannedFinalPath`：Start 前冻结，只是计划发布目标；publish 成功前不是用户可
  打开的视频。
- `PublishedPath`：publish 成功前必须为空；只由 Native publish 成功事实设置，
  是 Completed/Open Video/Open Folder 的唯一正式路径。

```text
working file
  -> normal Stop
  -> Finalize
  -> SourceReader validation
  -> worker releases resources and exits
  -> StopAndJoin performs same-volume, no-overwrite publish
  -> Completed points to final file
```

Finalize、validation 或 publish 任一步失败都保留 working 文件和原始错误。
P2.6A 同时提供真实路径/publish Snapshot，但不引入临时 manifest，不承诺崩溃
文件可播放，也不做启动扫描。

### P2.6B：跨进程 Session manifest

为每个 Session 原子持久化恢复决策所需的最小事实，包括最后已知的
`WorkingPath`、`PlannedFinalPath` 和 `PublishedPath`。它不替代运行时 Snapshot，
不复制完整诊断，也不凌驾于文件系统事实。P2.6A 的路径/发布状态应先稳定，
manifest 才不会固化错误模型。

### P2.6C：启动时未完成 Session 识别

只扫描受管目录和合法 manifest，不自动删除或改写视频。分类为：

- `finalized-unpublished`
- `published-needs-reconciliation`
- `recoverable-candidate`
- `invalid`
- `unknown`

“recoverable-candidate”只表示允许进入后续受控尝试，不表示已证明可恢复。

### P2.6D：崩溃恢复技术验证与选择

以隔离 Spike 比较普通 MP4、fragmented MP4 和分段方案。只有实证通过后才选择
产品容器/分段策略；不得在 P2.6A 中顺手重构编码链。

### P2.6E：磁盘、权限和路径安全

加入 Start 前空间门禁、录制中空间趋势/低空间预警、临界空间安全 Stop、
Finalize/publish 预留、权限和长路径验证。其 Stop 必须仍走 RecordingController，
不能成为第二套控制器。

推荐顺序为 `A -> B -> C`，同时在 A 完成后独立开展 D 的 Spike；E 的路径契约应
与 A 一起确定，空间策略可在 A 后实现。C 的自动修复入口必须等待 D 给出真实
能力边界。

## 6. 第一施工切片：P2.6A 安全发布骨架

这是 P2.6 的第一个可施工垂直切片。它应只改变文件生命周期，不改变 H.264、
普通 MP4 容器、时间戳、FrameTap、NV12、码率或 UI 主结构。

### 6.1 路径规则

- `WorkingPath`：`<SessionId>.partial.mp4`
- `PlannedFinalPath`：`<SessionId>.mp4`
- `PublishedPath`：Start 时为空，publish 成功时才设置为 `PlannedFinalPath`。
- working 和 planned final 在 Start 前同时确定，使用同一规范化绝对父目录。
- working 和 planned final 必须同卷，确保发布不退化为复制。
- 必须证明 working 由本 Session 独占创建，且已有 working 目标使 Start
  fail-closed、原文件不变。这里锁定 exclusive/no-overwrite 不变量，不提前硬锁
  某个创建 API。
- P2.6A 开工时先审计现有 `MFCreateSinkWriterFromURL` 路径能否与当前显式预留
  共同证明独占创建；若不能，再评估显式 writable byte stream/文件句柄。不得仅为
  追求某个 API 名称而重写 Encoder。
- final 不创建占位文件，避免未验证内容以最终名称出现。
- Start 时可以先检查 final 冲突，但真正 publish 仍必须使用“不覆盖”操作抵抗
  检查后的竞态。
- 唯一提交调用优先采用
  `MoveFileExW(WorkingPath, PlannedFinalPath, MOVEFILE_WRITE_THROUGH)`。
- 禁止 `MOVEFILE_REPLACE_EXISTING`、`MOVEFILE_COPY_ALLOWED`、copy+delete fallback、
  Managed `File.Copy`/`File.Move` 接管终态，以及冲突后偷偷改名继续发布。
- `MoveFileExW` 返回 `FALSE` 时必须立即保存原始 `GetLastError`，再投影 HRESULT；
  working 保留、final 原样不动、Session 不得 Completed。
- `MoveFileExW` 返回 `TRUE` 时立即、不可逆地记录 `publishHResult=S_OK`、
  `published=true`、`PublishedPath=PlannedFinalPath`。后续 Snapshot 或一致性读取失败
  不得把它倒写成“move 失败”。
- `MOVEFILE_WRITE_THROUGH` 只能描述为请求同步完成 move，不得描述成已经证明断电
  绝对安全；断电耐久边界仍需定向实验。

planned final 名称应在 Start 前确定，而不是 Stop 后临时决定。这样 UI、日志、manifest
和冲突策略从 Session 开始即一致，同时 publish 时仍以 no-overwrite 为最终裁决。

### 6.2 终态所有权

沿用 P2.5 已收敛的终态结构：

1. encoder worker 只写 `WorkingPath`，完成 Finalize、验证、资源清理并产生
   `WorkerOutcome`；
2. worker 不删除也不发布文件；
3. `StopAndJoin` single-flight 等待 worker 完全退出；
4. join 后由 `StopAndJoin` 计算正式 `ReadyToPublish`；
5. `ReadyToPublish` 成立时，`StopAndJoin` 才在 Native 生命周期内执行唯一 publish；
6. publish 成功后立即提交 `Published` 文件系统事实，再发布
   `Completed/OutputSuccess`；
7. publish 失败时发布 `Failed`，保留 working，不覆盖 final，并单独记录 publish
   HRESULT；
8. Preview Close 和显式 Stop 继续复用同一个 `StopAndJoin`。

固定生命周期为：

```text
working
  -> Stop
  -> Finalize
  -> SourceReader validate working
  -> release validation reader
  -> worker/encoder resources exit
  -> join complete
  -> ReadyToPublish
  -> Native MoveFileExW publish
  -> Published
  -> Completed
```

`ReadyToPublish` 的正式谓词为：worker 已退出且 join 完成；
`FinalizeAttempted=true`；`FinalizeCount=1`；Finalize HRESULT 成功；
`ValidationAttempted=true`；Validation HRESULT 成功；publish 前 WorkingPath 文件
真实存在且非零；录制专属资源全部释放；`ResidualOutstanding=0`。

`Published` 的正式谓词为：`PublishAttempted=true`；publish 调用成功；
`published=true`；`PublishedPath==PlannedFinalPath`；提交时 final 文件事实成立；
working 名称不再存在。

```text
Completed := ReadyToPublish && Published
OutputSuccess := Completed
```

Finalize 成功或 validation 成功都不能单独设置 `OutputSuccess=true`。内部
`readyToPublish` 也不得向 UI 冒充最终输出成功。

资源 cleanup 和文件 cleanup 必须完全分离。worker、SinkWriter、SourceReader、COM、
converter、pool、FrameTap consumer、纹理及 D3D 引用在成功和失败时都安全释放；
文件是否保留由第 7 节的媒体提交事实决定。当前 `DeleteFailedSessionOutput` 不能
原样作用于 working 文件。此前成功 Session、非本 Session 文件和已存在 final
永远不在 cleanup 范围内。

### 6.3 路径事实所有权与版本化 ABI

三个路径事实都由 Native Session/`StopAndJoin` 拥有：Start 冻结 Working 和
PlannedFinal，worker 只写 Working，publish 成功提交 Published。Managed 不从扩展名
猜测路径、不自行推断 publish，只映射同一个 Native Snapshot。

P2.6A **必须版本化扩展现有 `XbRecordingSnapshot`**，不另建独立 publish/path
snapshot。原因是 recording state、三类路径、validation、publish 和 Completed
必须在同一把 Native Snapshot 锁下形成一致读；分成两个 API 会引入跨调用撕裂，
并产生重复事实表面。

扩展后的 Snapshot 至少包含：

- `WorkingPath`
- `PlannedFinalPath`
- `PublishedPath`
- `ValidationAttempted`
- `ValidationHResult`
- `PublishAttempted`
- `PublishHResult`
- `Published`

原单一 `OutputPath` 不再承载随生命周期变化的语义。实施时使用不兼容 ABI 主版本
升级，使旧 Native/Managed 组合在创建或首个 Snapshot 调用前 fail-closed；同步扩展
ABI layout 的 recording snapshot size 事实。Native/C# 继续明确 x64、Pack=8、
UTF-16、总 Size 和每个新增字段 Offset，并增加双侧静态/运行时断言、P/Invoke
编组测试和版本不匹配负向测试。具体版本号和最终 Size 由实际布局计算后锁定，
不得手算后让实现迁就文档。

Managed 还必须把 `RecordingFailure` 与
`ControlPlaneSnapshotUnavailable` 分开。Interop/Snapshot 瞬时读取失败时保留最后
已知 Native recording 事实并标记控制面不可用，不得自行把底层状态改写为
`Failed`。特别是 publish 已成功后，Managed 读取失败不能倒写 Native 成功事实；
Close 在底层事实未知时仍应 fail-safe 地尝试同一正式 Stop 路径。
`RecordingFailure` 只能来自成功读取到的 Native `State=Failed` 事实；控制面错误
是读取状态，不是第二套 recording state。

## 7. 文件发布与失败保留规则

文件 cleanup 必须依赖 Session 所有权和“媒体提交是否开始”的确定事实，不能根据
文件大小猜测：

| 分类 | 文件处理 | 必需事实 |
| --- | --- | --- |
| A. 未取得 working 所有权/没有 working | 不删除任何路径 | owner=false 或路径从未创建 |
| B. Start 部分失败的纯启动垃圾 | 允许删除并记录 cleanup 结果 | 本 Session 独占所有；从未调用 WriteSample；媒体内容提交从未开始；仅 0-byte/header-only 启动垃圾 |
| C. 任意 WriteSample 已尝试 | working 保留 | `writeSampleAttempted=true`，无论调用成功与否 |
| D. Finalize 失败 | working 保留 | Finalize HRESULT 失败 |
| E. Validation 失败 | working 保留 | Validation HRESULT 失败 |
| F. publish 冲突/失败 | working 保留；final 原样不动 | publish HRESULT 失败 |
| G. Stop/Close/join/worker 异常 | 媒体写入已开始或事实 UNKNOWN 时保留 | 不确定性一律归入保留 |
| H. 崩溃/unknown/未来 manifest 关联文件 | 默认保留 | 未经用户确认不删除 |
| I. publish 成功 | 永不进入失败文件 cleanup；final 不删除 | `Published=true` |

仅凭“文件大小=0”不足以删除。允许删除启动垃圾必须同时证明 Session 所有权和
媒体写入从未开始。原始录制、Finalize、validation、publish 和 cleanup 错误分别
保存，cleanup 错误不得覆盖主失败。

### 7.1 两个正式崩溃提交窗口

**窗口 A：Finalize/validation 成功，但 publish 前崩溃。**

- `WorkingPath` 保留，`PublishedPath` 为空；
- 这是高价值 `recoverable-candidate`；
- P2.6A 不承诺自动恢复或自动发布；
- P2.6C 未来必须重新验证，而不是仅凭旧内存事实。

**窗口 B：原子 move 成功，但 Snapshot/未来 manifest 更新前崩溃。**

- final 已经是不可否认的文件系统事实，working 名称已经消失；
- 不能把 final 当成不存在，更不能删除；
- P2.6B/C 必须支持 `published-needs-reconciliation`；
- reconciliation 对账 manifest 和磁盘：PlannedFinalPath 存在且 WorkingPath 缺失
  时重新验证，再更新跨进程事实；不自动删除，也不单凭 manifest 宣判文件不存在。

### 7.2 UI 路径规则

- Starting/Recording：可展示保存计划，但 `PlannedFinalPath` 不是可打开文件。
- Failed：Open Video 禁用；若 `WorkingPath` 实际存在，未来最小行为可允许
  Open Folder 定位恢复素材，但不得把 working 当最终视频播放。
- Completed：Open Video/Open Folder 只使用 `PublishedPath`。
- Completed 后用户或外部程序删除 final，不倒改历史 Completed；UI 只根据当前
  文件存在性禁用打开按钮。
- P2.6A 只做上述事实所需的最小 UI 接线，不扩大正式视觉或恢复 UI。

未来“用户主动删除恢复材料”应由独立的 Recovery UI/服务通过 manifest 所有权
执行，并要求明确确认。本轮和 P2.6A 都不实现自动保留期限或删除按钮。

## 8. 最小 Session manifest 设计

跨进程恢复需要 manifest；运行时 `RecordingSnapshot` 不够。Snapshot 是线程安全的
当前进程事实，进程终止即消失；Recovery manifest 是最小、可持久的恢复决策事实。
二者必须保持为不同对象。

建议每个 Session 使用相邻 JSON，例如 `<SessionId>.session.json`，最小字段为：

```json
{
  "schemaVersion": 1,
  "sessionId": "GUID",
  "writerStrategy": "mf-sinkwriter-standard-mp4-v1",
  "workingPath": "absolute path",
  "plannedFinalPath": "absolute path",
  "publishedPath": "",
  "state": "recording|finalizing|validated|published|published-needs-reconciliation|failed|interrupted",
  "startedAtUtc": "ISO-8601",
  "lastUpdatedAtUtc": "ISO-8601",
  "finalize": { "attempted": false, "hresult": null },
  "validation": { "attempted": false, "hresult": null, "mode": null },
  "publish": { "attempted": false, "hresult": null },
  "failure": { "stage": null, "hresult": null }
}
```

manifest 持久化最后已知事实，但不是文件系统真值的替代物；启动 reconciliation
必须把三类路径与实际目录对账。尤其是 planned final 存在而 working 缺失时，不能
因 manifest 尚未写入 Published 就删除或忽略 final，而应重新验证并归类。

不写入帧级日志、内存/句柄统计、完整 RecordingSnapshot 或大体积诊断。manifest
更新采用同目录临时文件、flush、解析校验、无覆盖原子创建/替换；首次创建与后续
更新分别定义清楚。Windows 断电耐久性不能仅凭“rename 原子”推断，必须做定向
故障测试。元数据只在状态边界更新，不按帧或每秒写盘，避免影响正常录制性能。

## 9. 崩溃恢复候选比较

| 候选 | 对当前架构的改动 | 能解决什么 | 不能直接保证什么 | 建议 |
| --- | --- | --- | --- | --- |
| A. 普通 MP4 + working 名 | 最小；沿用现有 SinkWriter | 防止未验证文件冒充 final；保留失败素材 | 未 Finalize 崩溃文件可播放/可恢复 | P2.6A 立即采用，但口径仅为安全发布与保留 |
| B. fragmented MP4（`MFCreateFMPEG4MediaSink`） | 需要隔离验证新的 Media Sink/Byte Stream 与现有编码输入、硬件路径和 Stop 集成 | 理论上可缩小未完成容器的不可用窗口 | 本机兼容性、播放器支持、时长/索引、突然终止后的可读片段 | P2.6D 首选 Spike；通过前不锁定产品方案 |
| C. 分段/chunk 普通 MP4 | 周期性 Finalize 多个独立段并维护 manifest，改动明显 | 将最坏损失限制在最后未完成段 | 连续时间线、GOP、段合并、用户单文件体验和性能 | 若 fMP4 不满足再评估；不能混入第一刀 |
| D. 其他容器/外部 remux | 可能引入新容器、库或后处理依赖 | 某些容器更耐崩溃，或可事后重封装 | 与当前 MF/H.264、部署、许可和产品兼容性 | 仅在 A/B/C 证据不足时立项，不在当前范围 |

**现在不需要改变 MP4 容器策略。** 第一刀先建立不会误报成功、不会误删素材的
文件生命周期。真正的崩溃可播放能力必须由 P2.6D 独立验证后决定；如果 fMP4
Spike 成功，再评审是否替换 P2.6A 内部 writer strategy，而不是推翻 Controller。

## 10. 磁盘空间与无限时长原则

正式产品不设置 30 分钟、1 小时或 2 小时的人为录制上限。安全设计应基于容量
事实和受控 Stop：

1. Start 前读取 working 所在卷的可用空间；无法取得可信事实时 fail-safe 拒绝
   Start，并给出真实错误。
2. 基于当前码率、容器开销和 Finalize/publish 需要保留安全余量；阈值必须通过
   测试和产品决定，不在本轮拍脑袋指定。
3. 录制中低频监测空间，避免按帧查询。到预警阈值仅提示；到临界阈值通过正式
   RecordingController 发起 single-flight 安全 Stop。
4. 若 WriteSample/Finalize 已因空间失败，保留 working 和错误事实，不宣告成功。
5. 同目录 rename 通常不复制视频数据，但 manifest 更新和文件系统元数据仍需要
   余量；不能把 publish 当成“零空间需求”。
6. 任何空间事实 `UNKNOWN` 都不能解释为“空间足够”。

## 11. 生命周期与安全不变量

1. 未通过 Finalize、validation 和 publish 的文件不得冒充最终成功视频。
2. Finalize 失败不得删除 working 素材。
3. Validation 失败不得删除 working 素材。
4. Publish 失败不得删除 working 素材。
5. 原始录制错误、validation 错误、publish 错误和 cleanup 错误必须分开。
6. 正常 Stop 只能 Finalize 一次。
7. Recovery 不得创建第二套 RecordingController、Preview、FrameTap 或 Encoder。
8. 启动扫描不得自动删除 `unknown` 文件。
9. 恢复失败不得覆盖或改写原 working 文件；尝试输出必须使用新路径。
10. 用户未明确确认前，不主动删除恢复材料。
11. Session 元数据只在状态边界更新，不能明显拖慢正常录制。
12. 不通过限制录制时长解决空间与安全问题。
13. final 冲突必须失败，禁止静默覆盖。
14. publish 必须发生在 writer、SourceReader、FrameTap consumer、纹理和 worker
    全部释放且 join 完成后。
15. Failed 或 UNKNOWN 不能被 UI 的“打开视频”当作成功输出。
16. `PublishedPath` 在 publish 成功前必须为空。
17. `PlannedFinalPath` 不能冒充已发布文件。
18. `OutputSuccess` 只能由 `Completed` 派生。
19. `Completed` 必须同时满足 `ReadyToPublish` 和 `Published`。
20. publish 成功事实不可被后续 Managed/interop/Snapshot 读取失败倒写。
21. 文件 cleanup 必须基于 Session 所有权和媒体提交事实，不能根据文件大小猜测。
22. move 成功但 Snapshot/manifest 未更新是正式恢复窗口，不能否认 final。
23. working exclusive/no-overwrite 必须有实现和故障测试证据。
24. manifest 必须与文件系统对账，不可凌驾于磁盘事实。
25. Native Snapshot 读取失败是 `ControlPlaneSnapshotUnavailable`，不是由 Managed
    伪造的 `RecordingFailure`。

## 13. 明确非目标

本计划不设计或实现音频、Pause/Resume、后台录制、摄像头、60 FPS 选项、正式
视觉 UI、云备份、自动上传、视频编辑或智能导演，也不处理未合并热键桥分支。

## 14. 回滚边界

- P2.6A 应作为独立功能分支和独立提交，仅触及路径/发布所有权及其定向测试。
- 除版本化 Recording Snapshot 和最小 Managed 映射外，不改编码格式、码率、
  时间戳、FrameTap、OutputCanvas 或 Start/Stop Controller 语义。
- 在 P2.6A 门禁完全通过前，不删除当前直接写最终名实现；切换应集中且可整提交
  回退。
- 一旦启用安全发布，路径初始化失败必须拒绝录制，不能静默回退到直接写 final。
- P2.6B/C/D/E 各自独立提交；回退后不得让新 manifest 被旧版本自动删除。
- 不迁移、移动或清理现有 P2.4/P2.5 MP4；历史文件不自动纳入恢复扫描。

## 15. 合理停止线

出现以下任一情况时，停止 P2.6A 并重新审计，不扩大重构：

- working 与 final 无法保证同卷且发布会退化为复制；
- publish 必须在 worker/文件句柄仍活动时发生；
- 保留 working 会破坏 `StopAndJoin` single-flight 或 Preview Close；
- 无法在不覆盖 final 的情况下实现明确、可测的发布；
- 需要改变 H.264/MP4、时间戳或 Encoder 参数才能完成安全发布；
- 无法让版本化扩展后的单一 Recording Snapshot 原子表达三类路径和 publish 事实；
- 性能测试显示状态边界元数据写盘影响正常录制。

P2.6A 到此停止：working → Finalize → validate → Native publish、失败保留、
版本化真实路径/publish Snapshot，以及必要的最小 Managed/UI 映射。它不引入
manifest、启动扫描、自动 reconciliation、容器恢复或恢复 UI。达标线是“正常结果
只在验证后发布，文件 cleanup 有媒体事实，且旧的 Controller/Finalize/资源不变量
保持成立”。它不是“崩溃录像已经可播放”。

### 15.1 P2.6A 开工契约速查

1. Native Session 冻结/拥有 Working 和 PlannedFinal；Native `StopAndJoin` 只在
   move 成功后拥有/设置 Published；Managed 只映射。
2. `Completed := ReadyToPublish && Published`，`OutputSuccess := Completed`。
3. 唯一 publish 提交点是 worker join 后、Native `StopAndJoin` 内的一次
   `MoveFileExW(..., MOVEFILE_WRITE_THROUGH)`。
4. publish 前崩溃留下高价值 working candidate；move 后状态更新前崩溃可能已经
   留下 final，未来必须 reconciliation，不能否认磁盘事实。
5. WriteSample 已尝试、Finalize/validation/publish 失败或媒体事实 UNKNOWN 时，
   working 绝不能删除。
6. 只有本 Session 独占拥有、且能证明媒体提交从未开始的启动垃圾允许删除；
   仅凭 0-byte 不足以删除。
7. ABI 必须扩展，因为三类路径和 validation/publish/Completed 必须与 recording
   state 在同一 Native Snapshot 锁下原子读取，不能靠 Managed 推断或双 API 拼接。
8. P2.6A 在真实路径/publish Snapshot 和最小 UI 映射结束；manifest、扫描、
   reconciliation、可播放恢复和磁盘阈值分别留给 B/C/D/E。

## 16. 需要小g/小白决定的问题

1. **产品承诺口径：** P2.6 首先发布“安全发布 + 未完成素材保留/识别”，还是必须
   等 fMP4/分段实证后再对外称为“崩溃恢复”？建议采用前者并明确边界。
2. **恢复材料位置与可见性：** working/manifest 放在最终视频同目录直接可见，
   还是放在该目录下的受管恢复子目录？两者都应保持同卷；建议受管子目录，UI
   后续提供明确入口。
3. **磁盘策略：** Start 拒绝阈值、预警阈值、临界安全 Stop 预留，以及空间事实
   不可用时的提示文案。不得用录制时长上限代替这些决定。
4. **保留策略：** 未完成/unknown 材料默认永久保留到用户确认，还是在未来 UI
   提供按 Session 清理？建议本阶段默认不自动删除。
