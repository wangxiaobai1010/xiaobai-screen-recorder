# P2.5A Native Recording Control

## Stage status

P2.5A establishes the native recording-control baseline. It completes the
active-Preview recording loop and its native facts, but does not make P2.4 a
formal final freeze, does not complete P2.6 safe-save/recovery, and does not
replace the outstanding 60-minute final integration gate.

The preceding P2.4 60-minute gate remains
`BLOCKED-UNCONFIRMED-CLOSE`: P2.5A proves focused start/stop/finalize/close
behavior, not a long-duration end-to-end product sign-off.

## Goal and non-goals

The goal is an active Preview-local native loop:

```text
StartRecording -> encode OutputCanvas frames -> Stop/Finalize
               -> terminal Snapshot -> resources released
```

Preview remains active after a normal recording Stop, and the same Preview can
start a second independent Session. This stage deliberately does not add a
Managed RecordingController, UI, audio, pause/resume, camera, `.partial.mp4`,
atomic publication, crash recovery, a cleanup service, or 30/60-minute runs.
Those concerns remain outside P2.5A; the next implementation phase is P2.5B
Managed RecordingController and minimal UI.

## Native API and Snapshot facts

P2.5A exposes only the required native operations:

- `XbPreview_StartRecording`
- `XbPreview_StopRecording`
- `XbPreview_GetRecordingSnapshot`

The Snapshot state set is `Idle`, `Starting`, `Recording`, `Stopping`,
`Completed`, and `Failed`. It is protected by the native Snapshot mutex and
is the fact source for state, session ID, real start UTC time, elapsed encoded
PTS time, output path, error text, finalization facts, output success, and
resource residual count.

API version is `0x00030001`. Native and Managed `XbRecordingSnapshot` are both
1272 bytes. The layout asserts the cleanup fields at offsets 60, 64, and 68:

- `outputCleanupAttempted`
- `outputCleanupSucceeded`
- `outputCleanupHResult`

`failureHResult` is the original recording/start/finalize/validation failure;
it is independent from `outputCleanupHResult`. Thus a cleanup failure cannot
overwrite the original reason for the failed recording.

## Lifecycle and terminal ownership

The existing active Preview remains the sole source of OutputCanvas frames.
There is no second Preview, capture, Canvas, FrameTap, or encoder pipeline.
The Preview Renderer owns the `VideoEncoderConsumer`; the consumer registers
the encoder as the sole destructive FrameTap consumer for a Session.

The worker performs encoding, sink/pool/converter shutdown, FrameTap stop and
unregistration, D3D release, and writes a fixed-storage `WorkerOutcome` before
exiting. `WorkerOutcome` records output ownership and a fixed output path,
fixed `FailureStage`, HRESULTs, Finalize count, submitted-frame count, and
resource-residual facts without depending on dynamically allocated diagnostic
text.

`StopAndJoin` is the single-flight terminal owner shared by explicit
`StopRecording` and Preview Close. It signals stop, joins the worker, then
examines `WorkerOutcome`. Only after join and worker resource release does it
delete a failed output and publish final `Completed` or `Failed` Snapshot.
Stop returns only after the final Snapshot is visible on the normal terminal
path. Repeated Stop calls cannot finalize twice; `FinalizeCount` comes from
the real worker Finalize call.

## Failed output ownership

Each Session reserves its target using Windows `CREATE_NEW`; ownership becomes
true only for the file that this Session created. A failed Session can delete
only that owned path. Successful output is never sent to the cleanup path, and
a new Session resets its path and ownership, so it cannot remove a previous
Session's successful file.

Failed-output cleanup runs only after worker join. If deletion succeeds, the
Snapshot remains `Failed`, preserves its original `failureHResult`, and reports
cleanup `S_OK`. If deletion fails, `OutputSuccess` remains zero and the real
delete HRESULT is separately exposed in `outputCleanupHResult`.

## Exception boundaries

The encoder worker is split into an internally throwing implementation and a
`ThreadMain noexcept` entry boundary. That entry catches `std::bad_alloc`,
`std::exception`, and unknown exceptions, converts them to fixed
FailureStage/HRESULT facts, and still drives worker cleanup.

The C ABI exports for Preview Stop, StartRecording, StopRecording, and
GetRecordingSnapshot likewise catch all C++ exceptions. Internal functions
retain `noexcept` only where they can uphold it; configuration/string/mutex
paths that can throw propagate to the designated boundary. An exception cannot
cross the ABI or terminate the process while claiming successful output.

## Focused evidence

The directed native integration test uses the formal C API with a real active
Preview and validates:

- Idle/Starting/Recording/Stopping/Completed transition and PTS elapsed-time
  monotonicity.
- Duplicate Start rejection without replacing the current Session.
- Concurrent duplicate Stop and Preview Close/StopRecording races with exactly
  one real Finalize.
- Stop leaves Preview Running; two Sessions in one Preview have distinct paths.
- Successful MP4 output passes SourceReader quick validation and released-file
  handle checks.
- Unsupported failure injected after an owned file exists: post-join deletion
  succeeds, `failureHResult` is preserved, and all residuals are zero.
- Real deletion failure using a Windows sharing handle without
  `FILE_SHARE_DELETE`: primary and cleanup HRESULTs remain separate and
  `OutputSuccess` remains zero.
- Worker exception after output reservation: process stays alive, Stop returns
  NativeFailure, the failed output is cleaned, and residuals are zero.
- C ABI-boundary exception: the formal export returns NativeFailure and
  publishes a Failed Snapshot with fixed failure facts.

The focused Close scenarios also read the final Snapshot after Preview Stop and
race real threads calling `XbPreview_StopRecording` and `XbPreview_Stop`.
They verify no deadlock, use-after-free, duplicate Finalize, FrameTap/encoder
residual, open file handle, or background recording remains.

## Remaining 60-minute gate

P2.5A does not prove prolonged recording behavior. Before final product
approval, the 60-minute gate still needs to prove sustained active Preview and
recording behavior, A/V scope once audio is introduced, absence of progressive
memory/GPU/handle leaks, output integrity over duration, close behavior under
long-running load, and final safe-save/recovery semantics introduced by P2.6.
