# P2.5B Managed RecordingController and Minimal UI

## Stage status

P2.5A and P2.5B together establish the minimum RecordingController product
loop. P2.5A owns the native active-Preview recording facts; P2.5B adds the
Managed controller and a deliberately small development UI over those facts.

This is not a P2.4 final formal freeze. The deferred P2.4 60-minute final
integration gate remains unexecuted. P2.6 safe-save and recovery are also not
part of this stage.

## Goal and non-goals

The goal is the user-visible loop inside an already active Preview:

```text
Start -> Recording -> Stop -> Finalize -> Completed or Failed
      -> playable MP4 -> Preview remains active -> next Session
```

P2.5B does not add audio, pause/resume, tray or floating controls, a formal
home page, user-configurable output folders, 30/60 FPS options, `.partial.mp4`,
atomic publication, crash recovery, or long-duration 30/60-minute validation.

## Native facts and Managed state

P2.5A remains the only lower-level truth source:

- `XbPreview_StartRecording`
- `XbPreview_StopRecording`
- `XbPreview_GetRecordingSnapshot`

`RecordingController` is the sole Managed Start/Stop entry point. It maps the
native Snapshot directly to `Idle`, `Starting`, `Recording`, `Stopping`,
`Completed`, and `Failed`. The Managed snapshot is a locked cache of native
facts, not a second encoder, timing, frame, or resource state machine.

The Snapshot supplies the Session ID, start UTC, elapsed encoded PTS duration,
output path, error text, Finalize facts, failure HRESULT, output-cleanup facts,
and resource facts. The UI timer only refreshes this Snapshot; it cannot start,
stop, advance, or otherwise control the Encoder or the recording timeline.

Repeated Start and Stop calls share the in-progress Managed task. They do not
create a second native Session or a second Finalize. During window closing,
`StopForCloseAsync` waits for the native terminal Snapshot before the Preview
lifecycle is released.

## Minimal development UI and automatic save

The Host window exposes only the development controls needed for the loop:

- recording state;
- elapsed duration;
- complete output path with tooltip/copy visibility;
- Open Video;
- Open Folder.

Finalize completing the native recording makes the MP4 available immediately;
there is no separate Save action. A completed existing output enables Open
Video. A completed output with an existing parent directory enables Open Folder
so the user can inspect the location even if the file later disappears.

The current UI is not the intended final product wording. A later design stage
should use “保存到 / 更改位置” before recording and “已保存到 / 打开视频 /
打开文件夹” after recording. That visual and settings work is explicitly out of
scope here.

## Unicode Snapshot ABI correction

The P2.5A native Snapshot uses `wchar_t` fixed buffers. The Managed
`RecordingSnapshot` originally had correct Pack, Size, and field offsets but
did not declare `CharSet.Unicode`. The marshaler therefore treated the UTF-16
output path as ANSI at the P/Invoke boundary and observed only `E` from a path
beginning `E:\\小白录屏器\\...`.

Adding `CharSet.Unicode` preserves the native UTF-16 path byte-for-byte through
the Managed Snapshot and MainForm. The ABI remains API version `0x00030001`,
Pack 8, and 1272 bytes; the existing offset assertions alone were not enough
to prove correct fixed-string marshaling. End-to-end tests now use an actual
Chinese absolute path and compare Native, Managed, and UI values ordinally.

## Real MainForm test lifecycle correction

The original real-Form wiring test scheduled work from `Shown`, used nested
`Application.DoEvents`, and synchronously called `Close` from that reentrant
callback. That could overlap WinForms Handle creation and the asynchronous
MainForm close choreography, causing the intermittent CreateHandle/Dispose
exception observed from `MainForm.WndProc`.

The test now uses one STA thread and one `ApplicationContext` message loop.
It waits for a stable Handle before reading actual controls, uses asynchronous
condition waits rather than nested pumping, queues Close with `BeginInvoke`,
and waits for `FormClosed` and loop exit before detaching handlers and disposing
the Form. UI-thread exceptions are captured as test failures through the
WinForms thread-exception boundary rather than displayed as JIT dialogs.

Five consecutive real-MainForm runs, each with two real Sessions, passed with
distinct Session IDs and output paths. Every run exited cleanly with no
XbPreview, Managed.Tests, Encoder, corresponding dotnet test process, or test
window residual.

## User acceptance evidence

小白 verified the complete user loop in the formal Host executable:

- Start -> Recording -> Stop -> Completed;
- native PTS duration advanced correctly;
- MP4 was saved automatically and played normally;
- the complete Chinese output path and “已完成，可打开视频” text were shown;
- Open Video opened the current Session MP4;
- Open Folder located that MP4;
- two Sessions used distinct GUIDs and paths without overwriting each other;
- Preview stayed active after Stop.
