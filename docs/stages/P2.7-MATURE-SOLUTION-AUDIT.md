## 1. 当前根因

当前项目已经使用 `Direct3D11CaptureFramePool::CreateFreeThreaded`，不是 `Create`（`PreviewEngine.cpp:905-919`）。Native Preview worker 是 MTA（`PreviewEngine.cpp:476-493`）；`FrameArrived` 在 frame-pool worker 上执行 `TryGetNextFrame`，只把最新帧放进受 `frameMutex_` 保护的 single-frame slot，再唤醒独立 Preview worker（`PreviewEngine.cpp:1128-1178`）。这里不依赖 UI `DispatcherQueue`、WinForms timer 或 UI 消息泵。

真正停止下游的是 `PreviewEngine::ProcessPendingFrame` 的显式窗口门：当 `IsIconic(exclusionHwnd_)` 或 `!IsWindowVisible(exclusionHwnd_)` 时，代码立即 `Close` 当前 WGC frame、增加 dropped count 并返回（`PreviewEngine.cpp:1261-1267`）。因此帧没有到达 surface extraction、OutputCanvas 合成、`RenderFrameTap` 或 Encoder。

正常可见路径中，`PreviewRenderer::RenderFrame` 的顺序已经是：WGC texture GPU copy → OutputCanvas 合成与 Cursor → `RenderFrameTap::ObserveAndCopy`（`PreviewRenderer.cpp:222-281`）→ Preview back buffer draw → `Present(1, 0)`（`PreviewRenderer.cpp:283-321`）。所以正确切点是“只关闭 Preview presentation”，不是关闭整帧处理。

2026-08-08 的真实短复现进一步排除了其它候选：

| 阶段 | Capture | Present | Dropped / Recording PTS |
|---|---:|---:|---|
| 正常 | 约 60.7 FPS | 约 60.7 FPS | 0；PTS 正常前进 |
| 最小化约 3 秒 | 约 60.0 FPS，持续收帧 | 0 FPS | dropped 由 0 增至 181；PTS 约从 1.167 s 停到 4.433 s |
| 恢复 | 约 60 FPS | 恢复约 60 FPS | PTS 自动继续；最终完成 424 帧并成功发布 |

证据位于 `artifacts/p2.7-audit-runtime/p2.7-minimize-repro-20260808/`。结论是 **frame acquisition 正常，Preview visibility 门主动切断 OutputCanvas/FrameTap/Encoder**；不是 DispatcherQueue、compositor、timer 或 Encoder consumer 停摆。当前 `Present` 在最小化期间甚至没有被调用，故它不是这次冻结的直接触发点。

## 2. Windows 官方成熟方案

[Microsoft `CreateFreeThreaded` 文档](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframepool.createfreethreaded?view=winrt-26100)明确说明：该 API 去除 `DispatcherQueue` 依赖，并在 frame pool 内部 worker thread 触发 `FrameArrived`；最低为 Windows 10 1809 / build 17763、Universal API Contract v7。项目已经正确采用它，而且真实复现证明它在窗口最小化时仍约 60 FPS 收帧，因此无需替换或再包装 WGC。

兼容检查：

| 项目 | 结论 |
|---|---|
| Windows 最低版本 | `CreateFreeThreaded` 要求 1809；这是当前代码已存在的实际最低要求，推荐路线不再提高。当前机器 build `22631.2861` 满足。 |
| WinRT / C++ 用法 | 当前 C++/WinRT 静态调用、`IDirect3DDevice`、BGRA8、2 buffers 和 `SizeInt32` 参数均匹配官方签名。 |
| D3D device | FramePool、OutputCanvas、FrameTap 和 Encoder 继续复用同一 video-capable D3D11 device；不创建第二 device/context。 |
| FrameArrived thread | 回调只取帧、替换 single-frame slot 和通知；重合成仍在唯一 Preview worker，符合官方避免在 UI 线程做重工作的建议。 |
| COM apartment | FramePool 类型为 Agile / ThreadingModel.Both；Preview worker 已 `winrt::init_apartment(multi_threaded)`，Encoder worker 已 `CoInitializeEx(COINIT_MULTITHREADED)`。 |
| D3D 并发 | 当前 immediate context 已开启 multithread protection；微软文档确认该保护用于多线程共享 immediate context。推荐路线不改变线程或提交顺序。 |
| shutdown | 现有 `acceptingFrames_` + `CallbackGate::DeactivateAndWait` 先阻止并等完回调，再退订、关闭 session/pool，最后 shutdown renderer；保持不变。 |
| frame-pool recreate | 当前先关闭持有 pool buffer 的 frame，再在 Preview worker 调用 `Recreate`；符合[官方 Recreate 指南](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)，保持不变。 |
| OutputCanvas consumption | hidden/minimized 时继续既有 OutputCanvas 与 FrameTap 路径，只跳过 swap-chain back-buffer draw / `Present`。合成与 Encoder 输入合同不变。 |

微软的[录屏到视频示例](https://learn.microsoft.com/en-us/windows/uwp/audio-video-camera/screen-capture-video)同样用 `CreateFreeThreaded` 把 frame acquisition 与主线程分离，并用独立同步/消费循环编码。当前项目已经具备等价的成熟线程边界。

## 5. 不采用的路线及原因

- **A：直接采用 `CreateFreeThreaded`**：不作为施工方案，因为基线已采用，且运行证据证明它仍正常收帧；重复采用不能删除 `ProcessPendingFrame` 的主动丢帧门。
- **只删除 visibility guard、仍无条件 `Present`**：不安全。微软的 [`IDXGISwapChain::Present` 文档](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiswapchain-present)提醒 `Present` 可能等待消息泵线程；当前 swap chain 又是 flip-discard，不能把 `DXGI_STATUS_OCCLUDED` 当作可靠的最小化控制流。后台录制不应被无意义的 HWND presentation 反向节流。
- **最小化时 Stop/Recreate WGC，恢复时重启**：会引入捕获空窗、session/recreate/Stop 竞态并破坏连续 timestamp，且官方 free-threaded capture 本来没有停止。
- **另建 recording-only capture pipeline/device**：制造第二套 capture、几何、cursor、OutputCanvas 与 shutdown ownership，直接违反本阶段兼容门。
- **导入 Cap 或其它跨语言录制栈**：当前根因是一处本地 presentation 门，导入外部栈的风险和维护面远大于收益。
- **timer 补帧或 Encoder 重复帧**：绕开而不是修复断粮点，并会改变现有 timestamp/Encoder 合同。

## 6. 唯一推荐方案

**C：保持现有 capture，只解耦 Preview presentation。**

保留当前 `CreateFreeThreaded`、FrameArrived single-frame slot、唯一 Preview worker、OutputCanvas、RenderFrameTap 和 Encoder。每个有效 WGC frame 都继续完成 OutputCanvas 合成与 FrameTap；仅当 Preview HWND 可见且未最小化时才 draw swap-chain back buffer 并 `Present`。hidden/minimized 是 `presentation disabled`，不是 `capture disabled`。恢复时不重建 capture/session/device，下一帧直接恢复 Preview presentation。

这是一层很薄的 Native 内部 presentation gate，不是新 capture adapter，也不是后台录制架构重写。

## 7. 预计改动范围

   - presentation disabled 时跳过 preview back-buffer clear/draw 和 `Present`；恢复时复用现有 swap chain。

   - 复用现有正式 WGC/Recording C API 集成窗口，增加 minimize、hide、restore、hidden Stop 的短回归；不加产品 test hook。

## 8. 最小验证计划

1. 定向 Native 集成：正常录制 → minimize 2–3 秒 → restore；断言 Capture 与 recording PTS 持续前进、hidden 期间 Preview present 不增长、restore 后 present 恢复。
2. 同一入口执行 hide/show；证明与 minimize 相同，且 HWND/session/device 未重建。
3. hidden 状态 Stop：断言 Finalize/Publish 单次、`ResidualOutstanding=0`；随后 show，Preview 下一帧正常恢复，并可再完成一个短 Recording。
4. 活动录制时普通 Close：只跑一次短 close case，确认 Managed single-flight 和 Native `StopAndJoin` 次数不回退；不重跑 P2.6 crash matrix。
5. 运行现有定向 Native/Managed 回归、`git diff --check`；再做一次约 15 分钟 hidden background soak，检查 PTS、frames、内存、queue 和最终 MP4。无需先做 60 分钟长测才允许合入。
