# P2.6D-2B Actual After-Rename Crash + End-to-End Narrow Recovery

## 1. 阶段目标

本阶段只验证一个真实事故窗口：正式 Encoder 已成功把 Working 文件原子重命名到
PlannedFinalPath，但 Native Published/Completed 持久元数据尚未写入时，录制进程被真实
终止。随后必须由全新进程只依赖磁盘事实发现候选，并且只有显式用户动作才能通过正式
Narrow Reconciliation bridge 完成窄恢复。

阶段结论不表示任意损坏 MP4 都可修复，也不实现通用媒体 repair。

## 2. AfterRenameBeforePublishedMetadata 精确定义

精确顺序为：真实 Recording 与 WriteSample → Stop/Join → Finalize 成功 → SourceReader
Validation 成功 → worker 退出、录制资源释放且 residualOutstanding=0 → schema 2
ReadyToPublish 与 Working FILE_ID_INFO 持久化 → `MoveFileExW(Working,
PlannedFinalPath, MOVEFILE_WRITE_THROUGH)` 成功 → Working 严格不存在、Final 存在且身份
相同 → Published/Completed Manifest update 尚未开始 → barrier。

barrier 不靠 Sleep 猜测时机。

## 3. 为什么这是 A/B/C 恢复链的终极事故窗口

P2.6A 提供 Working/Final 隔离和安全 publish，P2.6B 提供跨进程 Manifest，P2.6C 提供
FILE_ID、owner、operation-time Guard、schema 3 NarrowReconciler、startup inspection 和显式
用户恢复入口。本窗口同时要求这些能力在真实进程死亡前后保持一致，是第一条贯通 A/B/C
全部事实层的真实事故链。

## 4. 精确 test-only barrier

复用既有 `VideoEncoderLifecycleTestHooks.publishMoveReached /
continueAfterPublishMove`。该 hook 仅在 `XBPREVIEW_NATIVE_TESTS` 编译条件下存在，并且只在
`PublishSessionOutput` 返回成功之后、published identity 捕获和
`PersistManifestPublished` 之前触发。正式 Native DLL 没有 named-event 等待、测试环境变量
或 crash API；产品默认路径零额外等待。

## 5. Kill 前事实

本轮真实 Session：`1E9C538A-A0BE-4940-9904-F91B1359C1E0`。Kill 前 Manifest 为 schema
2、ReadyToPublish、revision N=6；writeSampleAttempted/frameSubmitted 成立；FinalizeCount=1
且 HRESULT 成功；Validation attempted/passed 且 HRESULT 成功；workerExited、
recordingResourcesReleased 成立；residualOutstanding=0；Working persistent volume/file ID 已
持久化。

文件系统事实为 Working absent、Final regular/non-reparse、linkCount=1；Final 的 Volume
Identity + FILE_ID_128 与持久化 Working identity 完全一致。Owner 为 ActiveOwned。历史
publish fields 保持 attempted=false、published=false、hresult absent、publishedPath empty；
post-publish identity 与 reconciliation facts 也尚未成立。

## 6. 真实 TerminateProcess

Parent 通过 `CreateProcessW(CREATE_SUSPENDED)` 创建 Child，先核对 process handle、PID、
helper mode、nonce、parent PID、完整 image path，再恢复执行。到达精确 barrier 后，仅对这
个 Parent 持有的 Child handle 调用 `TerminateProcess`，退出码为 `0xD1260001`，Child PID
为 19152。该退出不是 Stop、Close、Finalize、throw 或正常 return。

Kill FILETIME UTC 100ns 值：`134306438566524459`。

## 7. Kill 后第一现场

未先做 recovery、Manifest 修改、媒体移动或 fixture cleanup。第一现场仍是 schema 2
ReadyToPublish revision 6，Manifest bytes 与 kill 前完全相同。Working 仍 absent，Final
仍存在；Final 的 SHA-256、size、FILE_ID、creation/last-write timestamp 均与 kill 前相同。

## 8. Owner 自动释放

Kill 前 owner probe 为 ActiveOwned。真实进程终止后，全新 Inspector 从内核 lease 事实
得到 InactiveLeaseReleased；owner rendezvous 文件存在不被误解释为 owner active。Recovery
Actor 的正式 Guard 成功证明 maintenance lease 已取得；bridge 返回后再次 probe 为
InactiveLeaseReleased。所有 helper 结束后无 owner 活句柄残留。

## 9. Fresh-process classification

第一阶段 Inspector 是全新 Native.Tests 进程，从零加载当前 Release Native DLL，仅依赖磁盘
持久事实。正式分类为 `PublishOutcomeUnprovenRetain`：Final exists、Working absent、identity
evidence exists，但历史 publish 结果不被推断。`deleteAllowed=false`，
`reconciliationAuthorized=false`；Scanner 本身始终只读且不授予 mutation capability。

## 10. Post-crash Final validation

真实 kill 后对 Final MP4 使用 Media Foundation SourceReader 做只读 quick validation：PASS。

## 11. 用户恢复候选映射

## 12. Explicit recovery action

Phase 1 Restart/Observe 结束后再次核对 Manifest 仍是 schema 2 revision 6，且候选映射没有
自动写入。Parent 明确记录 `P2.6D2B_USER_RECOVERY_ACTION` 后才创建新的 Recovery Actor，
等价于产品中的用户点击“尝试恢复”。

## 13. Recovery Actor 与正式 bridge

Recovery Actor 是全新的 `XbPreview.Managed.Tests.exe` 进程。它复用 Host 生产源码中的
`NativeNarrowRecoveryService` 和 `NativeMethods.XbPreview_ReconcileNarrowSessionV1`，输入正式
diagnostic directory、canonical SessionId 和 expected revision 6。没有由 Parent 调用 private
Manifest writer，也没有第二套 Reconciler。

Managed.Tests 当前把相同 Host 生产源链接到测试程序集，因此 Actor 不加载
`XbPreview.Host.dll`；provenance 如实记录 ManagedTests apphost/assembly 与 Native DLL。

## 14. Guard operation-time 链

正式 bridge 返回 GuardStatus=`EvidenceComplete`、CASStatus=`Succeeded`。因此真实执行了：
NarrowReconciler → maintenance lease → operation-time Manifest reload → expected revision →
Path Safety → held Final handle → persistent FILE_ID match → hard-link guard → Working absence →
CAS 前第二次 Working absence → source eligibility → immutable whitelist → single nowUtc →
expected-revision CAS。Scanner 的点时分类没有被当作授权。

## 15. Schema 3 mutation 结果

唯一写入为 schema 2/N=6 → schema 3/N+1=7，state=`ReconciledCompleted`。reconciliation kind 为
`FinalAtPlannedPathSamePersistentFileV1`，evidence kind 为
`MaintenanceLeaseCasHeldFinalIdentityV1`；sourceRevision=6；updatedAtUtc==reconciledAtUtc；
confirmedFinalPath==plannedFinalPath；originalPublishResultKnown=false。原路径、FILE_ID、Finalize、
Validation 和其他白名单外事实未改。

## 16. Historical truth 边界

虽然测试 Parent 知道 Child 曾真实成功执行 MoveFileExW，NarrowReconciler 只依据持久 FILE_ID
和当前文件系统事实。恢复后仍保持 publishAttempted=false、publish hresult absent、
published=false、publishedPath empty、postPublishIdentityVerification unattempted。没有伪造 Native
Published、Completed 或 OutputSuccess。

## 17. Media zero mutation

恢复前后 Final 的 SHA-256、size、Volume/FILE_ID、creation time、last-write time 全部相同：
SHA-256 `81470ada16419ee71f9d979b50a7a9074b9f49b5b481cc4cb7f2ac72127476aa`，
size 6054 bytes。Recovery Actor 没有 Move、Copy、Delete、rename、repair、truncate 或 touch
媒体。

## 18. Post-recovery fresh rescan

bridge 返回 Reconciled 后，启动另一个全新 Native Inspector 进程重新扫描磁盘。正式分类是
`ReconciledCompletedConsistent`，不是 `CompletedConsistent`；Manifest state 是
ReconciledCompleted revision 7，Owner InactiveLeaseReleased，两个 mutation authority 字段仍为
false。扫描前后 Manifest 与媒体均未变化。

## 19. 用户最终显示事实

只有在 post-recovery fresh scan 证实 `ReconciledCompletedConsistent` 后，另一个新的 Managed
进程才用正式 presentation mapping 和 confirmed SessionId 生成 Recovered 用户态（当前正式
等价文案为“录像已找回并确认保存”）。NarrowReconciler 的返回值本身没有提前触发成功显示。

## 20. 幂等验证

bytes、Manifest identity/timestamps 和 Final 的全部观察事实均相同。
