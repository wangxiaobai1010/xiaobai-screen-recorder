# P2.6A 安全发布骨架最终报告

## 1. 阶段状态与目标

**状态：P2.6A-FINAL-AUDIT-PASS / FREEZE-READY（未提交）。**

P2.6A 在已冻结的 P2.4 OutputCanvas 编码链和已通过的 P2.5
RecordingController 闭环之上，只改变录制文件的运行时生命周期：未验证素材写入
working 名称，只有完成 Finalize、SourceReader 验证、资源释放、worker join 和 Native
无覆盖发布后，才形成用户可见的最终 MP4 和 `Completed`。

本报告审查基线为 `main` / `1724870f339c4cb9956d5d703612facae1059afe`。
P2.6A 实现当前仍是该基线上的未提交受控差异；本轮没有修改生产代码、ABI、测试或
历史 P2.4/P2.5 报告，只新增本报告，等待独立冻结指令。

## 2. 设计原则

1. 文件名不是成功事实；只有 Native publish 成功才产生正式输出。
2. 路径、validation、publish、Completed 和资源事实必须在同一个版本化 Native
   `XbRecordingSnapshot` 下保持一致。
3. encoder worker 只负责编码、Finalize、验证、资源释放和固定 `WorkerOutcome`；
   文件发布由 join 后的 `StopAndJoin` 单点拥有。
4. 发布只允许同目录、无覆盖 rename，不允许复制回退、覆盖、自动换名或 Managed
   接管终态。
5. 已开始媒体提交的 working 文件默认保留；不确定性不得解释为可删除。
6. P2.5 的 single-flight Stop、FinalizeCount=1、Preview Close 和同 Preview 双
   Session 能力保持不变。

## 3. 实现内容

P2.6A 分为三个已完成切片：

- P2.6A-1：将 Recording Snapshot 升级为 ABI v4，加入三类路径和
  validation/publish 状态事实。
- P2.6A-2：正式 Recording Session 的 SinkWriter 从 `<SessionId>.mp4` 改为写入
  `<SessionId>.partial.mp4`；planned final 在 Start 时同时冻结。
- P2.6A-3：在 worker join 后执行 Native 无覆盖发布，切换 Completed 和
  OutputSuccess 语义，并把失败 cleanup 收紧为启动垃圾删除。

未改变 H.264/NV12、码率、PTS、OutputCanvas、FrameTap、Cursor、镜头、捕获链或
正式 RecordingController 的 Start/Stop 入口。

## 4. 生命周期模型

正式成功路径为：

```text
Start
  -> freeze WorkingPath and PlannedFinalPath
  -> CREATE_NEW reserves WorkingPath
  -> SinkWriter writes WorkingPath
  -> Stop
  -> Finalize exactly once
  -> QuickRuntimeValidation reads WorkingPath
  -> SinkWriter / validation reader / converter / pool shutdown
  -> FrameTap consumer unregisters; D3D references release
  -> worker stores WorkerOutcome and exits
  -> StopAndJoin completes join
  -> calculate ReadyToPublish
  -> MoveFileExW(WorkingPath, PlannedFinalPath, MOVEFILE_WRITE_THROUGH)
  -> Published / PublishedPath
  -> Completed / OutputSuccess
```

`ReadyToPublish` 只在以下事实同时成立时为真：worker 已退出且 join 完成；
Finalize 已尝试且 `FinalizeCount=1`；Finalize HRESULT 成功；Validation 已尝试且
HRESULT 成功；working 文件存在且非零；录制专属资源已释放；
`ResidualOutstanding=0`。

显式 Stop 和 Preview Close 仍复用同一个 `VideoEncoderConsumer::StopAndJoin`。
重复 Stop 读取同一个终态，不会再次 Finalize 或再次发布。

## 5. ABI 变化

- API version：`0x00040001`。
- Native/Managed Snapshot size：`2856` bytes。
- x64，`Pack=8`，Windows UTF-16；Managed 明确 `CharSet.Unicode`。
- Native `static_assert` 与 Managed `Marshal.OffsetOf` 锁定的新字段偏移：
  - `ReadyToPublish`：1272
  - `Published`：1276
  - `PublishAttempted`：1280
  - `PublishHResult`：1284
  - `ValidationAttempted`：1288
  - `ValidationHResult`：1292
  - `WorkingPath`：1296
  - `PlannedFinalPath`：1816
  - `PublishedPath`：2336
- ABI layout 继续公开 `recordingSnapshotSize`；v3 major 和旧 1272-byte Snapshot
  均 fail-closed 为 `AbiMismatch`。
- C ABI Snapshot、Native fixed buffer、P/Invoke 和 Managed Snapshot 使用同一布局；
  中文路径 round-trip 测试按字符比较。

`OutputPath` 被保留以维持 P2.5 ABI 字段位置。正式 Recording 中它当前镜像
`WorkingPath` 的值，但只是兼容字段，不是 P2.6A 权威路径，也不得用于判断发布或
成功。新代码必须使用三类显式路径事实。

## 6. Working / Published 路径模型

| 事实 | 形式 | 成立时间 | 权威用途 |
| --- | --- | --- | --- |
| `WorkingPath` | `<SessionId>.partial.mp4` | Start 时冻结 | SinkWriter 写入、Validation、失败材料定位 |
| `PlannedFinalPath` | `<SessionId>.mp4` | Start 时冻结 | 计划发布目标；publish 前不代表成功文件 |
| `PublishedPath` | 初始为空；成功后等于 PlannedFinal | Native move 成功后 | Completed、Open Video、Open Folder、LongRun MP4 验证 |

working 和 planned final 由一次配置函数生成，位于同一输出目录。Working 通过
`CREATE_NEW` 建立本 Session 所有权；final 不创建占位文件。发布调用只有：

```text
MoveFileExW(WorkingPath, PlannedFinalPath, MOVEFILE_WRITE_THROUGH)
```

没有 `MOVEFILE_REPLACE_EXISTING`、`MOVEFILE_COPY_ALLOWED`、copy+delete fallback
或冲突后自动换名。final 已存在时保留原 final 和 working，并发布真实 Win32
HRESULT 映射。

## 7. Completed 语义

正式定义为：

```text
Completed := ReadyToPublish && Published
OutputSuccess := Completed
```

Finalize 或 Validation 单独成功不能设置 OutputSuccess。Publish 成功时
`PublishAttempted=true`、`PublishHResult=S_OK`、`Published=true`，且
`PublishedPath=PlannedFinalPath`；失败时状态为 `Failed`、OutputSuccess 为 false、
PublishedPath 为空并保留 working。

Managed `RecordingController` 只映射 Native 事实。Snapshot 读取异常保留最后已知
事实，不把已发布的 Native 成功改写为 Managed `Failed`。MainForm 仅在
Completed、Ready、Published、OutputSuccess 和真实路径条件成立时开放成功文件，
并使用 `PublishedPath` 打开视频或定位文件夹。LongRun 的成功 Gate 和 summary MP4
事实也统一使用 `PublishedPath`。

## 8. Cleanup 策略

文件 cleanup 发生在 worker join 后，并与 encoder 资源 cleanup 分离。

允许删除的唯一类别是本 Session 通过 `CREATE_NEW` 拥有、从未尝试
`WriteSample`、提交帧数为 0、没有 Validation，且明确落在启动失败阶段的 working
垃圾。删除结果写入独立 cleanup 字段，不覆盖主失败 HRESULT。

以下情况默认保留 working：

- 任意 `WriteSample` 已尝试；
- Finalize 失败；
- Validation 失败；
- publish 冲突或其他 publish 失败；
- 已开始媒体提交的 Stop/Close/worker 异常；
- 媒体提交事实不确定；
- publish 已成功（final 永不进入失败 cleanup）。

新 Session 只持有自己的 working 路径，不会删除旧 Session 的 final 或其他现有
文件。

## 10. 已知限制

- 普通 MP4 在未 Finalize 的进程崩溃或断电后不保证可播放、可修复或完整。
- `MOVEFILE_WRITE_THROUGH` 是同步完成 move 的请求，不等价于已证明断电绝对耐久。
- move 已成功但进程在持久状态更新前崩溃时，磁盘可能只有 final；P2.6A 不做启动
  reconciliation，不能否认该磁盘事实。
- Snapshot 路径仍是 260 个 UTF-16 code unit 的固定缓冲；超长路径能力未在本阶段
  证明。
- QuickRuntimeValidation 是有界 SourceReader 验证，不替代整段逐帧解码或新的
  长时稳定性证明。
- P2.6A 不提供跨进程 Session 事实，也不对历史 `.mp4` 或任意目录执行扫描/清理。

## 11. P2.6B / C / D / E 边界

- **P2.6B**：独立实现最小、版本化、原子持久化的 Session manifest；不修改本轮
  三路径和 Completed 定义。
- **P2.6C**：只扫描受管目录和合法 manifest，做未完成 Session 分类与文件系统
  reconciliation；unknown 默认保留，不自动删除。
- **P2.6D**：隔离验证普通 MP4、fragmented MP4 或分段方案的崩溃恢复能力；没有
  实证前不得承诺崩溃后可播放。
- **P2.6E**：磁盘空间、权限、长路径和低空间安全 Stop；仍必须复用正式
  RecordingController。

本阶段明确不包含 Session manifest、启动扫描、reconciliation、真正崩溃恢复、
fragmented MP4、分段录制、磁盘阈值或恢复 UI。

## 12. 冻结结论

最终只读审查确认：三路径语义、Native publish 所有权、join 后发布顺序、
Completed/OutputSuccess 定义、失败保留、启动垃圾删除、ABI/Unicode 映射及
Managed/LongRun 成功消费者均一致；未发现假成功、覆盖 final、误删已写素材、重复
Finalize 或资源残留方面的阻断问题。

因此当前实现达到 **P2.6A-FREEZE-READY**。本结论只代表安全发布骨架成立，不代表
manifest、启动恢复扫描、崩溃录像可播放、磁盘安全策略或完整 P2.6 已完成。等待
下一步独立 Git 冻结指令；本轮不 commit、tag 或 push，也不开始 P2.6B。
