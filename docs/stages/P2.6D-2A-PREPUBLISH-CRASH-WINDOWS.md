## 1. Stage goal

P2.6D-2A extends the frozen D1 cross-process Crash Harness with two actual
pre-publish process-termination windows:

1. `StoppingBeforeFinalize`;
2. `ReadyToPublishBeforeRename`.

Each case uses a distinct recording Child created by the Parent, an exact
test-only lifecycle checkpoint, `TerminateProcess` on the Parent-owned process
handle, and a distinct fresh Restart Inspector process. This stage validates
persistent facts and conservative retention; it does not repair or publish
media.

## 2. Why D2 is split into D2A and D2B

D2A covers the two windows where the working path still exists and the final
path has not been created. The third and materially different window,
`AfterRenameBeforePublishedMetadata`, has a final file but stale
`ReadyToPublish` metadata. That case is intentionally reserved for P2.6D-2B so
this stage cannot accidentally manufacture or authorize a reconciliation.

## 3. StoppingBeforeFinalize exact definition

The Child first enters real Recording and persists first-media facts. Its real
Stop path then persists Manifest `Stopping`. Separately, the worker reaches a
test-only barrier immediately before the transition to Finalizing, before
`finalizeCount` is incremented and before `MfH264SinkWriterSession::Finalize`
is called. The Parent waits for both events before accepting the checkpoint.

This is an event-established ordering contract, not a sleep-based timing
guess:

`PersistManifestStopping -> StoppingPersisted event`

and

`worker Stopping -> BeforeFinalize event -> blocked -> Finalize`

The Parent kills only after both facts are true.

## 7. ReadyToPublishBeforeRename exact definition

The existing test-only Ready barrier is called only after the real worker has
exited and joined, the working file has passed pre-publish validation, and
`PersistManifestReady` has committed the Ready facts. The barrier executes
before `PublishSessionOutput` and therefore before `MoveFileExW`.

The precise order is:

`Finalize -> Validation -> release resources -> worker exit -> Join ->`
`PersistManifestReady -> Ready barrier -> MoveFileExW`.

The Child is blocked at the Ready barrier and the Parent verifies the final
path is absent before termination. No timing luck is involved.
