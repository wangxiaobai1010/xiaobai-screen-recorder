# P2.6C-3b Narrow Reconciliation Mutation Contract

## 1. 阶段目标

本合同定义 P2.6C 第一次允许修改历史 Session Manifest 前的最后一道设计门禁。它只针对
P2.6A durable publish crash window：录制、Finalize、Validation、worker 退出和资源释放都
已成功，`ReadyToPublish` 事实与 Working 持久文件身份已落盘，当前同一个底层媒体对象位于
`PlannedFinalPath`，但进程没有持久化后续 publish metadata。

本合同冻结以下边界：

- 唯一 source eligibility；
- 唯一 target semantic state；
- 历史动作事实与当前可证明文件事实的分离；
- mutation whitelist 与逐字段 immutable contract；
- 3a-3 Guard、expected-revision CAS、幂等性和结果模型；
- 实施前必须通过的测试矩阵。

本轮只交付设计，不实现生产 reconciliation。

## 2. 非目标

本合同不授权：

- startup 接线、Scanner 自动写回或 UI；
- `Recording`/`Stopping` 中断恢复；
- Finalize、Validation 或显式 Publish failure 恢复；
- Working 文件 republish、MP4 repair、copy、move、rename、delete 或 cleanup；
- Manifest Missing/Corrupt、schema 1、future schema、Unknown、无 identity、无 owner evidence；
- hard link、reparse、unsafe path、inaccessible 或 I/O 不确定场景；
- fragmented MP4、音频、磁盘策略或 P2.6D。

## 3. Source Eligibility

第一版**只允许**一个 source：`schemaVersion == 2` 且
`state == ReadyToPublish`。`state` 字符串本身不足以授权；Guard 锁内重读的 current
Manifest 必须同时满足以下完整谓词：

1. canonical SessionId、writer strategy、revision、UTF-16 路径及 schema 2 结构均有效；
2. `workingFileOwnedBySession=true`；
3. `writeSampleAttempted=true` 且 `frameSubmitted=true`；
4. `workerExited=true`；
5. `recordingResourcesReleased=true` 且 `residualOutstanding=0`；
6. Finalize：`attempted=true`、`count=1`、`hresult=S_OK`；
7. Validation：`attempted=true`、`passed=true`、`hresult=S_OK`；
8. Working identity：`attempted=true`、`captured=true`、`hresult=S_OK`，且 volume identity
   与 `FILE_ID_128` 为 canonical value；
9. `workingPath` 与 `plannedFinalPath` 是本 Session 在冻结 OutputRoot 下的精确路径；
10. `publish.attempted=false`、`publish.published=false`、`publish.hresult=null`；
11. `publishedPath` 为空；
12. post-publish identity verification 未尝试、未匹配且 HRESULT 为空；
13. `errorCategory=None`、`errorCode=null`、`errorMessage` 为空；
14. 3a-3 Guard 在 operation time 取得 maintenance lease、同 revision Manifest
    transaction、held final handle，确认 Working 严格 Absent、final 非零且位于
    `PlannedFinalPath`、持久 identity 完全匹配、`linkCount=1`，并在 CAS 前再次确认
    Working Absent。

任一条件不成立必须进入下述精确结构化失败结果，不能“修补”source facts。

第一版只接受“原 publish result 确实未知”的严格 crash window，并额外明确拒绝：

- schema 2 中出现任何 reconciliation provenance 或其他非 schema 2 字段；
- `publish.published=true`、非空 `publishedPath`，或任何已知 publish success/failure；
- post-publish identity 已尝试、已匹配、带 HRESULT，或其内部事实互相矛盾；
- Finalize/Validation/error facts 互相冲突；
- worker、资源释放和 residual facts 互相冲突。

source evaluator 的结果必须分层：Manifest 本身语义有效但 state 不是唯一 source 时返回
`NotEligibleState`；state 是 ReadyToPublish 但缺少完整 eligibility 时返回
`InvalidSourceFacts`；持久事实彼此矛盾时返回 `SemanticConflict`。三者均 fail closed、不得自动
修复或写盘，且不能被笼统合并为 NotEligible。

`State=Published` 但尚未 `Completed` 不属于第一版。它已有不同的历史 publish 事实，虽然
可以形成更简单的后续 metadata contract，但把两个 source state 放入第一版会扩大状态
集合和字段白名单。它保持 Retain，留给独立小步评估。

## 4. 当前文件事实与历史动作事实

必须永久区分：

| 事实类型 | 可以证明 | 不可以证明 |
| --- | --- | --- |
| 历史动作 | source revision 最后持久化时 publish 尚未记录；已有 Finalize/Validation 事实 | 崩溃后 `MoveFileExW` 是否由产品调用、调用时间和真实返回值 |
| 当前文件系统 | final 当前在 PlannedFinalPath；Working 当前 Absent；held handle 的 volume/file ID 与持久 Working identity 相同；无 reparse/hard link | 该 namespace 变化由产品还是用户完成 |

因此 reconciliation 只能声明：**当前 Session 媒体已由 operation-time 强身份事实确认在
计划最终位置，可作为该 Session 的 reconciled final media。**它不能声明原始 Native
publish API 成功，也不能制造其 HRESULT。

## 5. Schema 2 表达能力审计

Schema 2 无法无歧义表达上述结果。

当前字段语义与 validator 约束为：

- `publish.attempted` 必须与 `publish.hresult` 是否存在完全一致；
- `publish.published` 必须等价于 publish HRESULT 成功；
- `publish.published=true` 时 `publishedPath` 必须等于 `plannedFinalPath`；false 时
  `publishedPath` 必须为空；
- `State=Published/Completed` 必须等价于 `publish.published=true`；
- schema 2 的 Published/Completed 还要求 post-publish identity verification 已尝试；
- `ReadyToPublish -> Published -> Completed` 是现有唯一成功状态链；
- `ValidateUpdate` 禁止 schema 变化，且没有 reconciliation provenance。

所以把 Ready source 直接写成 Published/Completed，必须伪造
`publish.attempted=true`、`publish.hresult=S_OK`、`publish.published=true` 和 post-publish
历史动作。只写 `publishedPath` 也会被 validator 拒绝，并会让一个字段承担两种互斥语义。

结论：**schema 2 不足；schema 3 是代码实现前的硬前置。**

## 6. 最小 Schema 3 设计

Schema 3 不重解释 schema 2 的历史字段，而新增一个 root-level `reconciliation` object
和一个明确的 lifecycle state：`ReconciledCompleted`。

最小对象：

```json
"reconciliation": {
  "reconciled": true,
  "kind": "FinalAtPlannedPathSamePersistentFileV1",
  "sourceRevision": 6,
  "reconciledAtUtc": "2026-08-08T00:00:00.0000000Z",
  "evidenceKind": "MaintenanceLeaseCasHeldFinalIdentityV1",
  "originalPublishResultKnown": false,
  "confirmedFinalPath": "E:\\...\\<SessionId>.mp4"
}
```

严格语义：

- `sourceRevision` 是 Guard 锁内读取并用于 CAS 的 schema 2 revision；
- `reconciledAtUtc` 是 mutation operation time，不回填猜测的 publish 时间；一次 successful
  reconciliation candidate 只能捕获一次 canonical `nowUtc`，并同时设置
  `updatedAtUtc=nowUtc` 与 `reconciliation.reconciledAtUtc=nowUtc`。两字段必须完全相同，
  禁止分别调用两次 clock；
- `confirmedFinalPath` 必须逐字符/路径语义等于 source `plannedFinalPath`，并且正是 held
  final handle 已验证的 candidate；
- `originalPublishResultKnown=false` 表示崩溃窗口中的原始 API 调用结果不可证明；
- v1 不允许把该字段改成 true，也不保存猜测的 original HRESULT；
- `kind` 与 `evidenceKind` 使用封闭枚举，未知值 fail closed；
- 现有 `workingFileIdentity` 保留原样，不在 provenance 中复制第二份 identity 真相。

未来 schema 3 strict validator 只接受完整组合：schema=3、state=ReconciledCompleted、
`reconciliation.reconciled=true`、受控 kind/evidenceKind、
`revision=sourceRevision+1`、两个 timestamp 完全相等、
`originalPublishResultKnown=false`、`confirmedFinalPath=plannedFinalPath`、publish 历史字段保持
source unknown/unmodified、`published=false`、`publishedPath` 为空且全部 immutable source
facts 合法。state 与 reconciled 必须双向一致；任一缺失或矛盾组合均 SemanticInvalid/Retain。

为避免无意改变正常 Recording writer，实施时应区分：

- `RecordingManifestSchemaVersion = 2`：正常 P2.6A/P2.6B 写入继续使用；
- `ReconciledManifestSchemaVersion = 3`：只由受控 reconciliation migration 生成。

不能简单把当前默认 schema 常量改成 3，否则会把 schema 演进泄漏进正常录制热路径。
Parser/inspection 需同时严格支持 2 与 3；schema 1 和 future schema 仍 Retain。

## 7. Target Semantic State

第一版唯一成功 target 为：

```text
schemaVersion = 3
state = ReconciledCompleted
revision = sourceRevision + 1
updatedAtUtc = nowUtc
reconciliation = 严格成立的上述 provenance
```

其中 `reconciliation.reconciledAtUtc` 也必须等于同一个 `nowUtc`。reject、CAS failure、
NoOp/AlreadyReconciled 均不得产生新的持久 timestamp。

以下历史字段必须保持 source 值：

```text
publish.attempted = false
publish.published = false
publish.hresult = null
publishedPath = ""
postPublishIdentityVerification = 未尝试/未匹配/null
```

`confirmedFinalPath` 是 reconciled current filesystem fact 的唯一新路径；不得借用
`publishedPath`。因此它不会声称 Native publish 成功。

P2.6A 的 Native/runtime `Completed := ReadyToPublish && Published` 语义保持不变。Schema 3
的 `ReconciledCompleted` 是独立持久状态，不是普通 `Completed` 的另一种暗中解释。未来
consumer 若需要展示可用媒体，必须显式区分 `Completed` 与 `ReconciledCompleted`，并显示
各自 provenance；本轮不接 UI。

## 8. Mutable Field Whitelist

一次合法 mutation 只允许以下差异：

| 字段 | 唯一允许变化 |
| --- | --- |
| `schemaVersion` | 精确 `2 -> 3`，仅作为本次受控 migration |
| `revision` | 由 CAS 精确 `N -> N+1` |
| `updatedAtUtc` | 与 reconciliation object 共用一次捕获的 canonical `nowUtc`，且不早于 source |
| `state` | 精确 `ReadyToPublish -> ReconciledCompleted` |
| `reconciliation` | 从 schema 2 不存在变为完整、严格、不可变的 provenance object |

明确**不在白名单**：`publishedPath`、全部 `publish.*`、post-publish identity facts 和 error
facts。schemaVersion 的变化是唯一、显式的 schema identity 例外；不允许 3→3 重写、
3→2 降级或其他版本迁移。

## 9. Immutable Field Contract

以下现有字段必须逐字段 semantic-equal：

- writer strategy、SessionId、createdAtUtc；
- workingPath、plannedFinalPath、publishedPath；
- working ownership、WriteSample、frame facts；
- workerExited、recordingResourcesReleased、residualOutstanding；
- Finalize attempted/count/HRESULT；
- Validation attempted/passed/HRESULT；
- Publish attempted/published/HRESULT；
- Working persistent volume identity、FILE_ID、capture facts；
- post-publish identity verification 全部事实；
- errorCategory、errorCode、errorMessage。

未来实现必须提供一个明确的
`ValidateNarrowReconciliationMutation(before, after)`（名称可按代码风格调整），先验证
完整 source/target contract，再显式比较上述每一个字段。只依赖通用
`ValidateUpdate` 的“单调不倒退”检查不够；任何非白名单差异必须返回
`ImmutableFieldViolation` 且不调用写入。

原错误事实不能清空或覆盖。第一版 source eligibility 本身要求无错误；即使未来扩大
source，也必须把历史错误保留，并用独立 reconciliation provenance 记录成功。

## 10. Guard 调用边界

`ReconciliationEvidenceGuard` 是所有 mutation 前证据的唯一入口。Narrow Reconciler 不得
复制 owner、revision、PathSafety、FILE_ID、hard-link、Working absence 或 TOCTOU 逻辑。

调用合同：

1. Scanner 只提供 canonical SessionId、expected revision 与 candidate hint；
2. 显式调用 `ReconciliationEvidenceGuard::Acquire`；
3. 只有 `EvidenceComplete` 且 RAII Guard 仍持有 maintenance lease、Manifest transaction、
   media root 与 final handle，才进入 source/target evaluator；
4. evaluator 必须基于 `guard.CurrentManifest()`，不能复用 Scanner Manifest；
5. 先过 Source Eligibility，再生成唯一 whitelist candidate；
6. 紧邻 CAS 由 Guard 重验 final facts、linkCount 和第二次 Working absence；
7. 任一变化立即放弃。

`EvidenceComplete != Reconciled`。Guard 只提供 operation-time evidence，不选择业务转换。

## 11. CAS 边界

Schema 3 migration 必须使用 3a-3 同一 maintenance lease、`manifest.write.lock` 和原子保存
核心，但不能放宽通用 Recording `ValidateUpdate`。

实施建议是增加专用窄接口，例如：

```text
CompareExchangeNarrowReconciliation(before, schema3Candidate)
```

它必须：

- 只接受 transaction 锁内 current schema 2 Ready source；
- current revision 精确等于 `sourceRevision`；
- 先执行 mutation whitelist/immutable validator；
- CAS 前再次重读 current 完整内容并确认未变化；
- CAS 前由 Guard 第二次证明 Working Absent 并重验 held final；
- 复用现有 serializer、strict parser、Flush、verify、ReplaceFileW 原子 commit；
- 成功只写一次 revision `N+1`；任何失败保持旧 Manifest byte-valid；
- 不自动重试 stale candidate。

## 12. 单向与幂等

唯一方向是：

```text
schema 2 ReadyToPublish@N
  -> schema 3 ReconciledCompleted@(N+1)
```

禁止降级、回滚、重新 publish 或再次更新 reconciliation 时间。

第二次调用遇到严格有效的 schema 3 `ReconciledCompleted` 时返回 `AlreadyReconciled`，不取
mutation 授权、不写文件、不增加 revision。若并发 loser 得到 revision mismatch，应只读
重载：如果 winner 已形成完全有效的相同 target，返回 `AlreadyReconciled`；否则返回
`RevisionChanged`。不得循环重试。

任何 `AlreadyReconciled` 都必须来自 operation-time structured reload 和 strict schema 3
validator；不得来自旧 Scanner classification、旧 ScanResult、缓存 Manifest 或调用方声明。
初始调用已经观察到 schema 3 时也必须重新读取磁盘并验证完整 target，才能 no-op。malformed、
unsupported 或交叉事实不一致的 schema 3 不能被视为已处理。

### 12.1 Reconciliation Target Semantic Equivalence

并发 loser 对 winner 结果的等价判断必须要求以下事实相同：

- SessionId；
- `sourceRevision`；
- reconciliation kind 与 evidenceKind；
- `originalPublishResultKnown=false`；
- `confirmedFinalPath`；
- target lifecycle state `ReconciledCompleted`；
- 所有 immutable source facts。

持久 target 必须满足 `revision == sourceRevision + 1`。等价比较唯一允许忽略的是两个 caller
各自在内存中生成、尚未持久化的 `updatedAtUtc/reconciledAtUtc` 值；winner 已落盘的两个时间
自身仍必须完全相等。timestamp 差异不得驱动第二次写入。

两个 caller 同基于 revision N 时，A 成功写入 N+1 后，B 的 CAS 必须失败。B 随后执行
operation-time structured reload：若 winner 是严格有效且与 B 意图 semantic-equivalent 的
target，返回 AlreadyReconciled；否则返回 RevisionChanged/ConcurrentChange。两条路径都不得
再次写盘或推进 N+2。

## 13. 媒体零修改原则

P2.6C-3b 只允许 Manifest metadata CAS。生产 Reconciler 不得包含或调用：

- `MoveFileExW`、`DeleteFileW`、copy、rename、replace；
- write/truncate/touch media；
- timestamp 修改、repair、republish 或 cleanup。

Guard 的 final handle 仅用于证据并拒绝 write/delete sharing。成功前后 final 的 bytes/hash、
volume identity、FILE_ID、size、creation/last-write timestamps 必须保持。WorkingPath 必须
继续 Absent；不得创建 placeholder 来锁定 absence。

## 14. 用户手工移动同一文件

用户在 Ready crash 后手工把 WorkingPath 同卷移动到 PlannedFinalPath，可能保持相同
Volume Identity 与 `FILE_ID_128`。此时 Guard 可以证明：

- 当前 final 是 source 持久 Working identity 指向的同一底层文件对象；
- 当前路径是精确 PlannedFinalPath；
- Working 当前严格不存在；
- 当前 owner inactive、路径安全且 linkCount=1。

Guard 不能证明移动者是产品，也不能证明历史 `MoveFileExW` 调用和 HRESULT。因此系统只
能生成 `ReconciledCompleted + originalPublishResultKnown=false`，不能写
`publishAttempted=true`、`publishHResult=S_OK`、`published=true` 或普通 `Completed`。

## 15. Result 模型

未来 `NarrowReconciliationResult` 至少区分：

- `Reconciled`
- `AlreadyReconciled`
- `NotEligibleState`
- `InvalidSourceFacts`
- `SemanticConflict`
- `GuardRejected`
- `RevisionChanged` / `ConcurrentChange`
- `ImmutableFieldViolation`
- `UnsupportedSchema`
- `EvidenceInsufficient`
- `CasFailed`
- `IoFailure`
- `Unknown`

结果应保留 Guard/CAS 的结构化子结果、expected/observed revision 和 HRESULT；不得只返回
bool。`Reconciled` 只表示 schema 3 provenance 已原子落盘，不表示原始 Native publish
结果已被发现。

结果语义固定为：

- `NotEligibleState`：Manifest 语义有效，但 lifecycle state 不是第一版唯一 source，例如
  Recording、Stopping、Published；
- `InvalidSourceFacts`：state 是 ReadyToPublish，但缺少 worker/resource/Finalize/Validation/
  identity 等完整 eligibility；
- `SemanticConflict`：持久事实彼此矛盾，例如明确关键失败 error 与成功前置 facts 并存、
  Ready source 却存在 publish/publishedPath/post-publish 矛盾事实。

Result 只用于诊断，不改变安全规则。上述三类均 no write，不能清空、补齐或“修复”原事实。

## 16. Future Startup 调用链

未来调用关系只能是：

```text
Managed startup
  -> read-only Scanner / candidate hint
  -> explicit Narrow Reconciler call
  -> 3a-3 operation-time Guard
  -> strict source eligibility
  -> whitelist candidate
  -> expected-revision dedicated CAS
```

Scanner 继续永久保持：

```text
deleteAllowed = false
reconciliationAuthorized = false
```

Classification 只能决定“是否值得尝试”，不能授权 mutation。单 Session 失败必须隔离，
不得阻断 App 启动、影响其他 Session、删除素材或把失败压成全局成功。本轮不实现该链。

### 16.1 Schema 3 reader-first activation order

schema 3 writer 绝不能先于安全 Reader/Consumer 启用，实施顺序冻结为：

1. Manifest parser/strict validator 先支持 schema 3；
2. 所有 Native Manifest consumer 显式认识 `ReconciledCompleted`；
3. `SessionInspection`/Classifier 加入独立
   `ReconciledCompletedConsistent`，不得复用 `CompletedConsistent`；
4. 本合同的全部消费者负向门禁通过；
5. 才允许启用 NarrowReconciler production mutation API；
6. Managed startup orchestration 留给 P2.6C-4，本阶段不接。

在第 5 步前，不得产生生产 schema 3 Manifest。旧/未升级 consumer 只能把 schema 3 作为
UnsupportedSchema/Unknown Retain，不能推导普通 Completed、OutputSuccess 或可删除/可恢复
授权。

### 16.2 ReconciledCompletedConsistent

该只读 classification 最少要求：

- schema 3、state ReconciledCompleted 与完整 provenance 严格有效；
- `originalPublishResultKnown=false`；
- `confirmedFinalPath == plannedFinalPath`；
- publish attempted/published/HRESULT 保持 source unknown/unmodified，`published=false`；
- `publishedPath` 为空；
- current final 的 read-only path/identity 事实与持久 provenance/Working identity 一致，且
  Working 当前 Absent；任何 inaccessible/unknown/reparse/hard-link/identity mismatch 均 Retain。

该 classification 始终保持 `deleteAllowed=false`、`reconciliationAuthorized=false`。它不能
设置或推导 Native Completed/OutputSuccess。

### 16.3 Native Completed / OutputSuccess 永久边界

P2.6A Native 定义永久保持：

```text
Completed := ReadyToPublish && Published
OutputSuccess := Completed
```

`ReconciledCompleted` 只是 historical recovery terminal semantic state，不是 Native
Completed，也不是 Native OutputSuccess。不得为兼容旧 consumer 而伪造
`published=true`、`publishedPath`、publish HRESULT 或 post-publish verification。

## 17. 测试施工图

### Happy path 与幂等

1. 严格 schema 2 Ready crash-window + Guard EvidenceComplete，成功生成 schema 3
   ReconciledCompleted；
2. revision 精确 `N+1`；
3. final bytes/hash 完全不变；
4. 除 whitelist 外全部 Manifest 字段 semantic-equal；
5. 第二次调用返回 AlreadyReconciled，revision 不再增加。

### Guard 拒绝

6. owner Active；
7. owner evidence missing 且不得创建 owner leaf；
8. revision changed；
9. identity missing；
10. identity mismatch；
11. Working present；
12. Working inaccessible；
13. real hard link；
14. root/intermediate/leaf reparse 或 path unsafe。

### Eligibility 拒绝

15. Recording；
16. Stopping；
17. Finalize failed/未尝试/count 非 1；
18. Validation failed/未尝试；
19. Publish explicitly failed + Working exists；
20. malformed Manifest；
21. unsupported/future schema；
22. schema 1、no identity、error facts 非空或不完整 Ready predicate。

### Historical truth 与 whitelist

23. 用户手工 same-volume move 同一文件：结果必须是 ReconciledCompleted，原 publish fields
    仍 false/null，provenance 明确 original result unknown；
24. 测试 mutator 故意改变每一类非白名单字段，逐项得到 ImmutableFieldViolation/no write。

### Atomic/CAS 与媒体零修改

25. Replace/Flush/verification failure：旧 Manifest 仍 byte-valid；
26. 两个相同 expected revision 并发 caller：只有一个 Reconciled，loser 为
    AlreadyReconciled/RevisionChanged，最终 revision 只加 1；
27. before/after final hash、size、volume/file ID 完全相同；
28. creation/last-write timestamps 不变，Working 仍 Absent；
29. Scanner 仍不写、不授权，重复扫描不改变 revision；
30. 一个 Session reconciliation 失败不影响另一个合法 Session。

### Schema 3 专项

31. 既有 schema 2 Native Published/Completed round-trip 与语义不变；
32. schema 3 UTF-16 中文路径序列化/反序列化逐字符一致；
33. reconciliation object 缺字段、未知 kind/evidence、错误 sourceRevision、错误路径、
    `originalPublishResultKnown=true` 均 SemanticInvalid；
34. schema 4/future schema 为 UnsupportedSchema，不误写；
35. ReconciledCompleted 与 provenance/publish fields 任一交叉不一致即 SemanticInvalid；
36. 只有 schema 2 Ready→schema 3 ReconciledCompleted migration 被 dedicated validator 接受。

### 时间、幂等与并发专项

37. successful reconciliation 只捕获一次 nowUtc，持久
    `updatedAtUtc == reconciledAtUtc`；
38. 第二次 operation-time reload 后返回 AlreadyReconciled，revision 与两个 timestamp 不变；
39. 两个相同 revision caller 只有一个 CAS 成功，最终 revision 只加 1；
40. loser reload winner；即使 loser 内存 timestamp 不同，只要 target semantic-equivalent，仍
    返回 AlreadyReconciled 且不写盘；
41. winner target 与 loser 意图不等价时返回 RevisionChanged/ConcurrentChange；
42. 所有 reject、failure、NoOp 和 concurrent loser 路径均无第二次 write。

### Schema 3 consumer 负向门禁

43. ReconciledCompleted 不映射为 Native Completed；
44. ReconciledCompleted 不映射为 OutputSuccess=true；
45. schema 3 持久 `publish.published` 必须继续为 false；
46. schema 3 `publishedPath` 必须继续为空；
47. publish attempted/HRESULT 与 post-publish facts 不得被补写；
48. Scanner 返回 ReconciledCompletedConsistent，不得返回 CompletedConsistent；
49. 缺失/false reconciliation、错误 state/provenance 组合为 SemanticInvalid/Retain；
50. ReconciledCompleted 但 `published=true` 明确拒绝；
51. ReconciledCompleted 但 `publishedPath` 非空明确拒绝；
52. `originalPublishResultKnown=true` 且不存在合法原始 publish 事实明确拒绝；
53. `sourceRevision` 与 target revision/CAS 前 revision 关系非法明确拒绝；
54. `confirmedFinalPath != plannedFinalPath` 明确拒绝；
55. Ready source 中 error/Finalize/Validation/publish/post-publish/resource 事实冲突返回
    SemanticConflict 且不写；
56. schema 1/2 parser、writer、Classifier、Native Completed/OutputSuccess 与 LongRun 行为不变；
    Managed Controller/UI 与 LongRun 若不读取历史 Manifest，必须由调用图和负向测试明确证明。

所有 fixture 使用正式 Guard/CAS/serializer/parser，不直接写入期望结果。测试不得对真实历史
Session 执行 mutation。

## 18. 实施门槛

进入 P2.6C-3b 代码实现前必须同时完成：

1. schema 3 数据模型、严格 serializer/parser/validator 设计评审通过；
2. 正常 Recording writer 继续固定 schema 2，不因新增 schema 3 改变热路径；
3. `ReconciledCompleted` 与 reconciliation object 的交叉字段不变量可被严格验证；
4. dedicated whitelist validator 覆盖每一个现有 Manifest 字段；
5. dedicated CAS 复用 3a-3 locks/handles/atomic writer，不放宽普通 UpdateManifest；
6. Scanner 仍不授权；实现阶段若需识别 schema 3，只增加只读分类；
7. 56 项施工图及 P2.6A/B、3a1/3a2/3a3、ABI 回归全部通过；
8. 无媒体 mutation API、无 startup 自动调用、无 UI。

当前 `P2.6C-STARTUP-SCAN-CLASSIFICATION-PLAN.md` 对 schema 2 Ready+final/no-working
继续要求 Retain 是正确的。只有 schema 3 provenance、专用 mutation validator 与全部门禁
实际实现后，才能为本合同定义的单一场景增加显式 Narrow Reconciler；本轮不修改 PLAN。

## 19. 已知限制与合同结论

- 文件身份能证明“同一个文件对象现在位于计划路径”，不能证明历史操作者；
- Windows 不提供覆盖 Manifest 与 Working absence 的全局文件系统事务，继续依赖 Guard
  双检与 fail closed；
- hard link、owner evidence missing、legacy/no identity、inaccessible 和外部恶意竞态均
  Retain；
- 第一版不处理 Published→Completed，即使它具备独立的简单 metadata contract；
- ReconciledCompleted 不是媒体修复，也不执行新的 SourceReader Validation；source 只记录
  P2.6A 当时 Validation 成功，当前 Guard 证明同一 file object 的身份与位置，但不把该
  身份事实扩大为“外部从未修改过内容”；
- 正常 runtime Snapshot/Completed、Managed UI、LongRun 与 Native ABI 均不在本合同中修改。

冻结的七项答案：

1. Source：唯一为严格 schema 2 `ReadyToPublish` 加全部前置事实与 3a-3 operation-time
   evidence；
2. Target：schema 3 `ReconciledCompleted`，不是 Published 或普通 Completed；
3. Mutable：schema 2→3、revision +1、updatedAtUtc、state、new reconciliation object；
4. 永不伪造：publish attempted/HRESULT/published、publishedPath、post-publish verification、
   Finalize/Validation、identity、error 与其他历史事实；
5. Schema 2 不足；
6. Schema 3 最小新增 ReconciledCompleted + reconciliation provenance object；
7. 手工同卷移动只能证明当前 same-object final fact，不能证明产品 publish API 成功。
