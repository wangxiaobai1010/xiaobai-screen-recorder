# P2.6C-3a-2 Session Lifetime Owner Evidence

## 1. 问题定义

P2.6C-3a-1 的持久文件身份只能证明 working 与 rename 后 final 是同一
Windows 文件对象，不能证明当前是否仍有另一录制进程可能修改 media、Manifest
或发布状态。本切片新增跨进程 lifetime owner evidence，但不授予任何
reconciliation。

## 2. 为什么 PID 不足

PID 会复用、进程查询会受权限影响，PID 文件也无法随崩溃原子地表达句柄释放。
PID 可用于诊断，但不参与正确性判断。本实现的事实源是 Windows kernel handle
与 share-mode 冲突。

## 3. Owner lease 设计

- 独立模块：`SessionLifetimeOwner.h/.cpp`。
- rendezvous 文件：`sessions/<CanonicalSessionId>/session.owner.lock`。
- owner 以 `CreateFileW(OPEN_ALWAYS, shareMode=0)` 原子创建或打开文件并持续持有
  handle。
- `SECURITY_ATTRIBUTES.bInheritHandle=FALSE`，并用 `GetHandleInformation` 再次验证
  `HANDLE_FLAG_INHERIT` 未设置。
- 新 leaf 的 `CreateFileW` 成功本身就是原子 lease 事件，不在其后添加可能失败的
  持久化步骤；既有 stale leaf 在接管前验证为非 reparse 普通文件。成功 owner
  文件不会在 release 时删除。
- owner 文件存在仅说明此 Session 曾建立过该机制，不表示当前 Active。

它与 `manifest.write.lock` 明确分离：后者只保护一次原子 Manifest 写入且写完即
释放；owner lease 覆盖整个可变 Session 生命周期。

## 4. Deterministic owner path

路径只由既有 `RecordingOutputRoot` 的 `sessionsRoot` 与
`RecordingSessionIdentity` 的 36 字符大写无花括号 GUID 构造。不读取 Manifest
中的任意 owner path，不新增第二套 root/GUID 规则。

## 5. Acquire 合同

acquire 前先对 canonical Session 目录执行既有 handle-based Path Safety。目录
不安全、reparse、不可访问或 SessionId 非 canonical 时不建立可信 lease。
同一 Session 的第二次 acquire 由 Windows sharing violation 拒绝；不同 Session
互不阻塞。

owner acquisition 是未来恢复授权的证据，不是用户录像成功的前置条件。失败仅
记录 `LifetimeOwnerAcquireAttempted/Acquired/HResult/Path` 诊断，不能停止
Encoder、删除 working、阻断 Finalize/Validation/Publish，或把成功录像改成
Failed。证据不可用的 Session 未来必须 Unknown/Retain。

## 6. Probe 状态模型

`SessionLifetimeOwnerProbeResult` 不是布尔值，状态包括：

- `ActiveOwned`：专用 owner leaf 的只读 `OPEN_EXISTING` 得到
  `ERROR_SHARING_VIOLATION`/`ERROR_LOCK_VIOLATION`；
- `InactiveLeaseReleased`：只读打开成功，并确认 leaf 是非 reparse 的普通文件；
- `EvidenceMissing`：owner leaf 不存在；
- `UnsafePath`：Session 路径或 owner leaf 不满足安全合同；
- `Inaccessible`：AccessDenied/Privilege 等无法证明的结果；
- `IoFailure`：其他 I/O 错误；
- `Unknown`：无效输入或未知异常。

Probe 只用 `OPEN_EXISTING`，不会创建、删除、truncate、写内容、改时间或修改
Manifest。AccessDenied 绝不折叠成 Inactive。

## 7. 精确 acquisition/release 生命周期

acquisition point：`CreateManifest` 成功、Session 目录已真实存在后，且在
`Starting` revision 写入前。此后 `VideoEncoderConsumer::Impl` 持有 handle。

覆盖窗口：Starting → Recording → Stopping → Finalize → Validation → worker
exit → join → ReadyToPublish → `MoveFileExW` → Published/Completed 或 Failed
Manifest → terminal Snapshot → diagnostics summary。

release point：最后一次 media/cleanup/Manifest/Snapshot/diagnostics mutation 完成
后。正常 Stop、Preview Close 与重复 Stop 仍复用同一个 `StopAndJoin`。启动失败
在 Failed Manifest 与已有诊断写完后释放；join 异常若 worker 仍存活则不提前
释放，由对象/进程最终生命周期兜底。

## 8. Crash 自动释放保证

Windows 在正常退出和异常进程终止时自动关闭内核 handle。测试真实启动第二个
`XbPreview.Native.Tests.exe` helper 持有 lease：父进程能看到 Active；正常退出
后看到 Inactive；`TerminateProcess` 不执行 release 逻辑时，OS 仍释放 handle，
owner 文件继续存在但 Probe 为 Inactive。没有通过删除 lock 文件伪造 crash。

## 9. Non-inheritable handle

owner handle 创建时显式不可继承，并在 acquire 成功前读取 handle flags 复核。
因此子进程不能在录制器退出后意外延长 Active 状态。

## 10. Path Safety 边界

先验证 SessionsRoot/canonical Session 目录，再对 deterministic owner leaf 做专用
share-mode probe。活跃 owner 自身会阻止普通 leaf 打开，所以 SharingViolation 在
这个专用 Probe 中是 Active 正证据，而不是“无 owner”。Session 目录 reparse、
root escape 或无法证明的权限/I/O 结果仍为 Unsafe/Unknown/Retain。

## 11. Acquisition failure 策略

Manifest 创建失败或 owner acquire 失败时不改变 P2.6A 安全发布。诊断会明确
`Acquired=0` 与真实 HRESULT；没有 owner 文件的 Session 被 Scanner 暴露为
EvidenceMissing。未增加 Manifest capability 字段，schema 保持 2；正式唯一 GUID
Session 合同与 deterministic owner 文件已足以区分新证据和 legacy 缺证据。

## 12. Legacy / EvidenceMissing

旧 Session 没有 owner 文件是正常兼容事实。EvidenceMissing 不等于 Inactive，
也不得成为自动 mutation 依据。

## 13. SessionInspection 只读暴露

`SessionInspectionResult` 新增只读 `lifetimeOwner` facts，并新增
`LiveOwnerActive`、`LifetimeOwnerEvidenceMissing` reasons。既有 12 类分类保持，
所有路径继续强制：

- `deleteAllowed=false`
- `reconciliationAuthorized=false`

Active、Inactive、EvidenceMissing、fileIdentity match 的任意组合均不改变此门禁。

## 14. 与 3a-1 file identity 的组合边界

Ready + persisted working identity + Active owner 时不得 reconcile；rename 已成功
但 Published Manifest 尚未更新、原进程仍活着时 owner 仍为 Active。原进程在该
窗口崩溃后，owner 变 Inactive，但本轮只能证明“没有 live owner”。

**Owner Inactive != Reconciliation Authorization。**

**FileIdentityMatch + OwnerInactive 仍不足以自动 mutation。**

## 15. 跨进程与真实录制测试

新增入口 `--p2.6c3a2-lifetime-owner` 与仅测试 helper
`--p2.6c3a2-owner-helper`。helper 通过真实独立进程持有 share=0 handle；测试 seam
只在 `XBPREVIEW_NATIVE_TESTS` 编译，正式 DLL 没有 hooks、命令或控制入口。

真实 Encoder 测试在独立 Stop 线程的三个现有边界观察：Stopping、join 后
ReadyToPublish、MoveFile 成功而 metadata 未完成。三个窗口均由外部 Probe 证明
Active，terminal mutation 后证明 Inactive。

## 16. 32 项矩阵

1. fresh acquire；2. 同 Session 第二 owner 拒绝；3. 不同 Session 独立；4. handle
不可继承；5. 中文 root/canonical path；6. 活跃 Probe；7. 正常 release；8. owner
文件存在但 Inactive；9. EvidenceMissing；10. AccessDenied 非 Inactive；11. 非法
SessionId；12. reparse Session Unsafe；13. 跨进程 Active；14. helper 正常退出；
15. helper 强制终止；16. crash 后文件保留但 Inactive；17. 正式 Start Active；
18. Recording Active；19. Stopping Active；20. Finalize/Validation/worker exit/join/
Ready Active；21. rename 后 metadata 前 Active；22. terminal 后 release；23. acquire
失败仍 Completed/OutputSuccess；24. IoFailure 非 Inactive；25. Scanner Active；
26. Scanner Inactive；27. Scanner legacy EvidenceMissing；28. owner facts 不授权；
29. identity match + Active 不授权；30. identity match + Inactive 不授权；31. 重复
Stop 不泄漏/重获 owner；32. 测试/Session handle 最终归零。

定向结果：32/32 PASS。

矩阵也一次通过。该现象不在 owner/Manifest 事实链上，但作为测试环境观察保留。

## 18. 已知限制

- owner 只证明 live process ownership，不证明某项恢复动作正确；
- owner acquisition 是 best effort，缺证据必须保留；
- owner 文件持久存在，不提供清理策略；
- 不使用 PID、未实现 recovery UI、自动扫描 mutation 或 reconciliation。

## 19. P2.6C-3a-3 依赖

下一证据切片仍需建立 expected revision re-read/CAS、operation-time revalidation、
TOCTOU/reparse/hard-link 防御及最终 narrow reconciliation 授权组合。本切片不得
被单独解释为 mutation 许可。
