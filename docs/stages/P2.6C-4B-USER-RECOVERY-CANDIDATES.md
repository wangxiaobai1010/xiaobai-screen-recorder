# P2.6C-4b 用户可见恢复候选与显式窄恢复入口

## 1. 阶段目标

本阶段把 P2.6C-4a 已送达 Managed 层的只读启动扫描结果，翻译为普通用户可以理解的历史录制关注入口；同时仅对产品合同明确支持的唯一窄恢复候选，提供由用户主动点击触发的“尝试恢复”。

本阶段没有自动 recovery、自动 reconciliation、媒体删除、清理、视频修复或 P2.6D 行为。Preview 和普通录制仍是首页主流程。

## 2. 为什么不显示工程状态名

用户需要知道“录像是否需要关注、文件是否被保留、当前能否尝试找回”，不需要理解内部持久化和并发协议。UI 因此不显示 Manifest、ReadyToPublish、PublishOutcomeUnprovenRetain、ReconciledCompleted、reconciliation、schema、revision、HRESULT、FILE_ID 或 owner 等工程词汇。

这些事实仍完整保留在 Native 结果、Managed 内部诊断和测试中，但不得进入用户文案。

## 3. UserRecoveryPresentation 映射

Managed 层新增纯 presentation mapping，只把同一个 `StartupInspectionSnapshot` 中的 Native 事实翻译为四类用户语义，不重新解析 Manifest、不重新判断文件系统安全，也不自行计算 mutation 资格：

- `Recovered`：仅用于本次显式恢复后，经重新只读扫描确认的成功结果；正常启动时不会把它长期列为待处理候选。
- `CanTryRecovery`：仅对应唯一受支持的 `PublishOutcomeUnprovenRetain` 现场，并要求 owner inactive、存在 expected revision。
- `RecordingPreserved`：存在 working media，但合同不允许当前自动处理；告诉用户原始录制文件已保留。
- `NeedsAttentionRetained`：unknown、corrupt、missing facts、unsupported、unsafe、inaccessible、filesystem conflict 等其他 Retain 情况；告诉用户暂时无法自动处理且文件不会被删除。

正式不变量是：

`Scanner Classification != User-facing State`

## 4. 提示入口设计

MainForm 在 Preview 上方加入隐藏优先、非阻塞的 compact notice。只有终态启动扫描结果中存在需要用户关注的历史 Session 时才显示：

- 单个候选：“发现 1 段未正常结束的录制”；
- 多个候选：显示准确数量；
- 操作仅为“查看”，点击后展开轻量列表。

入口不弹 MessageBox、不抢焦点、不阻塞 Preview 或录制，不使用大面积危险警告，也不把首页改造成 Recovery dashboard。

## 5. 哪些 Session 允许“尝试恢复”

只有 presentation 映射为 `CanTryRecovery` 的 Session 显示按钮。其来源必须是当前 Native Scanner 精确分类 `PublishOutcomeUnprovenRetain`，且具备 canonical SessionId、expected revision 和 inactive owner 事实。

这只是“允许向 NarrowReconciler 发出一次显式请求”，不是 Scanner 对 mutation 的授权。真正授权仍由 Native NarrowReconciler 在操作时重新进入 3a3 Guard、严格 eligibility 和 expected-revision CAS。

正式不变量是：

`StartupInspectionSnapshot != Mutation Authorization`

## 6. 只能 Retain 的 Session

下列情况没有“尝试恢复”按钮：Recording 中断且 working 存在、Finalize 失败、Validation 失败、Publish 明确失败、Manifest missing/corrupt、unsupported schema、unknown、filesystem conflict、owner active、legacy/no identity、hard-link ambiguity、路径 unsafe/inaccessible，以及所有其他 Retain 分类。

它们只显示“录制文件已保留”或“暂时无法自动处理，文件不会被删除”的平静文案。恢复失败也保留该 Session，不从列表中伪装消失，不自动无限重试。

## 7. 显式用户动作调用链

唯一 mutation 调用链为：

`用户点击“尝试恢复”`

→ Managed `RecoveryActionCoordinator` 发出指定 Session 的显式请求

→ `NativeNarrowRecoveryService`

→ 版本化 Native Narrow Reconciliation ABI

→ 现有 `NarrowReconciler`

→ 3a3 operation-time Guard

→ strict source eligibility

→ expected-revision CAS

→ 结构化结果返回 Managed。

MainForm 启动、启动扫描结果到达、查看列表、Timer 刷新或 Preview/Recording 状态变化均不会触发该链。

## 8. NarrowReconciler bridge

新增独立 Narrow Reconciliation ABI v1，没有复用 RecordingSnapshot，也没有让 Managed 直接写 Session Manifest：

- 产品 API：`0x00040003`（major 4，minor 3）；
- Narrow ABI：`0x00010001`；
- layout/options/result：32/48/64 bytes，Pack=8；
- 输入：受信任 diagnostic root、canonical SessionId、expected revision；
- 输出：显式结构化 status、HRESULT、observed revision、Guard/CAS facts；
- 版本、尺寸、reserved、canonical identity 不匹配均 fail-closed；
- 所有 C++ 异常在 C ABI 边界内终止传播。

旧 `XbPreviewAbiLayout`、`XbRecordingSnapshot` 2856 bytes 和 Historical Scan ABI v1 均未扩展或改变。Managed 按枚举映射结果，不解析错误字符串决定流程。

## 9. Recovery single-flight

第一版采用全局 single-flight：同一时刻仅允许一次显式恢复尝试。快速双击共享同一个进行中 Task，不会并发调用 Native；不同 Session 在已有尝试进行时也不会启动第二个 mutation。

执行期间按钮显示“正在检查…”，不声称正在修复视频。失败不自动 retry；再次打开应用后，新的只读扫描可重新呈现仍需关注的事实。

## 10. 结果文案

- Reconciled：重新扫描确认后显示“录像已找回并确认保存。”
- AlreadyReconciled：仍必须重新扫描；确认后表示这段录像已经处理好。
- GuardRejected、EvidenceInsufficient、RevisionChanged、ConcurrentChange：显示现场已变化、暂时无法自动处理且文件已保留。
- NotEligible、InvalidSourceFacts、SemanticConflict、UnsupportedSchema：显示暂时无法自动恢复且文件已保留。
- IoFailure、CasFailed、Unknown：显示暂时无法读取或处理，建议稍后再试，文件不会被删除。

HRESULT 和内部状态只写诊断，不显示给用户。

## 11. 成功后的 rescan

Reconciler 返回 `Reconciled` 或 `AlreadyReconciled` 后，Coordinator 必须调用正式 read-only `SessionInspection` 重新扫描同一输出根。只有 rescan 在同一 Session 看到 `ReconciledCompletedConsistent`，UI 才显示恢复成功。

本地 candidate 状态、mutation 返回值或旧 StartupInspectionSnapshot 都不能单独成为最终成功显示事实：

`最终用户成功显示事实 = rescan 的 ReconciledCompletedConsistent`

## 12. Display-safe path

UI 只显示 P2.6C-4a Managed DTO 已明确提供的 display-safe path。Managed 4b 不读取 Manifest 原始路径，不把 SessionId 拼成路径，也不重新实现 Path Safety。没有安全展示路径时宁可不显示路径。

列表不显示 SessionId、Manifest 路径、revision、schema、HRESULT、FILE_ID 或 owner 状态。

## 13. 关闭安全

窗口关闭先请求 RecoveryActionCoordinator 取消，随后退订回调并等待进行中的 orchestration 安全终止，再释放 startup inspector 和 Preview lifecycle。已经进入 Native Guard/CAS 的短临界区不会被 force kill；Managed 在关闭后不再更新已释放 UI。

Coordinator 的 callback 带当前实例/快照身份检查，异常被观察，不产生重复 callback、late UI access、UAF 或 unobserved Task exception。

## 14. 多实例

另一个 App 实例重新取得 lifetime owner 时，NarrowReconciler operation-time Guard 会返回拒绝/现场变化。4b 不抢占 owner、不 kill 另一实例、不无限等待。用户只看到“当前无法处理，文件已保留”。

点时 Scanner owner 事实不是 mutation capability；每次点击仍走完整 Native operation-time revalidation。

## 15. 测试矩阵

Native `--p2.6c4b-user-recovery`：12/12 PASS，覆盖 ABI/version、唯一 eligibility、schema2→schema3、无 publish facts 伪造、media hash/identity/timestamps 零变化、AlreadyReconciled 无 N+2、noncanonical identity、revision change、active owner、unsupported schema 和 missing owner evidence。

Managed `--p2.6c4b-user-recovery`：33/33 PASS，覆盖至少要求的 32 项：

- 0/1/多候选提示、四类 presentation、禁用工程词；
- 仅支持候选显示按钮；指定 Session、双击与全局 single-flight；
- Reconciled/Already 经 rescan 确认；Guard/revision/I/O 安全文案且无 retry loop；
- media SHA 不变、unsupported Manifest bytes 不变；
- Scanner 无 mutation authority、Managed 无 Manifest writer；
- 4a 非阻塞、终态后才显示、close/cancel 无 late callback；
- active owner、多实例 fail-closed；unsafe path 不泄露原始路径；
- 实际 Native DLL bridge、实际 Host DLL MainForm STA 控件接线与进程/线程归零。

测试/Debug 专用人机 fixture：

`artifacts\bin\Release\x64\XbPreview.Managed.Tests.exe --p2.6c4b-recovery-fixture`

它只使用测试数据，展示可尝试候选、已保留但不可自动处理候选和恢复成功状态，不写正式用户数据。

## 17. 当前 UI 限制

本阶段只有功能性最小 notice 和轻量列表，没有正式 Recovery Center、最终视觉精修、批量操作、排序筛选、复杂历史管理或自动视频修复。安全事实不足时不会为了“更完整的列表”显示原始路径或提供动作。

Preview、录制按钮、镜头/设备和既有输出 UI 布局没有被重新设计；恢复提示不抢过录制主操作。

## 18. P2.6C 后续边界

P2.6C-4b 已建立用户可理解的候选入口、唯一显式窄恢复动作、成功 rescan 事实闭环与关闭/多实例安全。阶段仍需后续独立审查与 Git 冻结指令后才能成为正式冻结基线。

本阶段未开始 P2.6D、自动视频修复、清理策略、自动 reconciliation、媒体删除、正式 Recovery Center 或最终视觉精修。

阶段结论：`P2.6C-4B-USER-RECOVERY-CANDIDATES-READY`。
