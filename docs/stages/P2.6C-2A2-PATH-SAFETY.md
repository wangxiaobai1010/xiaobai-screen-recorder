# P2.6C-2a-2 Handle-based Path Safety Foundations

日期：2026-08-07

分支：`feature/p2.6c-inspection-foundations`

基线：`c0805f4e678117ce6a5041deefb37a6794844066`

## 1. 模块职责与阶段边界

本切片新增独立 Native `SessionPathSafety.h/.cpp`，回答一个有限问题：给定由产品配置
解析出的 TrustedRoot 和一个不可信 CandidatePath，在当前检查时刻，是否有足够的
Windows handle 事实允许未来 Scanner 对该对象做只读检查。

模块不属于 `VideoEncoderConsumer`、`SessionManifest` 或 Managed Controller，也不读取或
修改 Manifest/媒体内容。它不枚举 Session，不分类，不 publish，不删除、移动、覆盖或
修复文件。本切片没有修改 Native ABI、Manifest schema、P2.6A Publish/Completed、Encoder
生命周期、Managed Controller/UI 或 LongRun。

最重要的合同是：

> `SafeForReadOnlyInspection` **不等于** `SafeForMutation`。

本结果只是某一时刻的只读事实快照。任何未来 delete/rename/overwrite/reconciliation
必须在操作时重新打开 handle，并重新验证 path、reparse、containment、volume/file
identity 与 Manifest revision；不得复用旧 `PathSafetyResult` 作为写操作授权。

## 2. TrustedRoot 合同

TrustedRoot 的字符串仍只能来自 P2.6C-2a-1 的 shared `RecordingOutputRootResolution`：

- Session 目录使用 `sessionsRoot`；
- Working/PlannedFinal/Published 媒体使用 `mediaOutputRoot`；
- Manifest 中的路径只是不可信候选事实，不能反向定义 root。

resolver 成功不等于 root 已安全。Path Safety 从盘符根开始逐组件打开 TrustedRoot，使用
`CreateFileW(FILE_READ_ATTRIBUTES, FILE_SHARE_READ|FILE_SHARE_WRITE|FILE_SHARE_DELETE,
FILE_FLAG_BACKUP_SEMANTICS|FILE_FLAG_OPEN_REPARSE_POINT)`，并要求：

- 输入是当前产品支持的绝对 DOS drive path；
- 每一级真实存在、可打开且是目录；
- 任一级都不是 reparse point；
- 最终 TrustedRoot 是目录；
- 可取得 `GetFinalPathNameByHandleW`、attributes、volume serial、file ID 和 link count。

TrustedRoot 缺失、不可访问、类型错误、含 reparse 或事实读取失败时，Candidate 永远不能
得到 Safe。检查器不创建缺失 root/目录。

## 3. PathSafetyResult 模型

结构化 Outcome 包含：

| Outcome | 含义 |
| --- | --- |
| `SafeForReadOnlyInspection` | 当前 handle 事实足以授权只读检查 |
| `Absent` | root/parent 链已验证，leaf 打开得到真实 not-found |
| `ParentAbsent` | 某一级 parent 缺失，不能虚构 leaf identity |
| `Inaccessible` | access/sharing/lock/privilege 等真实不可访问 |
| `OutsideTrustedRoot` | component 或 handle-resolved containment 不成立 |
| `ReparseEncountered` | root、intermediate 或 leaf 出现 reparse |
| `UnsupportedPathForm` | 当前产品合同不支持的路径语法 |
| `InvalidInput` | 空输入、无效 roots 或非 canonical SessionId |
| `TrustedRootInvalid` | root 缺失或不是目录 |
| `TypeMismatch` | Candidate 实际类型与预期 file/directory 不同 |
| `IoFailure` / `Unknown` | 其他 I/O/资源失败或未分类事实 |

结果保留 probe stage、原始 HRESULT、candidate existence/type、parent-chain 与 containment
证明位、root/candidate final path、诊断路径、reparse path/tag，以及 root/candidate 的
volume serial、file ID 与 hard-link count。打不开不等于不存在；只有明确的
`ERROR_FILE_NOT_FOUND`/`ERROR_PATH_NOT_FOUND` 且安全 parent 链已验证时才产生 `Absent`。

## 4. Existing path 的 handle 证明

Candidate 必须先通过 component-boundary 词法预筛选，但该筛选不是最终证明。实现从已经
验证的 TrustedRoot 开始逐组件打开 Candidate：

1. 每一级都用 `FILE_FLAG_OPEN_REPARSE_POINT`，不跟随 link/junction；
2. 每一级读取 attributes、reparse tag、final path 和 handle identity；
3. 每一个已打开 parent 的 final path 都再次按 path component 与 root final path比较；
4. 每一级 volume serial 必须与 TrustedRoot 相同；
5. leaf 存在时再次验证 resolved final containment 和预期类型；
6. 预期 regular file 时请求 `FILE_READ_DATA|FILE_READ_ATTRIBUTES`，因此真实 sharing/access
   阻挡会成为 `Inaccessible`，而不会假报 Safe 或 Absent。

containment 从不使用 `string starts_with(root)`。它使用 Windows 大小写不敏感的路径组件
边界、handle-resolved final path 和同卷事实，所以 `recordings2` 不会被误认为
`recordings` 的子项。

## 5. 支持的路径形式

当前固定产品合同只支持绝对 DOS drive path（`X:\...`），并逐组件拒绝空组件、`.`、
`..`、alternate separator、trailing dot/space、非法字符、ADS 冒号和保留 device name。
单个目录 trailing separator 可规范化；冗余 separator 安全失败。

以下形式明确返回 `UnsupportedPathForm`，不尝试访问：relative、UNC、`\\?\` extended
length、device namespace、forward slash、reserved device-like input。该限制是有意收窄，
不是声称兼容全部 Windows namespace。

## 6. Reparse 策略

TrustedRoot、从 root 到 Candidate 的任何 intermediate component、以及 leaf 本身都检查
`FILE_ATTRIBUTE_REPARSE_POINT` 与 `FileAttributeTagInfo`。当前最保守策略对 symbolic
link、junction、mount point 及其他 reparse tag 一律返回 `ReparseEncountered`，即使目标
最终仍在 root 内也不跟随、不自动 Safe。

真实 Windows junction 测试分别覆盖 leaf、指向 root 外的 intermediate、指向 root 内的
intermediate，以及 Manifest PublishedPath 经过 junction 的情形。

## 7. Absent 与 Inaccessible

不存在的 leaf 没有 file handle，也没有 file identity。仅当 TrustedRoot 已验证、语法受
支持、全部现有 parent 逐级无 reparse 且 final-path/volume containment 成立、最后一次
leaf open 明确返回 not-found 时，结果才是 `Absent`。

parent 缺失返回 `ParentAbsent`；SharingViolation/AccessDenied 返回 `Inaccessible`；其他
无法确认的 Win32 错误返回 `IoFailure`。真实独占共享测试证明读取阻挡不会降级成 Absent，
且失败 probe 不污染后续 probe。

## 8. Session 与 Manifest 媒体路径规则

`InspectCanonicalSessionDirectoryForReadOnly` 只接受 shared `sessionsRoot` 加 P2.6C-2a-1
canonical SessionId。它不接受 Manifest 提供的任意 SessionDirectoryPath；带花括号、
小写或其他非 canonical writer form 均为 `InvalidInput`。

`InspectRecordingMediaPathForReadOnly` 把 Manifest 的 WorkingPath、PlannedFinalPath 与
PublishedPath 全部视为不可信候选，并只相对于 shared `mediaOutputRoot` 做 regular-file
检查。媒体不被错误要求位于 `sessions/<SessionId>`，保持现有 P2.6A/P2.6B 布局。

## 9. Hard-link 与 TOCTOU 边界

`BY_HANDLE_FILE_INFORMATION` 提供 volume serial、64-bit file ID 和 hard-link count；测试
用真实 hard link 证明这些字段可作为诊断事实。它们没有写入 Manifest，也没有形成完整
hard-link mutation defense。root 内路径是同一对象，只能说明当前可只读检查，不能证明
未来可安全修改该对象的全部链接。

路径链的逐组件检查也是顺序、point-in-time 观察，不是跨调用原子事务。P2.6C-3 仍必须
补齐 persistent media identity、cross-process lifetime owner、revision re-read/expected
revision/CAS、operation-time reopen/revalidation，以及 reparse/hard-link/object replacement
TOCTOU 防御后，才可能授权极窄 reconciliation。

## 12. 已知限制与后续依赖

- 当前只支持固定 DOS drive path；UNC/extended/device namespace 是 fail-closed 限制。
- reparse 一律 Retain，不支持安全跟随。
- Path Safety 不解析 MP4，不判断 Working 媒体是否可恢复。
- sessions-only Scanner 对没有 Session 目录的孤立媒体仍有既定发现盲区。
- 结果没有跨时间稳定性，不提供 mutation authorization。
- 现有 handle file ID/link count 只是运行时诊断，尚未形成 persistent identity。

P2.6C-2b Scanner 可复用本模块执行只读事实检查，但必须保持 Manifest parse、path facts、
filesystem state 与 classification 分层，并继续把 Unknown/Inaccessible/Reparse 默认 Retain。
本报告不授权启动 2b。

P2.6C-3 前仍缺：persistent volume/file identity、跨进程 lifetime owner、revision CAS、
operation-time revalidation、硬链接/reparse/object replacement 的 mutation 级 TOCTOU 防御。

## 13. 阶段结论

Handle-based Path Safety foundations 已建立，能可靠回答 Candidate 在当前时刻能否做只读
检查，同时明确拒绝把该结论升级为写操作授权。

结论：`P2.6C-2A2-PATH-SAFETY-READY`。
