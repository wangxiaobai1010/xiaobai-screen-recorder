# P2.6B Session Manifest 最终阶段报告

## 1. 阶段目标

P2.6B 在 P2.6A Safe Publish 基线上建立每个 Recording Session 的持久事实记录，
使进程退出后仍可知道最后一次成功落盘的 Session 身份、路径、生命周期边界以及
Finalize、Validation、Publish 结果。

本阶段只负责记录事实，不扫描历史 Session，不执行 reconciliation，不自动发布、
修复或恢复视频，也不向 UI 提供恢复入口。

## 2. 为什么需要 Manifest

`XbRecordingSnapshot` 是进程内一致快照。它适合 Controller、UI 和 LongRun 读取，
但进程结束后不再存在。P2.6A 已保证 working 与 final 的安全发布关系，却没有提供
跨启动的 Session 状态载体。

Session Manifest 补充的是“最后一次成功持久化事实”：它为未来异常 Session 发现和
磁盘对账提供输入，但不能替代运行时 Snapshot，也不能仅凭自身宣称磁盘文件有效。

## 3. Snapshot 与 Manifest 边界

| 载体 | 事实范围 | 当前消费者 | 权威边界 |
| --- | --- | --- | --- |
| Recording Snapshot | 当前进程的实时状态、PTS、Finalize、Publish、资源和错误事实 | RecordingController、MainForm、LongRun | 当前运行时事实 |
| Session Manifest | 最后一次原子落盘的身份、路径、生命周期及关键操作事实 | 当前仅 Native writer 和定向测试；未来 P2.6C scanner | 跨进程持久事实，不等同于磁盘真值 |

审查确认：

- Manifest writer 位于 Native `VideoEncoderConsumer`，没有第二套 Managed 状态机。
- `RecordingController`、MainForm 和 LongRun 未读取 Manifest，继续消费 Snapshot。
- Manifest 更新结果不驱动 Encoder、Stop、Finalize、Publish 或 Snapshot 状态。
- Manifest I/O 不在 `snapshotMutex` 内执行，也不回调 Managed 或 FrameTap。

## 4. 存储设计

每个 Session 使用独立受管目录：

```text
<ManagedOutputRoot>/
  sessions/
    <SessionId>/
      manifest.json
```

Manifest 与视频位于同一受管输出根和同一卷，但不会混入用户视频列表。SessionId 必须
是规范 GUID，并同时约束 Session 目录名以及 working/final 文件名。Manifest 中的三条
路径必须是受管输出根下的完整绝对路径。

Manifest 使用 UTF-8 JSON 保存；Native 内部路径保持 UTF-16。路径、SessionId、时间、
schema、字段类型和状态组合均由严格生产 parser/validator 校验。

## 5. 字段模型

Schema v1 的持久字段包括：

- Schema：`schemaVersion`、`revision`、`writerStrategy`。
- 身份：`sessionId`、`createdAtUtc`、`updatedAtUtc`。
- 路径：`workingPath`、`plannedFinalPath`、`publishedPath`。
- 生命周期：`state`。
- 媒体边界：`workingFileOwnedBySession`、`writeSampleAttempted`、
  `frameSubmitted`。
- worker/资源：`workerExited`、`recordingResourcesReleased`、
  `residualOutstanding`。
- Finalize：`attempted`、`count`、`hresult`。
- Validation：`attempted`、`passed`、`hresult`。
- Publish：`attempted`、`published`、`hresult`。
- 错误：`errorCategory`、`errorCode`、受限长度的 `errorMessage`。

错误分类至少区分 `Recording`、`Finalize`、`Validation`、`Publish`、
`ManifestPersistence` 和 `UnknownCrash`。`Unknown` 可被 schema 表达和严格解析，但正常
live writer 不主动把已知运行结果猜成 Unknown；该分类由未来扫描/对账阶段使用。

Manifest 不复制实时 PTS、每帧计数、UI 状态、Windows 进程资源或全部 Snapshot 字段。

## 6. 生命周期写入点

正常成功 Session 的持久序列为：

```text
Created
  -> Starting
  -> Recording
  -> Stopping
  -> ReadyToPublish
  -> Published
  -> Completed
```

已知失败可从 Published/Completed/Unknown 之前的合法状态进入 `Failed`。正常路径的
revision 边界如下：

1. 创建 `Created`，revision 1。
2. Native Start 进入 `Starting`，revision 2。
3. working 文件 `CREATE_NEW` 成功后记录 Session 所有权，revision 3。
4. 第一次 `WriteSample` 成功后记录 `writeSampleAttempted=true`、
   `frameSubmitted=true` 并进入 `Recording`，revision 4。
5. 正式 Stop/Close 请求进入 `Stopping`，revision 5。
6. worker 已退出、join 完成、Finalize/Validation 成功且资源残留为 0 后进入
   `ReadyToPublish`，revision 6。
7. P2.6A Native publish 成功后记录 Publish 结果和 `publishedPath`，进入
   `Published`，revision 7。
8. 持久化最终成功状态 `Completed`，revision 8。

写入不是按秒或按帧执行。`PersistManifestRecording` 虽位于媒体提交循环之后，但使用
一次性原子边界，只在首个成功 `WriteSample` 后写一次。Stop、Ready、Published 和
Completed 同样只在既有生命周期边界提交。

## 7. 原子保存策略

首次创建和后续更新共同遵守以下流程：

1. 在 Session 目录生成唯一临时文件名，并以 `CREATE_NEW` 创建。
2. 循环完整写入 UTF-8 JSON，检查每次 `WriteFile` 结果。
3. 对临时文件执行 `FlushFileBuffers`。
4. 使用同一生产 parser 回读临时文件，重新验证 schema、SessionId、revision、路径、
   状态和全部字段组合，并确认序列化结果一致。
5. 首次创建使用同目录 `MoveFileExW(..., MOVEFILE_WRITE_THROUGH)`，不覆盖已有
   `manifest.json`。
6. 后续更新在 Session 写锁内重新读取正式 Manifest，确认磁盘 revision 仍等于
   expected revision，再使用 `ReplaceFileW` 原子替换。
7. 临时写入、Flush、校验、revision 或替换任一步失败，旧正式 Manifest 保持不变，
   临时文件由作用域清理。

revision 从 1 单调递增。调用方 revision、锁内重新读取的磁盘 revision 和待发布的
`expected + 1` 必须同时成立，因此旧 revision、延迟 writer 或非法状态迁移不能覆盖
新事实。

## 8. 失败策略

Manifest 是观察和持久化层，不是媒体控制层。当前策略为：

- Manifest 创建或任一次更新失败后，记录首次及最后失败 HRESULT，并停止本 Session
  后续 Manifest 写入，防止跳过 revision 伪造更高状态。
- 已成功落盘的旧 revision 继续保留；若首次创建失败，则该 Session 没有可信 Manifest。
- Manifest 失败不停止 Encoder，不把成功录制改写为 Failed，不改变正式 Snapshot。
- Manifest 失败不触发 working/final 删除，也不改变 P2.6A startup-garbage cleanup
  规则。
- Stop 先请求媒体源停止，再尝试写 `Stopping`，因此持久化不是安全 Stop/Finalize 的
  前置条件。
- Ready 写入失败不阻止 P2.6A publish；Published/Completed 写入失败也不能否认、
  删除或回滚已经成功的 final 文件。

录制自身失败时，Manifest 在可写前提下进入 `Failed`，并保留此前已经成立的所有权、
媒体提交、Finalize、Validation 和 Publish 子事实。Finalize、Validation 和 Publish
错误分别保存，不压缩成一个模糊字符串。

- 非法状态迁移拒绝。
- 截断/损坏 JSON 读取失败。
- `Unknown` 状态及错误分类 round-trip。
- 新 Manifest 默认资源、Finalize、Validation、Publish 字段安全。

P2.6B-2 生命周期测试覆盖：

- 真实 Start 持久化 Created、Starting 及冻结路径。
- working 所有权和首个成功 WriteSample 的 Recording 边界。
- 正常双 Session 到 revision 8 Completed，GUID、working/final 和 Session 目录互不串用。
- Stopping、ReadyToPublish、Published、Completed 的合法单调链。
- Finalize 失败、Validation 失败和 final 冲突导致的 Publish 失败均进入分类正确的

## 10. 已知限制

P2.6B 不包含：

- 启动扫描、历史 Session 枚举或 live-owner 判断。
- Manifest 与 working/final 的 reconciliation。
- 自动恢复、自动重新发布、自动删除或保留期限策略。
- 普通未 Finalize MP4 的可播放性承诺或视频修复。
- fragmented MP4、分段录制、音频或磁盘阈值。
- Recovery UI、用户确认流程或恢复中心。

Manifest 只是最后成功持久化事实。进程可能在任意两个原子文件操作之间退出，因此
Manifest 与磁盘文件不一致是预期输入，不能在 P2.6B 中被猜测性修复。

## 11. P2.6C 与 P2.6D 依赖

P2.6C 负责发现异常 Session：在确认没有 live owner 后扫描受管 `sessions` 根，严格
解析 schema/revision，重新检查三路径磁盘事实，并把缺失、损坏、落后或冲突组合分类
为可审查状态。P2.6C 不应仅凭 Manifest 自动删除、覆盖或发布媒体。

P2.6D 负责恢复能力验证：针对 P2.6C 发现并分类的候选，验证普通 MP4/working 文件在
不同中断点的实际可读取、可播放或可恢复边界，再决定允许提供哪些受控恢复动作。

P2.6C/D 都依赖 P2.6B 已冻结的 schema、Session 命名空间、严格 parser、单调 revision、
三路径、媒体提交、资源释放以及 Finalize/Validation/Publish 独立事实。

## 12. 冻结结论

最终审查确认 P2.6B 已建立独立于运行时 Snapshot 的跨进程 Session 持久事实模型，
完成受管存储、严格字段模型、关键生命周期接入、原子替换、revision 防倒退和媒体安全
优先的持久化失败隔离。

未发现 Manifest 控制录制、UI/LongRun 读取 Manifest、持久化失败破坏 working/final
或改变 P2.6A publish 的阻断问题。P2.6B 达到冻结准备标准；本结论不代表 P2.6C 扫描、
P2.6D 恢复验证或任何自动恢复能力已经完成。
