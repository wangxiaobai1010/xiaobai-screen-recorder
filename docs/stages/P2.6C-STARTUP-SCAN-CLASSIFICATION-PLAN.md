# P2.6C 启动扫描与异常 Session 分类施工图

## 1. 阶段目标

状态：**P2.6C-PLAN-AUDIT-CLOSED（设计收口，未实现）**。

本设计基于本地冻结提交
`c0805f4e678117ce6a5041deefb37a6794844066` 及标签
`p2.6b-session-manifest-pass-2026-08-07`。P2.6C 的目标是：在应用启动后，
只读发现受管输出根中的历史 Session，把最后持久化的 Manifest 事实与当前文件系统
事实交叉验证，并产生稳定、保守、可审查的分类结果，作为后续 reconciliation 和
P2.6D 恢复技术验证的输入。

```text
受信任的 ManagedOutputRoot
  -> 只枚举 sessions/<SessionId>/
  -> 严格读取 manifest.json
  -> 只探测由受信任根和 SessionId 派生的文件路径
  -> Manifest facts + filesystem facts + live-owner observation
  -> read-only classification
```

本阶段继续遵守：

- `RecordingSnapshot` 是当前进程运行时事实；
- Session Manifest 是最后一次成功持久化事实；
- 文件系统是文件是否实际存在的现场事实，但“存在”本身不等于媒体成功；
- `Completed = ReadyToPublish && Published`；
- 无法证明可以删除，就不得删除；`Unknown = Retain`。

P2.6B 当前为 **LOCAL FROZEN / REMOTE SYNC PENDING**。`origin/main` 仍为
`8a00f29b9234e8ae36395fe22db0088381f8fea7`，原因是
`TCP github.com:443 BLOCKED`。本轮不尝试 push，也不修改 Git 网络配置。

## 2. 非目标

本轮不实现：

- startup scanner、classifier 或任何生产模块；
- Manifest 自动改写、自动 reconciliation、自动 publish 或自动删除；
- working MP4 修复、可播放性推断、fragmented MP4 或分段录制；
- Recovery UI、用户确认流程、保留期限或磁盘策略；
- ABI、Manifest schema、Encoder、Publish、Completed、UI 或 LongRun 修改；
- P2.6D 恢复技术验证。

分类结果只说明“现场属于哪一种事实组合”，不承诺 working 文件可播放或可恢复。

## 3. 当前结构影响审计

### 3.1 ManagedOutputRoot 的产生、持有与传递

当前并不存在一个由 Managed 显式命名和持有的 `ManagedOutputRoot` 对象。真实链路是：

1. `MainForm.OnShown` 在 `AppContext.BaseDirectory/diagnostic-logs` 创建诊断目录。
2. `NativePreviewSession.Create` 通过 `XbPreviewCreateOptions.diagnosticLogDirectory`
   将该路径传给 Native。
3. `PreviewEngine` 保存 `diagnosticLogDirectory_`；正式录制开始时调用
   `CreateRecordingConfiguration`。
4. `VideoEncoderConfig.cpp::ArtifactsRoot` 从诊断目录向上四级得到 `artifacts`，
   再把正式录制输出根固定为 `artifacts/p2.5a-recordings`。
5. `VideoEncoderConfiguration.outputDirectory` 是当前 Native 录制 Session 的受管
   输出根；`VideoEncoderConsumer::PrepareManifest` 将它传给
   `SessionManifestStore`。

因此，当前输出根的**配置事实由 Managed 提供的诊断目录间接决定，最终路径由 Native
私有 helper 派生并持有**。未来 scanner 不能从任意 Manifest 路径反推根，也不能在
Managed 和 Native 各复制一次“向上四级”的算法。

P2.6C-2a 必须建立唯一的 Shared OutputRoot resolver 契约：

- 输入只能是当前正式录制配置已经信任的诊断目录/产品配置，不能是 Manifest 路径、
  current directory、最近视频或 UI 显示文本；
- 正式 Recording configuration 与 `SessionInspection` 必须调用同一个 resolver 实现；
- 输出是结构化 `OutputRootResolution`，至少包含成功/失败状态、绝对规范显示路径、
  由目录 handle 得到的最终路径、volume identity 和固定 `sessions` 子目录事实；
- resolver 只读，不创建目录，不跟随 reparse point；根无法安全打开或身份不确定时
  fail-closed 为 root-level error，Scanner 不访问任何子项；
- 当前仍保持固定 `artifacts/p2.5a-recordings` 语义，不在 P2.6C 增加用户目录设置。

当前固定 OutputRoot 不构成 blocker。未来若输出根允许从 D 盘改到 E 盘，旧 root 不会由
本 Scanner 自动发现；在引入可配置根前必须另行设计持久 historical-root registry 或
显式迁移。不得通过扫描整个磁盘补偿。

### 3.2 sessions 根的创建位置

`SessionManifestStore` 构造时只计算：

```text
sessionsRoot     = managedOutputRoot / "sessions"
sessionDirectory = sessionsRoot / sessionId
manifestPath     = sessionDirectory / "manifest.json"
```

实际目录由 `SessionManifestStore::SaveAtomic` 在首次 CreateManifest 时通过
`create_directories(sessionDirectory_)` 创建。sessions 根不存在是合法的“没有可发现
Session”结果，未来扫描应返回空集合，而不是使 App 启动失败。

### 3.3 现有 LoadManifest 的严格行为

`SessionManifestStore::LoadManifest` 先读取固定 `manifest.json`，再调用同一生产
validator。当前严格行为包括：

- 只接受非空且不超过 1 MiB 的文件；
- 只接受严格 UTF-8；JSON 禁止重复 key、尾随数据、浮点数、非法转义和错类型；
- 根对象必须恰好包含 schema v1 的 22 个字段，三个子对象字段数也必须精确；
- `schemaVersion`、revision、规范 GUID、UTC 时间、writer strategy、错误长度和全部
  状态枚举必须有效；
- working/planned 必须是受管根直接子文件，文件名必须与 SessionId 匹配；
- publishedPath 只能在 publish 成功后存在，且必须等于 plannedFinalPath；
- WriteSample、frame、worker、资源、Finalize、Validation、Publish 组合必须满足
  P2.6A/P2.6B 不变量；
- 任何解析、schema、路径或状态组合错误均 fail-closed。

当前 `DeserializeWide`、`ValidateManifest` 位于 `SessionManifest.cpp` 的内部实现中，
`LoadManifest` 只向调用者返回 HRESULT。这个接口足以供已知 Session 的 writer 回读，
但不足以供 Scanner 分类。

P2.6C-2a 必须提供只读、结构化 `ManifestParseResult`，至少区分：

- `Valid`；
- `NotFound`；
- `Inaccessible`；
- `MalformedJson`；
- `UnsupportedSchema`；
- `SemanticInvalid`；
- `UnknownOrFutureState`（对应 Unknown/FutureState）；
- `IoFailure`。

路径或 Manifest 文件本身不安全时另报 `UnsafePath`/`UnsafeManifestFile`，不得折叠成
`NotFound` 或 `MalformedJson`。future schema 不是 corrupt；即使最终都 Retain，也必须
保留独立原因。该只读表面可复用现有 parser/validator，但不得放宽 writer 的严格规则，
不得修改 schema，也不得用异常文字驱动分类。

### 3.4 当前启动生命周期与安全插入点

当前 Managed 启动链为：

```text
Program.Main
  -> new MainForm
  -> Application.Run
  -> MainForm.OnShown
     -> 创建 diagnostic-logs，取得窗口 Handle
     -> new PreviewLifecycleController
     -> InitializeAsync
        -> Task.Run(NativePreviewSession.Create)
        -> Preview state = Stopped
     -> GetOrCreateRecordingController
     -> UI/Timer 初始化
     -> 自动 StartPreviewAsync
```

最安全的未来插入点是 **Managed 启动编排层**：`OnShown` 已解析受信任诊断目录、Native
Session 已初始化但任何 Recording Session 尚未开始之后。扫描在后台执行，不能阻塞
窗体显示或让单个坏 Session 使 Preview 启动失败。Preview 可以启动；“开始录制”在
扫描完成、被安全取消或根级失败被记录前保持不可用，从而避免扫描新建中的 Session。
若扫描达到边界超时，先停止/放弃扫描，再开放录制，而不是让二者继续竞争。

历史扫描不属于 `RecordingController` 的状态机，也不属于
`VideoEncoderConsumer` 当前 Session 生命周期。

### 3.5 设计审查确认的契约风险（2a-1 已关闭实现项）

独立反证审查已从实际生产源码确认一个 P2.6C-2b 前必须关闭的契约 blocker：

- `PreviewEngine::GuidToString` 当前移除了 `StringFromGUID2` 结果中的 `{}`；
- `SessionManifest::ValidSessionId` 则把值与带 `{}` 的 `StringFromGUID2` 规范文本比较；
- P2.6B Native 生命周期测试构造的是带 `{}` 的 SessionId。

这不是待实证的“可能”：正式 `GuidToString` 输出不带花括号，validator 与现有测试要求
带花括号；`CreateManifest` 在 Session 目录建立前校验失败，而录制继续 fail-open，因而
可能成功发布视频但没有可扫描的 Session 目录或 Manifest。

### 3.5.1 SessionId canonical contract

统一契约以正式生产 `PreviewEngine::GuidToString` 的现有形态为准：

- canonical SessionId 是 `StringFromGUID2` 规范 GUID 文本去掉最外层 `{}` 后的 36 个
  UTF-16 字符，格式为 `8-4-4-4-12`；不带花括号，不含空白或其他包装；
- Writer 在 Session 创建时只生成一次 canonical 文本，后续不得二次格式化；
- canonical Writer 固定使用大写十六进制；这是现有 `StringFromGUID2` 生产形态，避免
  改变已发布媒体文件名；
- Session 目录名必须与该 canonical SessionId 逐字符一致；
- Manifest `sessionId` 必须与目录名和 Writer 的 canonical 值逐字符一致；
- working/final leaf 必须分别是 `<canonical>.partial.mp4` 与 `<canonical>.mp4`；
- Manifest Reader/validator 可严格接受 bare 36 字符或仅包一层 `{}` 的 38 字符 GUID，
  并可接受十六进制大小写变体；读取后必须按 GUID value 统一为大写 bare canonical。
  不接受 Trim 后才有效、额外包装或其他 GUID 语法；Writer 仍只接受 canonical form；
- Scanner 的物理 Session 目录合同仍只承认 canonical Writer form，不得通过 Trim、补/删
  花括号或改大小写猜测另一个目录。旧的带花括号物理目录只能作为 legacy/unrecognized
  事实 Retain，不能自动迁移或 reconciliation。

P2.6C-2a-1 已独立修复 Writer/validator/test 契约，并用不依赖 WGC 的正式 Native
Encoder/Manifest lifecycle 证明 SessionId、目录名、Manifest 与媒体 leaf 全链一致。2b 仍须
P2.6C-2a-2 已建立 handle-based Path Safety，并以真实 junction、共享阻挡和 25 项矩阵
通过定向验证；其实现状态由 `P2.6C-2A2-PATH-SAFETY.md` 记录。

此外，当前只有一次 Manifest 更新期间持有的 `manifest.write.lock`，没有覆盖整个
Recording Session 的跨进程 live-owner 锁。它不能用于证明历史 Session 已无活跃
writer。live owner **不阻止 P2.6C-2b 纯只读扫描**：owner 不明时分类为
`UnknownRetain + LiveOwnerUnknown`。它是允许任何自动 reconciliation 前的硬前置条件。

## 4. 扫描职责归属

推荐采用两层职责，而不是把全部逻辑塞进一个现有类：

| 层 | 职责 | 不负责 |
| --- | --- | --- |
| 新 Native `SessionInspection` 模块 | 受控枚举、严格 Manifest 读取、Win32 文件/路径/reparse 事实、纯分类 | 当前录制、Encoder、Snapshot、UI、任何写入动作 |
| Managed startup orchestrator | 决定启动时机、取消、超时、当前进程 active Session 排除、未来展示 immutable 结果 | 解析 Manifest、判断媒体有效、直接修改文件 |

Native 独立模块最合适，原因是严格 Manifest parser 已在 Native，UTF-16 路径、Win32
文件属性、reparse point 和未来文件身份检查也应位于 Native 语义域。Managed 负责调度，是因为 App
何时显示、Preview/Controller 何时可用以及何时允许新录制属于 Host 生命周期。

`VideoEncoderConsumer` 不得拥有 startup scan：它是**当前 Session** 的媒体生命周期
所有者，历史 Session 检查与其 worker、FrameTap、StopAndJoin 无关。`RecordingController`
也不得拥有扫描状态；它继续只映射当前 Native Snapshot。

## 5. 输入事实模型

分类器输入必须是一次只读观察快照，明确分三类：

### 5.1 ManifestFacts

- manifest 是否存在、是否为普通文件、是否严格读取成功；
- parse result：`Valid`、`NotFound`、`Inaccessible`、`MalformedJson`、
  `UnsupportedSchema`、`SemanticInvalid`、`UnknownOrFutureState`、`IoFailure`；
- Manifest 文件/路径不安全时独立记录 `UnsafeManifestFile`/`UnsafePath`，不读取其中路径；
- schemaVersion、revision、writerStrategy、sessionId、created/updated UTC；
- WorkingPath、PlannedFinalPath、PublishedPath；
- state、workingFileOwnedBySession、writeSampleAttempted、frameSubmitted；
- workerExited、recordingResourcesReleased、residualOutstanding；
- Finalize、Validation、Publish 独立事实；
- errorCategory、errorCode；错误文字只作本地诊断，不参与删除或成功判断。

### 5.2 FilesystemFacts

每个文件系统事实都必须使用四态基础结果：`Exists`、`Absent`、`Inaccessible`、
`UnknownOrIoError`。`UnsafeReparse`、`IdentityMismatch` 等是附加安全事实，不能把
“读取失败”降级为 `Absent`：

- Session 目录和固定 `manifest.json`；
- 由受信任 output root + SessionId 派生的 expected working/final；
- Manifest 路径与 expected path 是否一致；
- 路径是否在受控根内、是否是普通文件、是否为 reparse point；
- 文件大小；0 byte 只是事实，不单独证明可删除；
- working、planned final、published path 是否指向同一 Session 身份；旧 schema 当前没有
  持久 final identity 时必须明确为 identity unavailable，而不是用路径名冒充身份；
- working/final 同时存在、PublishedPath 与 PlannedFinalPath 不一致等冲突。

本阶段不打开 SourceReader，不解析 MP4 box，不推断可播放性。

### 5.3 CurrentProcessFacts

- 受信任的 ManagedOutputRoot 与 SessionsRoot；
- 当前进程明确 active 的 SessionId 集合；
- startup scan generation、取消状态和是否仍允许开始新录制；
- 未来的跨进程 live-owner 结果。

历史 Session 的状态分类**不得依赖 RecordingSnapshot**。Snapshot 只能用于排除本进程
当前 active Session，不能为旧 Session 补写 PTS、Finalize 或成功事实。若无法证明
没有 live owner，分类必须是 `UnknownRetain`，且禁止 reconciliation。

## 6. 分类枚举

主分类修订为以下 12 项；详细原因用 reason flags 表达，避免为每种字段组合无限扩张
枚举：

| 分类 | 含义 | 默认动作 |
| --- | --- | --- |
| `CompletedConsistent` | Manifest Completed/Published 事实与唯一 final、无 working 的当前磁盘观察一致；不声明内容身份未被外部替换 | 只读记录，final 保留 |
| `PublishedMetadataNeedsReconciliation` | Manifest 已持久 `State=Published` 且 `publish.published=true`，final 当前安全存在、working 不存在 | 保留 final；只可作为未来 Published→Completed 元数据对账候选 |
| `PublishOutcomeUnprovenRetain` | Manifest 仅为 ReadyToPublish，final 存在而 working 不存在，但当前无持久 file identity 可证明 final 来源 | final 保留；禁止自动 Published/Completed |
| `ReadyToPublishWorkingPreserved` | Ready 前置事实已持久化，working 存在、final 不存在 | 保留，等待恢复验证 |
| `IncompleteWithWorkingMedia` | 非终态/失败 Session 有媒体提交事实或非空 working | 保留，等待恢复验证 |
| `IncompleteNoMediaRetain` | 仅观察到无 WriteSample、无 frame、无 owned/有效 working；持久事实可能陈旧 | 保留；不得作为自动删除依据 |
| `PublishFailedWorkingPreserved` | Publish 明确失败且 working 保留 | 保留，等待受控动作 |
| `FinalizeOrValidationFailedWorkingPreserved` | Finalize 或 Validation 明确失败且 working 保留 | 保留，等待 P2.6D |
| `ManifestCorrupt` | 固定 manifest 存在，但 JSON/schema v1/语义无法严格读取 | 不信任其中路径，保留 |
| `ManifestMissing` | 合法 Session 目录存在但固定 manifest 不存在 | 只探测安全派生路径，保留 |
| `FilesystemConflict` | Manifest 与安全文件事实冲突，或路径越界/reparse/身份不一致 | 全部保留，禁止动作 |
| `UnknownRetain` | future schema、未知状态、I/O 不确定、live owner 不明或未覆盖组合 | 全部保留 |

建议严重程度为：`Info`、`Attention`、`RecoveryCandidate`、`CriticalRetain`。严重程度只
用于排序和展示，不授权删除、发布或修复。

建议 reason flags 至少包括：`FinalMissing`、`WorkingAndFinalBothPresent`、
`PathOutsideRoot`、`ReparsePoint`、`IdentityMismatch`、`ManifestIoError`、
`UnsupportedSchema`、`LiveOwnerUnknown`、`NoMediaProven`、`MediaSubmitted`、
`FinalizeFailed`、`ValidationFailed`、`PublishFailed`、`PublishIdentityUnavailable`、
`InventoryIncomplete`。主分类与 reason 必须是纯函数输出。

## 7. 分类矩阵

“自动 reconcile”仅表示未来 P2.6C-3 可在额外门禁后原子更新 Manifest；本轮不执行。
“未来清理”也不是当前授权。

| 现场 | 分类 | 严重度 | 保留素材 | 未来自动 reconcile | 等待 P2.6D | 未来清理 |
| --- | --- | --- | --- | --- | --- | --- |
| A. Completed，Published=true，final 存在，working 不存在 | `CompletedConsistent` | Info | final 必须保留 | 不需要 | 否 | 仅未来元数据保留策略；不自动删视频 |
| B. Completed/Published=true，但 final 不存在 | `FilesystemConflict` | CriticalRetain | 保留任何 working/旁证 | 否 | 是，且需用户/文件系统调查 | 否 |
| C. State=Published，publish=true，final 存在，working 不存在 | `PublishedMetadataNeedsReconciliation` | Attention | final 必须保留 | 仅 Published -> Completed 元数据推进；仍需 P2.6C-3a 全部门禁 | 否 | 否 |
| D. ReadyToPublish，final 存在，working 不存在 | `PublishOutcomeUnprovenRetain` | CriticalRetain | final 必须保留 | **否；路径存在不能证明该文件由本 Session publish** | 否 | 否 |
| E. ReadyToPublish，working 存在，final 不存在 | `ReadyToPublishWorkingPreserved` | RecoveryCandidate | working 必须保留 | 否；重新 publish 不是纯对账 | 是 | 否 |
| F. Recording，writeSample=true，working 存在 | `IncompleteWithWorkingMedia` | RecoveryCandidate | working 必须保留 | 否 | 是 | 否 |
| G. Starting，writeSample=false，working 不存在且 owner=false | `IncompleteNoMediaRetain` | Attention | Manifest 与全部现场仍保留 | 否 | 否 | **否；不能作为自动删除依据** |
| H. Stopping，working 存在 | `IncompleteWithWorkingMedia`；若所有媒体事实均明确为 false 且文件确认 Absent，也只能归 `IncompleteNoMediaRetain` | RecoveryCandidate | working 默认保留 | 否 | 是 | 否 |
| I. Publish 失败，working 存在 | `PublishFailedWorkingPreserved` | RecoveryCandidate | working 必须保留，现有 final 不得触碰 | 否 | 是 | 否 |
| J. Validation 失败，working 存在 | `FinalizeOrValidationFailedWorkingPreserved` | RecoveryCandidate | working 必须保留 | 否 | 是 | 否 |
| K. Finalize 失败，working 存在 | `FinalizeOrValidationFailedWorkingPreserved` | RecoveryCandidate | working 必须保留 | 否 | 是 | 否 |
| L. manifest 损坏，working 存在 | `ManifestCorrupt` | CriticalRetain | 只保留安全派生的 working；不跟随 JSON 路径 | 否 | 是 | 否 |
| M. manifest 缺失，partial 存在 | `ManifestMissing` | CriticalRetain | partial 必须保留 | 否 | 是 | 否 |
| N. manifest 存在，working/final 均不存在 | 只有 owner/write/frame 均明确 false 时为 `IncompleteNoMediaRetain`；否则 `FilesystemConflict` | Attention 或 CriticalRetain | 保留 Manifest | 否 | 冲突时是 | 否；任何分支都不自动清理 |
| O. Manifest 路径指向 output/sessions 根外 | `FilesystemConflict` + `PathOutsideRoot` | CriticalRetain | 不访问外部目标；保留 Session 目录 | 否 | 否，需安全/人工处理，P2.6D 也不能授权外部访问 | 否 |
| P. PublishedPath 与 PlannedFinalPath 不一致 | `FilesystemConflict` + `IdentityMismatch` | CriticalRetain | 两者均不由 scanner 触碰 | 否 | 否，需安全/人工处理 | 否 |
| Q. working 和 final 同时存在 | `FilesystemConflict` + `WorkingAndFinalBothPresent`；即使是已知 final 冲突也不选边 | CriticalRetain | 两者都保留 | 否 | 是（若要恢复 working） | 否 |
| R. Unknown state 或 future schema | `UnknownRetain` | CriticalRetain | 全部保留 | 否 | 待兼容 scanner；恢复则仍需 P2.6D | 否 |

对于 D，即使当前 schema 的严格 `ReadyToPublish` 已证明 FinalizeCount=1、Validation
成功、worker exited、资源已释放、residual=0，且 expected final 是普通非 reparse 文件、
working 缺失、无 live owner，当前仍**没有**持久 file identity 证明 final 是该 working
经 rename 后的同一对象。它只能 Retain，不能自动推进 Published/Completed。若 Manifest
仅停在 Recording/Stopping 而 final 已存在，同样应分类为 `UnknownRetain` 或
`FilesystemConflict`，不能跨过缺失事实猜成 Completed。

## 8. 文件事实优先规则

分类必须执行以下交叉验证：

1. Manifest 声称 Published，但 final 不存在：不能宣称成功，归冲突并保留。
2. final 存在、working 已消失，但 Manifest 仍是严格 Ready：不能证明 final 已由 P2.6A
   move 形成；不能因旧 revision 否认或删除 final，也不能自动补写成功，归
   `PublishOutcomeUnprovenRetain`。
3. working 存在且 WriteSample 已尝试、Finalize/Validation/Publish 失败或事实不明：
   working 是潜在唯一素材，必须保留。
4. 文件存在只证明路径现场，不证明它是有效 MP4；本阶段不把大小或扩展名当成功。
5. 文件缺失与文件无法访问必须分开；ACL/I/O 错误一律 `UnknownRetain` 或冲突。
6. Manifest 路径只用于比较，未通过安全校验前不能作为 Open/Delete/Move 的目标。
7. 0 byte 不能单独授权删除；`IncompleteNoMediaRetain` 即使同时观察到无 owner、
   无 WriteSample、无 frame、无安全 working，也只是一项只读分类，永不授权自动删除。

## 9. 路径安全

未来 Scanner 必须从 Shared OutputRoot resolver 取得受信任 output root，而不是信任
Manifest。P2.6C-2a 建立独立、handle-based `PathSafetyFacts` 层：

1. 将 output root 转为绝对规范路径，并以目录 Handle 获取最终路径、volume identity 和
   stable file ID；
   根本身无法安全打开时整次扫描只返回 root-level error，不访问子项。
2. `sessions` 必须是 output root 的直接子目录；只枚举其直接子目录，不递归任意树。
3. Session 目录名必须符合统一、已实证的规范 GUID；非 GUID 目录不进入 Session parser。
4. Session 目录、manifest、working、final 任一项带 `FILE_ATTRIBUTE_REPARSE_POINT` 时，
   第一版不跟随；记录 `ReparsePoint` 并 `CriticalRetain`。
5. 固定 `manifest.json` 必须是 Session 目录的直接普通文件。临时文件、lock 文件或
   其他文件不是权威 Manifest。
6. Manifest 三路径先做纯字符串/lexical 拒绝检查：相对路径、`..`、ADS、UNC、意外
   `\\?\`/device namespace、NUL/截断、trailing dot/space 和未知规范化均 fail-closed；
   允许的路径必须逐项等于由 trusted root + canonical SessionId 派生的 expected path。
7. 只有等于 expected path 后才允许以 `FILE_FLAG_OPEN_REPARSE_POINT` 打开对应对象，
   再用 handle final path、卷和 file ID 验证仍在受控根内；不能先跟随路径再判断。
8. 初版不允许 Session 目录、Manifest 或媒体文件通过 symlink/junction/mount point/
   reparse point 跳转。异常一律分类保留，不访问目标。
9. hard link 不带 reparse 标志；必须用 volume identity + stable file ID 表达对象身份，
   不能以路径文本、文件名、大小或扩展名代替。
10. expected leaf 不存在时只能证明可信父目录与固定 leaf name；`Absent` 必须来自明确的
    `ERROR_FILE_NOT_FOUND/ERROR_PATH_NOT_FOUND`，ACL、sharing、设备或瞬态 I/O 一律是
    `Inaccessible`/`UnknownOrIoError`。

Windows 路径比较按 handle 指向的真实对象及当前卷语义进行。**禁止把字符串
`starts_with` 当作“位于受控根内”的证明**；它无法抵御相似前缀、junction、8.3/设备
别名、trailing dot/space 或对象替换。也不能靠 `Trim`、补引号、加/删花括号、大小写
改写或猜测扩展名修复损坏 Manifest。长路径支持尚未实证；遇到无法规范化或打开的
路径应 fail-closed 为 `UnknownRetain`，而不是退回 ANSI/截断路径。

`PathSafetyFacts` 只描述本次观察：canonical/display path、handle final path、对象类型、
reparse 状态、volume identity、stable file ID、大小和四态访问结果。它不授予未来操作；
P2.6C-3 必须在 operation time 重新打开并验证同一事实。

## 10. 扫描根与枚举规则

唯一扫描根为：

```text
<ManagedOutputRoot>/sessions/
```

不扫描整个磁盘、用户视频目录或 Manifest 指向的任意目录。枚举规则：

- sessions 根不存在：成功返回空 inventory；
- 只处理直接子目录，不递归其未知子目录；
- 规范 GUID 目录：建立一个独立 inspection unit；
- 非 GUID 目录或 sessions 根下未知文件：不打开、不删除，记录为
  `UnrecognizedEntryRetain` 扫描诊断，但不伪造成 Session；
- 有效 Session 目录中的 `manifest.*.tmp`、`manifest.write.lock` 和其他未知项不作为
  Manifest；只记录 unexpected entries，不自动清理；
- Manifest 缺失时，只根据已验证的目录 SessionId 派生 output root 直属的 expected
  `.partial.mp4`/`.mp4` 进行只读探测；
- 没有 Session 目录的 output-root 孤立媒体不会由本 scanner 扫描。这是受控扫描边界，
  也是 Manifest 首次创建 fail-open 的已知发现盲区。它不能归入 `ManifestMissing`，
  也不能通过扩大到全盘搜索补偿；inventory 必须如实声明 coverage limitation。

每个 Session 的路径、错误、分类和 reason flags 存在独立结果对象中；枚举顺序不得影响
结果，输出可按 SessionId 稳定排序。

## 11. Reconciliation 边界

P2.6C-2 只读，不写 Manifest。未来 P2.6C-3b 可自动 reconciliation 的范围应严格限制为：

1. `State=Published`、publish=true、final 安全存在、working 不存在，且全部严格事实
   一致：原子推进为 Completed。

上述候选仅是已持久 publish 成功事实的**元数据推进**，仍必须先通过 P2.6C-3a：

- 跨进程 Session lifetime owner 证明；PID 文件或瞬时 write lock 不足；
- 写回前重新读取 Manifest，并以当前 revision 作为 expected revision/CAS 条件；
- operation time 重新打开 root、Session、Manifest 与 final，重新验证路径、reparse、
  volume/file identity、访问状态和 working absence，不能复用旧 ScanResult；
- 在检查与写回间出现 revision、对象、hard-link/reparse 或访问状态变化时立即放弃；
- crash-at-each-write 与并发 writer 测试成立；不覆盖、移动或删除任何媒体。

`State=ReadyToPublish + final exists + working absent` 明确不在自动范围。若未来要安全识别
P2.6A 的 move-success/Manifest-not-updated 窗口，需要先持久化 file identity：至少记录
working 所在 volume identity 与 stable file ID，并在 rename 后打开 final 验证仍为同一
对象，再把该身份随 publish 事实持久化。旧 schema 或任何 identity unavailable Session
只能 Retain；不得因路径、大小、时间或 hash 单独推断 Published。

以下类别不得自动 reconcile：

- `ReadyToPublishWorkingPreserved` 与 `PublishOutcomeUnprovenRetain`：重新 publish 或补写
  Published 都不是当前可证明的事实对账；
- 任意 working 媒体、Finalize/Validation/Publish failure；
- Manifest Missing/Corrupt、future schema、Unknown；
- 路径越界、reparse、身份不一致、working/final 同时存在；
- 任何 live owner 不明或文件访问错误。

`IncompleteNoMediaRetain` 不是 reconciliation，也**永远不作为自动删除依据**。Manifest
写入失败、陈旧 revision 或未持久化的首次媒体提交都可能造成假“无媒体”；自动删除、
保留期限和用户确认均不属于 P2.6C。

## 12. Startup 调用时机

推荐未来调用链：

```text
MainForm.OnShown（UI 已显示）
  -> resolve trusted output root once
  -> PreviewLifecycleController.InitializeAsync（尚无 Recording）
  -> start SessionInspectionService.ScanAsync on background task
       -> Native SessionInspection read-only scan
       -> per-Session immutable results
  -> Preview 可继续初始化/运行
  -> scan terminal / safely canceled / root-level failure recorded
  -> 才允许 RecordingController.StartAsync 被 UI 调用
  -> 后续 UI 仅展示候选，不让 Manifest 控制当前录制
```

要求：

- UI 首次显示不等待扫描；扫描进度不由 UI Timer 驱动；
- 新录制不得与尚未结束的 startup scan 争用同一 Sessions 根；
- 若用户要求立即录制，应先请求扫描取消并等待只读枚举退出，再启用 Start；
- 扫描失败不使 App/Preview 启动失败，也不能禁用正常录制到无限期；
- 当前进程 active Session 必须排除；跨进程 owner 无法证明时只分类不操作；
- 关闭窗口时取消扫描并等待 bounded completion，不 force kill，不调用 Encoder。

## 13. 错误隔离与幂等

- 每个 Session 独立 try/catch、独立文件 Handle、独立事实和分类；单个坏 JSON、ACL、
  路径或异常目录不能终止整体枚举。
- 根级错误与 Session 级错误分开。根无法安全打开时返回扫描级失败；已经完成的 Session
  结果仍可保留为诊断，但不宣称 inventory 完整。
- scanner 不修改文件，因此同一磁盘快照重复运行应产生同一分类；排序、线程调度和
  单 Session 失败不改变其他结果。
- JSON/read/path 错误必须结构化记录，不把异常文字作为分类逻辑。
- 取消只停止后续枚举；已打开 Handle 通过 RAII/using 释放，不能留下锁或后台线程。
- 任何未覆盖异常在该 Session 降级为 `UnknownRetain`；进程级 OOM 等无法可靠继续的
  情况终止 scan，但仍不得阻止 App 启动或触碰媒体。

## 14. P2.6C-2 测试施工图

### 14.1 纯分类与文件契约

- A-R 全矩阵逐项测试，分类、severity、reason、retain/reconcile flags 精确一致；
- Completed observed consistent、已持久 Published 的 metadata reconciliation candidate、
  Ready move-window 的 identity-unproven Retain；
- Recording 中断、Stopping、Finalize/Validation/Publish failure；
- no-media 只有全部正面条件成立才出现，且始终 Retain/不得删除；任一 unknown 都回退 Retain；
- `ManifestParseResult` 逐项覆盖 Valid、NotFound、Inaccessible、MalformedJson、
  UnsupportedSchema、SemanticInvalid、Unknown/FutureState、IoFailure；
- 中文 output root、Session 目录及 UTF-8/UTF-16 路径逐字符一致；
- 路径越界、`..`、相对/UNC、ADS、device path、大小写、trailing dot/space、过长路径；
- Session dir、manifest、working、final 的 symlink/junction/reparse point；
- hard link、对象替换、检查后替换与 string-prefix bypass；
- working/final 同时存在、PublishedPath 与 PlannedFinalPath 不一致；
- manifest missing/corrupt 时不跟随其中路径，只探测安全派生路径；
- unknown files/temp/lock 不被当成正式 Manifest。

### 14.2 枚举、隔离与并发

- sessions 根不存在返回空成功；
- 两个及以上 Session 混合分类互不污染；
- 单 Session 损坏、拒绝访问或异常 I/O 不影响其余 Session；
- 扫描幂等、稳定排序、取消后 Handle/任务归零；
- active current Session 被跳过；live owner unknown 禁止 reconciliation；
- 扫描期间 Start gate 不能让新 Session 进入被枚举集合；
- 正式 C API 真实短 Session 证明 SessionId/目录/Manifest/媒体身份合同一致。
- 大量目录/小 JSON 的 entry/result/concurrency 上限、取消与 `InventoryIncomplete`；
- `Exists`、`Absent`、`Inaccessible`、`UnknownOrIoError` 不互相降级。

### 14.3 禁止的测试替代

- 不用伪造 Snapshot 给历史 Session 补事实；
- 不只测试 classifier helper 而绕过真实 Win32 文件属性和 reparse 行为；
- 不通过最新 MP4、文件大小或扩展名猜测成功；
- 不运行长测，不在 P2.6C-2 测试里执行恢复、发布或删除。

## 15. P2.6D 边界

P2.6C 只回答“发现了什么、事实是否一致、是否必须保留”。P2.6D 才能通过隔离故障
实验回答：

- 未 Finalize、Finalize failure 或 validation failure 的普通 MP4 是否可读/可播放；
- 是否能从 working 安全产生新的恢复输出；
- 恢复失败时如何保证原 working 哈希不变；
- 是否需要 fragmented MP4、分段或其他容器策略。

因此 `IncompleteWithWorkingMedia`、`ReadyToPublishWorkingPreserved`、Finalize/
Validation/Publish failure 只能成为候选，不能在 P2.6C 中承诺恢复。路径安全冲突也
不能靠 P2.6D 绕过。

## 16. 安全不变量

以下不变量是 P2.6C-2a/2b/3a/3b 的共同硬约束：

1. 文件系统不可逆事实不能被旧 Manifest 否认；当前存在的 final/working 不因旧 revision
   被删除或覆盖。
2. Manifest 声明成功不能替代当前 final 文件事实；final 缺失、不可访问或身份不明时
   不得宣称当前输出可用。
3. 任何 working media 默认 Retain；不因 final 存在、0 byte、扩展名或旧状态删除。
4. Unknown、Corrupt、UnsupportedSchema、Inaccessible、IoFailure 默认 Retain。
5. 未经路径安全验证的 Manifest 路径不可访问、修改、移动或删除，只能作为诊断文本。
6. Scanner 绝对只读：不写 Manifest、不创建/删除目录、不 publish、不修复、不控制 Encoder。
7. ScanResult 不是操作授权；reconciliation 必须在 operation time 重读、重开、重验。
8. 无法证明文件属于该 Session 时，不得自动推进 Published/Completed。
9. 访问失败不等于不存在；只允许明确的 NotFound/PathNotFound 成为 `Absent`。
10. trusted root 只来自 Shared OutputRoot resolver，不来自 Manifest/current directory。
11. revision 只描述读取时版本；写回必须 re-read + expected revision/CAS，不匹配即放弃。
12. working 与 final 同时存在时两者均保留，不自动选边。
13. `IncompleteNoMediaRetain` 是观察结果，不是自动清理证明。
14. 单 Session 失败必须隔离；任何 root/entry/resource 上限都必须显式标记 inventory 不完整。
15. live owner 不明不阻止只读观察，但禁止一切自动 reconciliation。
16. Published 持久事实与当前文件身份分开；前者最多支持受限元数据推进，不授权媒体动作。

## 17. 已知风险与限制

1. **正式 SessionId 规范曾与 Manifest validator/test 不一致。** P2.6C-2a-1 已按 3.5.1
   统一并由真实 Native Encoder/Manifest lifecycle 证明；Scanner 仍不得猜测物理目录身份。
2. **当前没有跨进程 Session lifetime owner。** 一次写入锁不能证明 Session 已停止；
   在建立 owner 证据前只允许 read-only classify，禁止自动 reconcile。
3. **严格 parser 的错误结果原本过粗。** P2.6C-2a-1 已建立结构化 read status，同时
   保持 writer parser fail-closed；Scanner 必须复用该结果而非解析错误文字。
4. **受管输出根派生逻辑原本是 Native 私有 helper。** P2.6C-2a-1 已建立共享 resolver；
   Scanner 必须复用它，而不是从 Manifest 或 current directory 猜测。
5. **路径/文件系统边界采用有意收窄的产品合同。** P2.6C-2a-2 已用逐组件 handle facts、
   final path、volume identity 和 reparse fail-closed 取代 lexical authorization；UNC、
   extended/device namespace 与超出当前合同的路径形式仍明确 Unsupported/Retain。
6. **Manifest create fail-open 存在发现盲区。** 若连 Session 目录也未创建，严格只扫
   sessions 根无法发现 output root 下的孤立媒体；本阶段不扩大为视频目录扫盘。
7. **当前 Manifest 没有 persistent final file identity。** legacy/no-identity Session 只能
   Retain；Ready + final/no working 不能自动认定 Published。
8. **Scanner 结果存在 TOCTOU。** 任何未来写回都必须重新取得 handle facts 与 revision，
   不能直接执行 ScanResult 建议。

## 18. 最小实施拆分与门槛

根据独立反证审查，实施拆分固定为五段：

### P2.6C-2a Inspection Foundations

#### P2.6C-2a-1 Inspection Contracts（已实现，待独立冻结）

- 用正式 C API 实证/统一 SessionId 规范；
- 提取共享、只读 output root resolver；
- 为现有严格 Manifest parser 增加规定状态的结构化 read-only `ManifestParseResult`；

本切片不扫描、不接 UI、不写 Manifest schema；其实现状态由
`P2.6C-2A1-INSPECTION-CONTRACTS.md` 记录。

#### P2.6C-2a-2 Path Safety Foundations（已实现，待独立冻结）

- 定义 handle-based path/reparse/file facts、文件系统四态和 immutable inspection DTO；
- 不扫描、不接 UI、不写 Manifest。

实现位于独立 `SessionPathSafety.h/.cpp`，复用 shared roots 与 canonical SessionId；Native
项目、25 项定向测试和阶段报告已完成。未修改 schema、ABI、Consumer、Controller 或 UI。

**BLOCKER BEFORE P2.6C-2b：** SessionId canonical contract、Shared OutputRoot resolver、
Structured ParseResult、handle-based Path Safety primitives 必须全部通过定向审查和测试。

### P2.6C-2b Read-only Scanner + Classifier

- 新增独立 Native `SessionInspection` scanner/classifier；
- 只枚举 sessions 根；实现修订后的矩阵、分类优先级、资源上限、错误隔离、取消和幂等测试；
- 不改 Manifest，不执行 publish/delete/recovery。

### P2.6C-3a Reconciliation Evidence Foundations

- 设计并持久化 volume identity + stable file ID；rename 后验证同一对象；
- 建立跨进程 Session lifetime owner 证据，明确 PID reuse/stale PID 不构成证明；
- 建立 operation-time revalidation、revision re-read/expected revision/CAS；
- 建立 TOCTOU/reparse/hard-link/object-replacement 定向测试；
- 本切片只建立证据，不执行 reconciliation。

**MANDATORY BEFORE P2.6C-3 reconciliation：** persistent file identity、cross-process
lifetime owner、revision re-read/CAS、operation-time revalidation、TOCTOU/reparse/
hard-link defense 必须全部成立。旧 schema/no-identity Session 永久 Retain。

### P2.6C-3b Narrow Reconciliation

- 只处理严格 `PublishedMetadataNeedsReconciliation`；
- 在 3a 全部门禁下把已持久 Published 原子推进 Completed；
- `PublishOutcomeUnprovenRetain` 不进入自动动作；
- 不处理 working 恢复，不覆盖、移动或删除任何媒体。

### P2.6C-4 Managed startup + user-visible candidates

- Managed 负责后台启动、取消、超时、Start gate 和 immutable 结果展示；
- UI 只展示分类和路径，不读取 Manifest 作为当前录制状态；
- working 恢复按钮必须等待 P2.6D 证明，不在本切片承诺。

若产品暂不需要用户可见入口，P2.6C-4 可后置；P2.6C-2a/2b 仍应保持独立于
VideoEncoderConsumer 和 RecordingController。

**NON-BLOCKING LIMITATIONS：** 当前固定 OutputRoot；无 Session 目录孤立媒体发现盲区；
legacy/no-identity Session 只能 Retain；`IncompleteNoMediaRetain` 不自动清理。这些限制必须
进入 inventory/用户说明，但不授权扩大扫描范围或降低安全门禁。

## 19. 设计结论

当前结构支持在不改变 P2.6A publish、P2.6B schema 或运行时 Snapshot 的前提下建立
只读历史 Session 分类器。最小安全架构是“Native 独立 SessionInspection 领域模块 +
Managed startup 调度”，以 trusted sessions 根为唯一发现入口，以 Manifest 与文件
事实交叉验证，以 Unknown/不确定全部 Retain 为默认。

P2.6C-2a 的 SessionId、Shared OutputRoot、Structured ParseResult 和 handle-based Path
Safety 四项门禁均已实现并通过定向验证。live owner 不阻止只读 Scanner，
但与 persistent file identity、revision CAS 和 operation-time revalidation 一起阻止
任何 P2.6C-3b reconciliation。本文不授权实现、写回、删除、publish 或恢复。

结论：**P2.6C-PLAN-AUDIT-CLOSED**。
