# P2.4 OutputCanvas encoding implementation

## Scope

P2.4 adds the first internal, real product-path video-only pipeline:

`WGC -> Crop/Camera/Follow -> fixed BGRA OutputCanvas -> Custom Cursor -> RenderFrameTap lease -> VideoEncoderConsumer -> D3D11 VideoProcessor BGRA-to-NV12 -> H.264 Sink Writer -> MP4 -> Finalize -> bounded QuickRuntimeValidation`.

It does not add recording UI, a public ABI/P/Invoke, audio, pause/resume, safe publication, crash recovery, or `RecordingController`. It is enabled only by `XB_PREVIEW_DIAGNOSTIC_ENCODER=1`; all other values are disabled.

## Default-disabled invariant

`VideoEncoderConfig` parses the environment once, before the product D3D device is created. When disabled, device creation retains the P2.3B `D3D11_CREATE_DEVICE_BGRA_SUPPORT` flags and normal WARP fallback. No video-support flag, multithread protection, MF startup, encoder thread, NV12 pool, output directory, MP4, or encoder log is created.

When enabled, the renderer first requests `D3D11_CREATE_DEVICE_BGRA_SUPPORT | D3D11_CREATE_DEVICE_VIDEO_SUPPORT` on the capture adapter and enables `ID3D10Multithread::SetMultithreadProtected(TRUE)`. If either capability is unavailable, the renderer recreates the original P2.3B preview device and reports the encoder as unsupported; preview remains available and there is no CPU conversion fallback.

## Ownership and thread model

`RenderFrameTap` remains a bounded, nonblocking GPU-copy handoff. Its destructive queue has one internal owner: none, diagnostic, or encoder. Diagnostic and encoder consumers cannot coexist; conflict fails encoder startup while preview continues.

`VideoEncoderConsumer` owns an independent MTA thread. Render/FrameArrived never calls `WriteSample` or `Finalize`. Both render and encoder submissions use the same product device and the same multithread-protected immediate context. No second device, second immediate context, deferred context, shared handle, keyed mutex, staging texture, GPU Map, or full-frame CPU readback is introduced.

`VideoProcessorBlt` returning means that GPU work was submitted, not physically completed. The BGRA Tap lease is returned immediately after a successful submission because the Blt and later producer `CopyResource` commands are ordered through the same protected immediate context. A failed Blt follows the error cleanup path before the encoder stops.

The NV12 side is a fixed six-slot `D3D11_USAGE_DEFAULT` pool. A slot moves through `Free -> GpuProducing -> SubmittedToMf -> Free`. An `IMFTrackedSample` allocator callback performs the one-time return. The callback only updates short protected state and notifies a condition variable; it performs no GPU work. No free slot causes an encoder-side nonblocking drop. Late callbacks use weak shared state so a bounded shutdown timeout cannot access destroyed pool storage.

## Conversion and encoding

Input is the Tap pool's `DXGI_FORMAT_B8G8R8A8_UNORM` texture. Input views are cached by Tap generation and slot. Output is fixed-size `DXGI_FORMAT_NV12`; width and height must both be positive and even. Odd geometry is reported and rejected without cropping, padding, or modifying `SessionGeometry`/OutputCanvas.

The converter preserves the P2.2B SDR configuration: progressive RGB full-range input and BT.709 limited-range output. Sink Writer input is NV12 and output is H.264 in MP4, nominally 60/1 fps at 8,000,000 bit/s in the product configuration. Hardware transforms are requested, while encoder identity/actual hardware selection remains `Unknown` when Sink Writer cannot expose the selected MFT honestly.

## Timestamps

Accepted `SystemRelativeTime` from WGC is the only product sample-time source. The first accepted timestamp becomes zero and later sample time is `raw - first`; gaps remain in PTS and are not compressed. Missing and regressing timestamps are dropped and counted.

Duration begins at the nominal 166667 100-ns units. A bounded median of recent 8–40 ms positive deltas replaces it once cadence evidence exists. Large gaps are recorded but excluded from the cadence estimator, so a dropped-frame gap cannot pollute later sample duration. The last submitted sample uses the latest bounded estimate.

## Stop and failure order

Stop prevents new encoder frames and wakes the encoder, which completes or returns the current BGRA lease and boundedly drains/drop-returns queued leases. It then stops further conversion/writes, calls `Finalize` exactly once on the encoder thread, releases the Sink Writer, waits up to ten seconds for tracked NV12 returns, and opens the finalized file with Source Reader for `QuickRuntimeValidation`. Runtime validation reads at most eight decoded samples, checks dimensions and monotonic PTS, and never scans to EOS. The encoder then writes the final structured summary, releases converter/device-manager/MF objects, unregisters the Tap consumer, and exits. Renderer joins that thread before shutting down Tap and the remaining D3D resources.

`FullTestValidation` decodes to EOS and is called only by explicit Native integration tests. It is not reachable from `VideoEncoderConsumer`, so normal close latency does not scale with recording duration. Diagnostics separately record Finalize, tracked return, validation, encoder join, native Engine Stop, lifecycle close, and managed close durations.

The first managed `FormClosing` remains idempotent: it cancels the immediate WinForms close, sets the one-time cleanup guard, disables further commands, and synchronously calls `MainForm.Hide()` before starting or awaiting the existing single cleanup task. `Hide()` preserves the Form instance and HWND; it does not change `ShowInTaskbar`, recreate the handle, or weaken native cleanup. Repeated close messages do not create another Hide, Stop, Finalize, or final Close. Cleanup success and failure both post the same final Close after the safe native cleanup attempt completes.

Close diagnostics now correlate the native Session GUID with the managed close request, immediate Hide request/application, visibility and handle state after Hide, cleanup start/end, final Close posting, and `FormClosed`. `VisibleCloseLatencyMs` measures only first close request through synchronous `Visible == false`; it is intentionally distinct from cleanup and request-to-`FormClosed` durations. No process-exit timestamp is fabricated in-process.

Finalize or validation failure never becomes `Completed`; the encoder records failure and best-effort deletes the experimental output after releasing the writer. Timeout state remains safe through weak callback ownership. Preview lifecycle cleanup continues independently.

## Outputs and limitations

Enabled output is under `artifacts/p2.4-recordings/<session-guid>.mp4`; diagnostics are `p2.4-encoder-<session-guid>.jsonl` beside existing diagnostic logs. Disabled mode creates neither location. These experimental direct `.mp4` files do not implement final safe-save semantics; `.partial.mp4`, atomic publication, recovery, and failed-material retention belong to P2.6.

Quick Source Reader validation requires a nonempty file, matching decoded dimensions, at least one decoded frame, and monotonic sampled PTS. Full test validation additionally requires EOS and positive decoded duration. Small CPU decode/readback is confined to validation and is not part of capture or encoding.

## Verification boundary

Native tests cover disabled/config parsing, single-consumer ownership, timestamp missing/regression/gap behavior, fixed NV12 pool starvation and tracked return, five complete `VideoEncoderConsumer` Start/Stop lifecycles, and 5-second/30-second-equivalent product-module H.264 MP4 integrations. Both durations prove the runtime sample count remains fixed at eight; those explicit tests then invoke `FullTestValidation` to EOS as a separate acceptance control. Existing P2.2A, P2.2B, P2.3A, and P2.3B gates remain regression evidence. Real OutputCanvas content, live Preview responsiveness, Camera/Follow/Cursor/Resize behavior, and actual stop-produced MP4 still require the user real-machine run; this document is not formal acceptance or freeze evidence.

## Crop UV pixel-center quality correction

User review of real MP4 output found small desktop text visibly softer than the
source. A deterministic 1920x1080 GPU A/B isolated the former product Crop UV
mapping as a material cause. The old mapping treated the first and last texel
centers as interpolation endpoints:

`origin = (cropLeft + 0.5) / sourceWidth`

`scale = (cropWidth - 1.0) / sourceWidth`

Because the rasterizer already evaluates the pixel shader at output pixel
centers, that endpoint adjustment applied a second half-pixel compensation and
caused linear filtering between neighboring texels. The controlled baseline
matched only 92.00757% of OutputCanvas pixels, mismatched 165,731 pixels, and
retained 62.61404% of the one-pixel lines. Its Source-to-decoded PSNR was
21.65434 dB.

The product `ResolveCropTransform` now maps the complete half-open crop range:

`origin = cropLeft / sourceWidth`

`scale = cropWidth / sourceWidth`

with the corresponding vertical formulas. For output pixel `i`, raster UV
`(i + 0.5) / outputWidth` therefore samples
`(cropLeft + i + 0.5) / sourceWidth` whenever output and crop dimensions match.
Wide 1.0x consequently maps each output pixel center to the corresponding
source texel center without a special Wide branch.

The controlled candidate produced a pixel-exact OutputCanvas: 100% exact,
zero mismatches, zero maximum error, 100% one-pixel-line retention, and 255
checkerboard contrast. After the unchanged NV12/H.264 path, Source-to-decoded
PSNR was 40.31648 dB and one-pixel-line retention was 99.78180%. Candidate B
now calls the same product `ResolveCropTransform` implementation; Baseline A
retains the former formula only as historical evidence.

This correction changes only Crop UV coordinates. The product shader, linear
sampler, viewport, OutputCanvas sizing, Camera/Follow behavior, VideoProcessor
AutoProcessing and filters, color spaces, NV12 format, 8 Mbps bitrate, 60 FPS,
GOP, ABI, P/Invoke, and UI remain unchanged. Wide 1.0x is expected to be pixel
exact; 1.6x and 2.0x remain intentional linear upsampling and are not claimed
to be pixel exact. VideoProcessor AutoProcessing and final encoder-quality
tuning remain separate observations. P2.4 still requires user review of a new
real recording before formal acceptance.

## Startup failure diagnostics

P2.4 now records each real Native worker initialization boundary through the
single internal `StartupDiagnostics` executor. Every step emits begin and
success/failure records with the Native session GUID, stage, operation, API,
real `__FILE__`/`__LINE__` call site, worker thread, QPC/UTC time, elapsed time,
effective encoder state, applicable D3D flags/attempt/fallback, original
HRESULT and Win32 projection, and exception type/message. Missing fields are
serialized as `null`, `unknown`, or `not-applicable`; no screen content,
window titles, input text, or encoded pixels are logged.

The instrumented path follows the actual startup order: worker apartment and
P0 logger, WGC support and monitor geometry, encoder/Tap configuration,
DXGI adapter/output discovery, the D3D video-support attempt and original BGRA
fallback, multithread protection and WinRT D3D interop, SwapChain/back buffer,
real shader/buffer/sampler/rasterizer resources, RenderFrameTap and deferred
encoder-consumer registration, WGC activation/CaptureItem/FramePool/events,
CaptureSession cursor configuration, and `StartCapture`. Encoder MF/Sink
Writer/NV12 creation remains deferred until the first frame and is not
misreported as a worker-startup API.

Attempt 1 records `BGRA_SUPPORT | VIDEO_SUPPORT`; if it fails or lacks the
required multithread protection, fallback begin and attempt 2 record the
original P2.3B `BGRA_SUPPORT` path. A successful fallback clears the expected
first-attempt failure from the final startup summary while preserving both
attempt records. If both attempts fail, the final fallback HRESULT remains the
active root failure. Nested diagnostic scopes never replace the first precise
inner failure with an outer wrapper name. WorkerMain still performs the same
final catch and Error propagation; it only adds the active/last-completed
summary plus cleanup markers. HRESULTs and exceptions are rethrown unchanged.

Managed startup events use a stable `StartupAttemptId`. Once Native has created
a session, the controller emits the explicit attempt-to-SessionGuid mapping and
records Native start begin/return/throw, failure cleanup, Error/Retry state,
MainForm and PreviewSurface HWND state, visibility, disposal state, FormClosing,
and FormClosed. The existing visible Error -> Retry behavior is unchanged:
there is no automatic Hide, Close, retry, or process exit.

The historical `0x80070424` log predates these fields, so it cannot identify a
specific API retroactively. A controlled test injects that exact HRESULT to
prove that future occurrences retain the original code and identify the real
stage/operation/API call site.

## Next long-run controller rule

The next 60-minute gate must call `WaitForInputIdle`, refresh the process, and
enumerate top-level windows owned by the target PID before choosing a close
target. It must record HWND, class, visibility, and whether the title belongs
to this product; `MainWindowHandle == 0` is not evidence that the product has
no window. It may send exactly one normal `WM_CLOSE`/`CloseMainWindow` only
after confirming the target HWND. A true `CloseMainWindow()` return is only an
API return value, not `CloseAcceptedByProduct`; acceptance requires the product
Managed Close diagnostic. Missing target-window or close-log evidence is
BLOCKED, never a reason to force-kill the process. No new internal close ABI is
introduced by this diagnostic patch.
